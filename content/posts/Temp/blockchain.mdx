# 블록체인 개요
- 분산 컴퓨팅 기반 데이터 위변조 방지 기술
- 가상 화폐 시스템에서 처음으로 구현되었기 떄문에 **비트 코인**과 **이더리움** 위주로 시스템을 학습하게 됨.

## 기존 데이터 처리 시스템의 단점
1. 단일 실패 지점(Single Point of Failure)
- 중앙 서버 장애 발생시 모든 네트워크 서비스 다운
2. 중개 비용 및 낮은 효율성
- 신뢰 보증을 위한 중개 기관 개입. 수수료 발생
3. 검열과 프라이버시 문제
- 하나의 메인 시스템 존재로 인한 검열 및 보안 문제 발생 가능
4. 투명성 부족
- 악의적인 기업이 위변조 가능 

## 블록체인 기술이 내놓은 해법
- 탈중앙화 p2p 시스템 
- 해시 연결구조를 통한 데이터 불변성 및 분산 시스템을 통한 검증(51%)
- 오픈 소스에 대한 알고리즘적 신뢰 
- 데이터 공개를 통한 투명성 

# 비트코인
- 블록체인 시스템을 통해 거래의 신뢰성을 보장받는 가상 화폐
- 핵심 개념: **P2P 구조를 통한 탈중앙화**, **블록체인 기술을 통한 공개 장부**, **합의 규칙**, **PoW매커니즘**
- 비트코인 생산(채굴) 방식: 거래 중계를 통한 보수 및 수수료
- 비트코인이 해결한 디지털 화폐 문제: 
    1. 위조 방지
    2. 이중 지불 문제
    3. 소유권 확인
- 비트코인 저장 방식: Desktop, Mobile, Web, **Hardware**
- Fullnode, Lightweight Client, Third-party API Client
- 키를 통한 화폐 소유. 키 분실 시 복구 방법 존재
- 주소 관리
- 비트코인 거래 방법

# 비트코인 키(Key)
- 비대칭 키 시스템(타원곡선 암호) 사용
- Add 연산과 Double 연산이 있음. 이를 통해 nG를 찾음

## P2PK(Pay to Public Key)
- a가 b에게 코인을 지불할 때, b의 공개 키를 사용해서 트랜잭션을 올림
- b의 사인 - b의 공개키 - checksig의 형태로 스택이 쌓임. 스택 쌓으면서 op처리
- 문제점: 공개키를 얻기 위해 IP가 공개됨, 미들웨어 어택이 가능함. 
- 공개키가 대놓고 공개됨 -> 나중에 양자컴퓨터에 의한 보안 위험성 -> 최근엔 Hash 덧붙여 사용함
- 주소를 지정해야 함 -> 오타 문제 

## P2PKH
- 수신자 b가 a에게 자신의 주소(해시 sha160 결과)를 주고 a가 해당 해시가 담긴 output script를 날림
- b가 자신의 서명과 공개키를 가지고 해당 코인을 받아옴.
- Input에서의 공개키가 해시 값과 비슷한지 확인 후, 서명 확인 절차를 걸침
##### 동작 방식
- Input Script: Bob's sign, Bob's public key
- output Script: op_dup, op_hash160, bob's commitment, op_equal, op_checksign  
-> dup으로 public key 복사. 해당 키 hash160으로 해시-> 해당 해시 값이 commitment랑 일치하는지 확인 => 송금자가 지적한 수신자가 맞는지 확인  
-> check_sign으로 수신자 인증 

## P2SH
- 송신자 부담을 덜기 위해 해시를 통한 고정 20바이트 스크립트로 트랜잭션 올림.
- 해시 크기 160비트 특성상 보안에 취약했음. 

## 비트코인 주소
- 공개키(65바이트)를 hash160으로 20바이트 변환후 base58 인코딩하여 사용
- 공개키 압축을 통해 33바이트로 압축도 가능함. (x, y 각 32바이트 및 패딩 1바이트 => 65바이트) -> (타원곡선 방정식 고정이므로 x와 y부호만 => 33바이트)

## Base58 인코딩
- 원래 영어 알파벳 26 + 26 + 숫자 10개 => 62개 문자를 가지고 인코딩 하는데, 0 O, I l 식별 힘든 4개 문자 제외하고서 인코딩


## bech32 인코딩
- bc1으로 시작하는 인코딩, 트랜잭션 전송 효율 증대 및 오타 검출 강화. 
- q 취약점 존재


# 비트코인 지갑(Wallets)
- 암호키(인증)와 공개키(UTXO)의 모음
- 비결정적 키 구조 -> 키 생성시 독립적으로 완전 랜덤하게 생성됨. 

- 결정적 키 생성 -> 시드(마스터 키) 기반으로 해시함수 사용해 연속적인 키 생성
- tweak 기반으로 상수 더해 자식 비대칭 키 만듦 
- $K + (tweak + g) = g(k + tweak)$ 라는 선형적 구조로 공개키가 생성됨. (tap root)
- 시드는 12에서 24자 사이의 문자열로 인코딩. BIP-32
- 패스프레이즈: 사용자가 임의로 문자열 추가하는 것. BIP-32는 마지막 단어가 체크섬 역할 하는데 이 오류 검출 기능이 없어진다는 단점 있음. 
- 논 키 데이터(거래 메타정보)
- 암묵적 패스: 이미 정의된 패스, tweak 사용하여 암호 생성
- 출력 스크립트 기술자: 주소기반 처럼 패스 표현 가능. 기존 암시적 패스 파인딩에서 스캔 없이 바로 접근 가능.
- 최신 지갑 기술 스택: 시드 노드, 마스터 키는 BIP 39, 결정론적 지갑 생성은 BIP32, 암시적 경로는 BIP 44
- 복구코드: 랜덤 키 기반으로 비트열 생성, SHA 256 해시 값 생성 및 체크섬 추가. BIP-39를 통한 워드열 생성

- HD 지갑 생성 방식: 시드키 기반으로 512 해시 돌림. 좌측 256을 암호키로 사용, 우측 256을 체인 키로 사용해서 연쇄적 지갑 생성. 
- 확장 키 인코딩: xprv, xpub 접두사로 갈림. prv는 암호키(blue)까지 저장, pub는 공개키만 저장. 
- BIP44 표준 구조: m / 목적' / 코인_유형' / 계정' / 잔돈 / 주소_인덱스
- m/44’/0’/0’/0/2 
- 공개키 앞에 8개 비트 추가됨(32바이트 -> 33바이트). 차이 숙지(부호값)

# 트랜잭션
- Input UTXO -> Output UTXO N:M mapping
- Input UTXO에는 암호키를 통한 서명, 잠금 해제를 하고 Output UTXO는 공개키를 사용하여 잠금
- 사전 서명된, 이전 버전의 트랜잭션 -> 나중에 비트코인이 고도화되면 무용해질 수 있음. 버전 번호 분리로서 격리
- SegWit 시스템. 버전번호 나타냄으로써 기술 충돌 회피
- TX input length - input UTXO의 개수를 적어놓은 필드 존재, 0xfd = 3byte, 0xfe = 5 byte, 0xff = 9byte 뒤의 n-1바이트 읽으라는 뜻
- tx input - outpoint - input으로 사용할 코인을, 해당 코인의 위치 => 이전 트랜잭션 output id (TXID)와 해당 txid에서의 인덱스값 입력해야함
- input script - 잠금 해제를 위해 넣는 서명과 공개키. 레거시에서는 스크립트 길이와 스크립트 포함. segWit에서는 위트니스 필드로 이동돼 길이 0만 삽입
- 시퀀스 - 트랜잭션 컨펌되기 전 내용 수정을 위한 것. 이전엔 단순 시퀀스 번호 높은 트랜잭션이 새로 오면 수정했지만 이제는,  
시퀀스 번호가 0xfffff... 보다 낮음 -> 수수료 더 센 트랜잭션으로 수정 가능. 혹은 msb가 0이면 타임락 걸림. 

- output count: 출력 주소 개수
- Amount field: 출금 양(사토시 단위)
- 546 사토시 미만 거래는 더스트라 판단하고서 무시해버림. 
- OP_RETURN 데이터 저장 위한 트랜잭션, 더스트 처리에서 예외됨. 

# 인증과 인가, 검증
- 코인 주소에 대한 권한을 다루는 주제
- 비트코인 스크립트는 튜링 불완전한 반복 없는 무상태 언어. 이로써 안전성을 더함. 
- 인증은 스크립트 인풋 아웃풋 스크립트를 통한 스택 연산에 의해 마지막에 남는게 true면 트랜잭션 생성 -> 허용
- P2PK
- P2PKH
- op_multsig로 n:m 서명 매핑 가능. 마지막 자리에 op_0이라는 더미를 둠으로써 해시 꺼내는 종료지점을 알림. 
- P2SH 처리해야할 스크립트(리딤 스크립트)를 목적지로 사용함으로써 송신자의 수수료 부담을 덞

- OP_RETURN. UTXO를 기록용으로 올려 네트워크가 오염되는 경우 발생
- UTXO는 걍 냅두고 장부에만 기록 남겨서 부하 덜라는 용도로 op-return을 통한 기록 저장을 가능하게 함. 
- nLockTime. 5억 아래값이면 블록 높이를, 5억 이상 값이면 유닉스 타임 기반 제한
- 하나의 UTXO에 대해 여러개의 lock걸 수 있음. 기존 락은 증발
- OP_CLTV. 시간 잠금 걸린 트랜잭션 즉시 발행. OP_CHECKLOCKTIMEVERIFY
- OP_CSV 상대적 시간 잠금. OP_CHECKSEQUENCEVERIFY

- OP_IF, NOTIF, ELSE, ENDIF 와 같은 조건 연산자 존재
- if문으로써 endif옵션까지 넣는 것보다, OP_EQUALVERIFY 사용하는게 더 효율적임. 분기 없다면 verify 사용
- 분기는 n:m 트랜잭션에서 유용함. 분기 보고서 멀티 시그체크 하는거 파악할 것. 

- segwit, witness 도입. 동작의 템플릿화 및 공개키와 싸인을 witness 필드에 넣으면서 비용 절약. witness 필드에 있는건 TXID 해시 계산할 때 제외됨.
- p2wpkh. 해시 길이 20 바이트
- p2wsh. 해시 길이 32바이트
- nest: lagacy -> segwit일 경우, P2SH 방식을 이용해 segwit에서의 output script가 스택에 남도록 유도함. 
- MAST: input script 올리기 전에 분기 계산 후 필요한 스크립트만 올림. 관련된 해시 값 다 포함해서. 머클 트리. 
- p2C: tweak 기반으로 이미 알고있는 상대방의 공개키를 통해 공캐기`를 예측하고서 트랜잭션 생성하는 기법
- 슈노르 멀티시그: 공개키 여러개를 합성해 하나의 공개키 생성. 
- p2TR(TapRoot): OP_1을 통한 자동 연산. MAST, P2C, MULTISIG 모두 합친 기술. teak 활용.   
keypath(multisig)시, sign이 미리 계산한 teaked publickey로 풀리는지 확인.  
scriptpath(mast)시, 새로이 계산한 tweaked publickey가 merkle root기반으로 미리 계산한 값이랑 일치하는지 확인.
