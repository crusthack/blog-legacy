# 프로그래밍 언어
- 컴퓨터를 조작하기 위해 사용하는 도구. 문장을 작성함으로써 컴퓨터에게 명령을 내릴 수 있음. 
- 언어는 컴파일을 통해 기계어로 번역되어 컴퓨터가 이해할 수 있는 형태로 변환됨.
- 언어는 문장의 집합으로 구성되며, 언어마다 각각의 문법과 키워드들이 존재
- 문법들로 인해 언어마다 표현하는 방식이 달라지며, 이는 프로그래머들의 사고방식과 컴퓨터를 바라보는 시각에 영향을 미침.

## 프로그래밍 언어 등장 배경
- 기존 컴퓨터는 물리적인 장치를 통한 직접적인 기계 조작으로써 동작(Fortran)
- 물리적인 회로 변경이나 직접적인 기계어 입력, 천공 카드를 통한 프로그래밍이 일반적
- 수작업으로 이뤄지는 프로그래밍 환경을 개선하고자 하는 방법이 요구
- 프로그램을 만드는 프로그램이 필요하게 됨.  
=> 특정한 규칙(문법)에 맞춰서 문장을 작성하면 이를 기계어로 번역하여 실행할 수 있는 프로그램으로 만들어주는 컴파일러 등장

## 언어가 제공하는 제약과 추상화
- 언어가 제공하는 편리성은 제약이 많아질수록 증가함. 제약이 많아질수록 컴퓨터라는 기계와는 멀어지게 됨. 
- 언어가 제공하는 기능이 많을수록, 컴퓨터의 동작이 추상화되어 세부적인 내부 구조를 감춤. (예시: 메모리 관리, 타입 시스템)
- 언어가 제공하는 제약이 적을수록, 컴퓨터의 동작을 직면하게 하며 기계를 더 직접적으로 조작할 수 있음. (예시: C, 어셈블리)
- 컴퓨터에 대한 이해를 기반으로 구조적인 개발을 하기 위해서는 저수준 언어와 고수준 언어를 모두 이해하는 것이 중요함.

## 컴파일러와 인터프리터
- 컴파일러: 전체 코드를 한 번에 번역하여 실행 파일을 생성하는 방식.
- 인터프리터: 문장을 한 줄씩 번역하여 즉시 실행하는 방식. -> 구현 난이도가 낮고 사용이 편리하지만 실행 속도가 느림.
- 현재 컴퓨터공학의 대부분 학술 체계는 C언어 기반으로 구축되어 있음. 프로그래밍 언어론 또한 컴파일 기반으로 설명돼있음
- 오늘날, 컴파일 언어(C++, Rust)와 인터프리터 언어(Python, JavaScript), 하이브리드형(C#, Java) 등 다양한 형태의 언어가 존재
- 언어에 대한 이해 단위를 언어가 제공하는 인터페이스(문법 규칙) - Frontend, 기계어 번역 과정(컴파일) - Backend로 나누어 구분

## 언어에 대한 이해
- 언어의 문법과 제약 체계를 학습함으로써 특정한 규칙 위에서 개발함을 인지하고 더 효율적인 개발을 할 수 있음.
- 언어의 컴파일 과정을 이해함으로써 더욱 최적화된 코드를 작성할 수 있음.
- 언어의 구성을 이해함으로써 나만의 규칙을 새롭게 설정할 수 있고 해당 규칙 하에서 더 나은 표현을 할 수 있음.

# 언어의 분류와 평가
- 주요 언어의 형태 구분: **명령형**, **함수형**, **논리형**
- 명령형 언어: C, C++, Java, Python 등. 프로그램이 상태를 변경하는 명령을 중심으로 구성됨.
- 함수형 언어: Haskell, Lisp, Erlang 등. 프로그램이 수학적 함수의 조합으로 구성됨.
- 논리형 언어: Prolog, Lean 등. 프로그램이 논리적 사실과 규칙으로 구성됨.

## 언어의 평가
- 언어의 평가 기준: **표현력**, **관리성**, **실행성**
- 고려 사항: **작성력**, **가독성**, **효율성**, **강건성**, **이식성**

### 표현력(Expressiveness)
- 언어가 얼마나 다양한 개념과 아이디어를 표현할 수 있는지에 대한 척도
- 작성력(코드 길이)에 영향을 받음

### 관리성(Maintainability)
- 코드가 이해/수정/확장이 얼마나 쉬운지에 대한 척도
- 작성력(코드 길이), 가독성(코드 스타일), 이식성(다른 환경에서의 실행 가능성)에 영향을 받음

### 실행성(Executability)
- 언어가 얼마나 효율적으로 실행될 수 있는지에 대한 척도
- 효율성(시간/공간 복잡도), 강건성(안정성), 이식성(가상머신)에 영향을 받음

## 직교성(Orthogonality)
- 언어의 기능들이 서로 독립적이고 조합 가능하게 설계되어 있는 정도
- 직교성이 높을수록 언어의 표현력이 증가하고, 관리성과 실행성도 향상될 수 있음
- 예시: C언어의 포인터와 배열은 직교적이지 않음. 포인터는 배열처럼 사용할 수 있지만, 배열은 포인터처럼 사용할 수 없음.
- for문과 while문은 직교성이 낮음. for문은 while문으로 표현할 수 있고, while문도 for문으로 표현할 수 있음.


# 컴파일
- 컴파일은 고수준 언어로 작성된 코드를 저수준 언어(기계어)로 번역하는 과정. 컴파일러는 프로그램을 받고서 프로그램(혹은 에러 메시지)을 내보냄. 
- 컴파일 과정은 Frontend와 Backend로 나뉨.
- Frontend: 어휘 분석 -> 구문 분석 -> 의미 분석 -> AST 생성 -> IR 생성
- Backend: IR 최적화 -> 코드 생성 -> 코드 최적화 -> 기계어 생성
- Frontend는 언어의 문법과 의미를 분석하여 중간 표현(AST)을 생성하는 과정, Backend는 IR을 최적화하고 기계어로 번역하는 과정

## 어휘 분석(Lexical Analysis)
- 소스코드를 패턴매칭을 통해 토큰 스트림으로 변환하는 과정. 토큰은 언어의 기본 단위(키워드, 식별자, 연산자 등)를 나타냄.
- 보통 정규 표현식과 유한 오토마타를 사용하여 구현됨. Lex(Flex) 등의 도구가 어휘 분석기 생성을 지원함.
- 각 토큰은 토큰 유형(패턴)과 실제 값(렉심)으로 구성. 
- 어휘분석 실습은 주로 flex를 사용해 수행.

## 구문 분석(Syntax Analysis)
- 토큰 스트림을 받아 생성 규칙에 따라 파스 트리를 생성하는 과정. 파스 트리는 프로그램의 문법적 구조를 나타냄.
- 구문 분석을 통해 작성된 프로그램이 언어의 문법에 맞는 구조를 가지고 있는지 검사할 수 있음.
- 생성 규칙은 bnf를 통해 표현하며, 문맥 자유 문법(Context-Free Grammar)을 사용하여 정의. 
- 구문분석 방법에는 재귀 하강, LL, LR 등의 구문 분석 알고리즘이 존재. Yacc(Bison) 등의 도구가 구문 분석기 생성을 지원함.

### 파스 트리
- 문장을 구문 규칙에 따라 분석하면서 나오는 트릭 구조. 각 노드는 언어의 구성 요소(어휘 요소)를 나타내며, 트리의 구조는 프로그램의 문법적 구조를 반영함.
- 시작기호를 루트로 가지며, 비단말 기호를 생성규칙에 따라 유도하면서, 최종적으로 리프 노드가 단말 기호로 구성되는 트리 구조.
- 같은 문장에 대해 여러개의 파스 트리가 나오면 **모호한 문법**이라고 함. 모호한 문법을 피하기 위해 수행하는 기본적인 기술이 2개 존재
1. 좌결합 구조를 우결합 구조로 변경하여 좌순환 방지
2. 생성규칙 추가로 연산자 우선순위 부여

### 구문 분석 방법
| |Top-Down|Bottom-Up|
|-|-|-|
|Table-Driven|LL Parsing|LR Parsing<br/>(Shift-Reduce Parsing)|
|Hard-Wired|Recursive-Descent| |
- Top-Down 방식은 루트 노드에서부터 트리를 파싱해나가는 방식, Bottom-Up 방식은 리프 노드에서부터 트리를 파싱해나가는 방식
- Table-Driven 방식은 구문 분석 테이블을 사용하여 구문 분석을 수행하는 방식, Hard-Wired 방식은 구문 분석 알고리즘을 직접 구현하여 구문 분석을 수행하는 방식
- 재귀 하강 -> LL -> LR 순으로 점점 더 복잡한 문법을 처리할 수 있는 구문 분석 방법. 구현 난이도는 더 어려워짐.

## AST(Abstract Syntax Tree)
- 구문 분석과정에서 생성되는 자료구조로, 프로그램의 문법적 구조를 나타냄. AST는 프로그램의 의미를 분석과 코드 생성에 사용됨.
```
// sum = sum + (a * 2);
(= . (sum . ((+ . (sum . ((* . (a . (2 . nil))) . nil))) . nil)))
=> 보기 편하게 하면
=> (= . (sum . (addNode . nil)))  sum은 첫 번째 피연산자, addNode는 두 번째 피연산자
addNode => (+ . (sum . (mulNode . nil)))  sum은 첫 번째 피연산자 mulNode는 두 번째 피연산자
mulNode => (* . (a . (2 . nil)))
// 트리 시각화
                           .
                         /   \
                        =     .
                             / \
                          sum   .
                               / \
                              .   nil
                            /   \
                           +     .
                                / \
                            sum    .
                                  / \
                                .   nil
                               / \
                              *   .
                                 / \
                                a   .
                                   / \
                                  2   nil
// Lisp 트리 구조
.   -   .   -   .   -   nil
=       sum     |
                .   -   .   -   .   -   nil
                +       sum     |
                                .   -   .   -   .   -   nil
                                *       a       2                       
```
- 런타임중에 트리를 탐색하면서 의미를 평가하거나 코드생성에 사용을 함. AST는 구문 트리보다 더 간결하고 의미적으로 중요한 정보만을 담고 있음.

## 의미 분석(Semantic Analysis)
- AST를 기반으로 프로그램의 의미적 오류를 검사하는 과정. 변수 선언과 사용, 타입 일치, 함수 호출 등의 의미적 규칙을 검사함.
- 의미 분석을 통해 프로그램이 언어의 의미적 규칙에 맞는지 검사할 수 있음. 예시: 변수 선언 없이 사용, 타입 불일치, 함수 호출 시 인자 개수 불일치 등
- LSP(Language Server Protocol)와 같은 도구가 의미 분석을 지원하여 코드 편집기에서 실시간으로 오류를 표시할 수 있도록 함.
