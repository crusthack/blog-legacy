# 1. 문서 목적

현재 블로그는 저장소에 있는 MDX 파일을 Next.js가 읽어 정적 페이지로 제공하며, 슬라이드에서 작성한 메모·그림·임시 수정 내용은 브라우저 메모리에만 보관한다.

현재 방식에서는 포스트를 작성하거나 수정하려면 VS Code로 프로젝트를 열고, MDX 파일을 직접 편집한 뒤 Git 커밋·푸시·배포 과정을 거쳐야 한다. 또한 A 컴퓨터에서 작업하다가 B 컴퓨터로 이동하면 변경 내용을 먼저 커밋하고 원격 저장소에 올린 다음 다시 내려받아야 한다. 이 과정에서 커밋 누락, 최신 버전 확인, 충돌 해결과 같은 불필요한 관리 부담이 발생한다.

이번 개선의 가장 기본적인 목적은 **포스트 관리를 VS Code와 특정 개발 컴퓨터로부터 분리하는 것**이다. 어느 컴퓨터에서든 브라우저로 관리자 페이지에 로그인하여 글을 작성하고, 서버에 저장된 최신 내용을 이어서 편집할 수 있게 한다.

앞으로는 블로그를 다음과 같은 **서버 기반 콘텐츠 플랫폼**으로 확장한다.

- VS Code나 로컬 프로젝트를 열지 않고 웹에서 포스트 관리
- 여러 컴퓨터에서 동일한 최신 포스트를 이어서 작성
- 관리자가 로그인하여 개인 포스트를 등록·수정·삭제
- 포스트와 슬라이드 변경 내용을 서버에 영구 저장
- 슬라이드별 메모와 그림을 저장하고 다시 불러오기
- 게스트가 Markdown 글을 작성할 수 있는 자유게시판
- PDF를 업로드하고 페이지별 메모와 그림을 관리
- 역할과 리소스별 읽기·쓰기 권한 설정
- AWS EC2에서 Nginx, Next.js, ASP.NET Core로 운영
- 초기 데이터베이스로 SQLite 사용

이 문서는 목표 구조와 구현 순서를 정의한다. 한 번에 모든 기능을 교체하기보다 기존 정적 블로그를 유지하면서 서버 기능을 단계적으로 추가한다.

# 1.1 해결하려는 현재 작업 흐름

```txt
현재
A 컴퓨터에서 MDX 수정
    -> Git commit/push
    -> B 컴퓨터에서 pull
    -> 충돌 또는 누락 확인
    -> 다시 편집 및 배포

개선 후
어느 컴퓨터에서든 관리자 로그인
    -> 서버의 최신 포스트 열기
    -> 웹에서 작성 및 자동 저장
    -> 즉시 미리보기 또는 게시
```

서버 데이터베이스를 포스트의 **단일 원본(Source of Truth)** 으로 사용한다. Git은 애플리케이션 코드와 배포 버전을 관리하고, 일상적인 포스트 내용은 관리자 웹 화면과 서버가 관리한다.

# 2. 핵심 목표

## 2.1 개발 환경과 콘텐츠 관리 분리

- 포스트 작성에 VS Code 설치를 요구하지 않음
- 로컬 Git 상태와 관계없이 브라우저에서 최신 포스트 조회
- PC, 노트북 등 다른 기기에서 작업을 바로 이어서 수행
- 자동 저장으로 커밋·푸시 누락에 따른 내용 손실 방지
- 수정 시각과 버전 이력으로 어떤 내용이 최신인지 확인
- 필요할 때 이전 포스트 버전으로 복원

Git 기반 버전 관리는 코드에 계속 사용한다. 콘텐츠에는 DB 기반 버전과 변경 이력을 적용하여 코드 배포와 글 수정을 서로 독립시킨다.

## 2.2 콘텐츠의 서버 저장

다음 데이터를 새로고침과 재접속 이후에도 유지한다.

- 포스트 원문과 메타데이터
- 포스트 공개 상태와 권한
- 슬라이드 분할 및 순서
- 슬라이드별 텍스트 메모
- 메모 위치, 크기, 접힘 상태
- 슬라이드별 그림 획
- 업로드한 PDF와 페이지 정보
- PDF 페이지별 메모와 그림

## 2.3 역할 기반 권한

서비스의 표시 등급은 초염몽·파이숭이·불꽃숭이 세 단계로 구성한다. 서버 내부에서는 로그인한 일반 사용자와 비로그인 게스트의 소유권 및 인증 방식을 구분하기 위해 불꽃숭이를 `User`와 `Guest` 두 역할로 나눈다.

| 역할 | 표시 이름 | 설명 |
|---|---|---|
| `SuperAdmin` | 초염몽 | 계정·역할·권한과 블로그 전체를 관리하는 최고 관리자 |
| `Admin` | 파이숭이 | 위임받은 카테고리와 포스트를 관리하는 관리자 |
| `User` | 불꽃숭이 | 로그인한 일반 사용자 |
| `Guest` | 불꽃숭이 | 로그인하지 않은 방문자 |

역할 이름과 화면 표시 이름은 분리한다. 서버의 권한 판정에는 `SuperAdmin`, `Admin`, `User`, `Guest`처럼 변경하기 어려운 내부 식별자를 사용하고, UI에서는 포켓몬 이름을 표시한다. 일반 사용자와 게스트는 모두 불꽃숭이로 표시하지만, 로그인 여부·사용자 ID·콘텐츠 소유권은 서로 다르게 판정한다.

## 2.4 안전한 사용자 콘텐츠

관리자 포스트는 기존 MDX 기능을 사용할 수 있지만, 자유게시판의 게스트 글은 **Markdown만 허용**한다.

게스트가 작성한 텍스트를 MDX 코드로 실행하면 임의 컴포넌트 호출이나 스크립트 삽입 문제가 생길 수 있다. 따라서 게스트 콘텐츠는 HTML을 비활성화하거나 서버에서 정화한 뒤 렌더링한다.

# 3. 목표 시스템 구성

```txt
사용자 브라우저
    |
    v
Nginx :80 / :443
    |
    +-- /, /posts, /board, /slides
    |      -> Next.js :3000
    |
    +-- /api/*
    |      -> ASP.NET Core :5000
    |
    +-- /uploads/*

ASP.NET Core

    +-- 포스트/게시판/PDF API
    +-- 슬라이드 주석 저장 API

    v

```

- PDF 페이지 뷰어
- 로그인 상태와 권한에 따른 버튼 노출
- ASP.NET Core API 호출

## 3.2 ASP.NET Core의 책임

- 로그인, 로그아웃, 세션 관리
- 비밀번호 해시 검증
- 역할 및 리소스 권한 검사
- 포스트 CRUD
- 게시판 CRUD
- 슬라이드·메모·그림 저장
- PDF 업로드와 메타데이터 관리
- 입력 검증, 파일 검증, 감사 로그
- SQLite 트랜잭션 관리

## 3.3 Nginx의 책임

- HTTPS 종료

- 정적 파일 및 PDF 전달
- 요청 속도 제한
- 실제 클라이언트 IP 전달

# 3.4 포스트 관리 아키텍처

포스트 관리는 **작성 시스템**과 **공개 시스템**을 분리한다.

```txt
작성·관리 영역                         공개 영역

관리자 브라우저
    |
    v
Next.js 관리자 UI
    |
    v
ASP.NET Core API
    |
    +-- SQLite 원본 포스트
    +-- 초안 및 버전 이력
    +-- 게시 스냅샷
    |
    +-- 게시 요청
            |
            v
       정적 빌드 작업
            |
            v
       Next.js build
            |
            +-- 정적 HTML
            +-- 정적 JSON
            +-- 이미지/첨부 리소스
                    |
                    v
                Nginx 공개
```

ASP.NET Core는 편집 가능한 원본을 관리한다. Next.js는 게시 시점에 확정된 읽기 전용 스냅샷을 가져와 정적 HTML을 만든다. 공개 페이지 요청마다 SQLite를 조회하지 않는다.

이 구조의 목표는 다음과 같다.

- 관리자는 어느 컴퓨터에서든 브라우저로 최신 글을 편집
- 공개 포스트는 정적 HTML로 빠르게 제공
- 백엔드 또는 DB에 일시적인 장애가 발생해도 이미 게시된 글은 계속 조회
- 초안 수정이 공개 페이지에 즉시 섞이지 않음
- 빌드에 실패하면 기존 공개 버전을 그대로 유지
- 게시했던 포스트 버전으로 정확하게 롤백 가능

## 3.5 백엔드 포스트 관리 구조

ASP.NET Core는 포스트의 **단일 원본(Source of Truth)** 이다. 관리 화면에서 발생하는 모든 변경은 먼저 백엔드에 저장한다.

백엔드는 다음 책임을 가진다.

- 포스트 생성, 조회, 수정, 소프트 삭제
- Slug, 제목, 설명, 카테고리, 태그 관리
- Markdown 또는 관리자용 MDX 원문 저장
- 초안 자동 저장
- 수정 버전과 작성 이력 보관
- 게시 가능 여부 검증
- 게시 스냅샷 생성
- 정적 빌드 작업 등록
- 빌드 상태와 배포 결과 기록
- 이전 게시 버전으로 롤백

### 포스트 상태

포스트의 편집 상태와 배포 상태를 하나의 값으로 섞지 않는다.

#### 편집 상태

| 상태 | 의미 |
|---|---|
| `Draft` | 작성 중인 초안 |
| `Review` | 게시 전 검토 중 |
| `Published` | 하나 이상의 버전이 공개됨 |
| `Archived` | 목록에서는 숨기지만 데이터는 유지 |
| `Deleted` | 소프트 삭제 상태 |

#### 배포 상태

| 상태 | 의미 |
|---|---|
| `NotPublished` | 게시된 적 없음 |
| `Queued` | 정적 빌드 대기 |
| `Building` | Next.js 빌드 진행 중 |
| `Deployed` | 정적 결과물 배포 완료 |
| `Failed` | 빌드 또는 배포 실패 |

예를 들어 이미 공개된 글을 다시 수정하면 편집 중인 최신 초안과 현재 공개 중인 버전이 동시에 존재한다. 초안을 저장했다고 기존 공개 페이지가 바뀌어서는 안 된다.

### 원본과 버전 분리

`Posts`에는 현재 편집 상태와 식별 정보를 두고, 실제 원문 버전은 별도 테이블에 저장한다.

### `PostRevisions`

| 필드 | 설명 |
|---|---|
| `Id` | 리비전 ID |
| `PostId` | 대상 포스트 |
| `RevisionNumber` | 포스트 내부 버전 번호 |
| `Title` | 해당 버전의 제목 |
| `Description` | 해당 버전의 설명 |
| `Content` | 해당 버전의 Markdown/MDX 원문 |
| `MetadataJson` | 태그, 슬라이드 설정 등 부가 정보 |
| `ChangeSummary` | 변경 내용 요약 |
| `CreatedBy` | 수정 사용자 |
| `CreatedAt` | 버전 생성 시각 |

자동 저장마다 영구 리비전을 만들면 데이터가 지나치게 늘어날 수 있다. 따라서 다음 두 단계를 구분한다.

- **작업 초안:** 현재 편집 내용을 계속 갱신
- **리비전:** 수동 저장, 게시, 일정 시간 경과 등 의미 있는 시점에 생성

### `PostPublications`

| 필드 | 설명 |
|---|---|
| `Id` | 게시 ID |
| `PostId` | 대상 포스트 |
| `RevisionId` | 공개할 확정 리비전 |
| `ReleaseId` | 포함된 정적 사이트 릴리스 |
| `PublishedBy` | 게시 사용자 |
| `PublishedAt` | 게시 요청 시각 |
| `DeploymentStatus` | 빌드 및 배포 상태 |

`PostPublications`를 통해 “현재 편집 중인 버전”과 “현재 방문자에게 공개된 버전”을 구분한다.

## 3.6 게시 스냅샷

Next.js 빌드 도중 포스트가 수정되면 페이지마다 서로 다른 시점의 데이터가 섞일 수 있다. 이를 막기 위해 빌드 시작 전에 변경되지 않는 **게시 스냅샷**을 만든다.

```txt
관리자가 게시 클릭
    |
    v
백엔드가 게시할 리비전 확정
    |
    v
Release 및 게시 스냅샷 생성
    |
    v
Next.js가 동일한 ReleaseId로 전체 데이터 조회
    |
    v
정적 빌드 및 검증
    |
    v
성공한 결과물만 공개 경로로 교체
```

### `Releases`

| 필드 | 설명 |
|---|---|
| `Id` | 불변 릴리스 ID |
| `Status` | `Created`, `Building`, `Ready`, `Deployed`, `Failed` |
| `CreatedBy` | 릴리스 생성 사용자 |
| `CreatedAt` | 생성 시각 |
| `DeployedAt` | 배포 시각 |
| `BuildLogPath` | 빌드 로그 위치 |
| `ArtifactPath` | 정적 결과물 위치 |

릴리스에는 해당 시점에 공개되어야 할 모든 포스트 리비전의 목록을 고정한다. Next.js는 빌드 전체에서 동일한 `ReleaseId`를 사용한다.

## 3.7 Next.js 정적 포스트 생성 구조

Next.js는 관리자 UI도 제공하지만, 공개 포스트 빌드에서는 백엔드의 게시 스냅샷을 읽는 **정적 사이트 생성기** 역할을 한다.

빌드 흐름은 다음과 같다.

1. 빌드 명령에 `RELEASE_ID`와 내부 API 주소 전달
2. Next.js가 릴리스의 공개 포스트 목록 조회
3. `generateStaticParams`에서 모든 포스트 경로 생성
4. 각 경로가 해당 릴리스의 확정 리비전 조회
5. Markdown/MDX를 검증하고 HTML로 렌더링
6. 카테고리, 태그, 검색 인덱스, 이전·다음 글 정보 생성
7. 정적 결과물의 링크와 필수 리소스 검사
8. 성공한 빌드 결과만 새 배포 디렉터리로 승격

개념적인 빌드 API는 다음과 같다.

```txt
GET /api/build/releases/{releaseId}
GET /api/build/releases/{releaseId}/posts
GET /api/build/releases/{releaseId}/posts/{slug}
GET /api/build/releases/{releaseId}/assets
```

이 API는 인터넷에 공개하지 않는다. localhost 또는 내부 네트워크에서만 접근하게 하고, 짧은 수명의 빌드 토큰을 요구한다.

### Next.js 공개 라우트

```txt
/
/Practice/Next.js/example
/posts/{slug}
/categories/{category}
/tags/{tag}
/archive
```

현재의 카테고리 기반 URL을 유지하려면 백엔드에 `RoutePath`를 저장한다. Slug나 카테고리를 변경할 때는 기존 경로를 `PostRedirects`에 기록하여 301 리다이렉트를 생성한다.

### 정적 생성 대상

- 포스트 상세 페이지
- 포스트 목록과 페이지네이션
- 카테고리 및 태그 목록
- 사이트맵
- RSS
- 검색용 정적 인덱스
- 공개 슬라이드 데이터
- Open Graph 메타데이터

관리자 화면, 로그인, 자유게시판 작성, 자동 저장 API는 정적 생성 대상이 아니다. 이 기능은 런타임 Next.js와 ASP.NET Core API를 사용한다.

## 3.8 초안 미리보기

정적 사이트는 게시된 내용만 보여 주므로, 관리자가 초안을 확인할 별도 미리보기 경로가 필요하다.

```txt
/admin/posts/{id}/edit
/preview/posts/{id}?token=...
```

미리보기는 다음 원칙을 따른다.

- 관리자 인증 필수
- 검색 엔진 색인 차단
- 캐시 금지
- 현재 초안을 ASP.NET Core에서 조회
- 실제 공개 페이지와 동일한 Markdown/MDX 렌더러 사용
- 미리보기 URL에 영구 관리자 권한을 포함하지 않음

가능하면 렌더링 코드를 공용 패키지 또는 동일 Next.js 컴포넌트로 공유하여 미리보기와 정적 결과가 달라지는 문제를 줄인다.

## 3.9 게시와 배포 작업

관리자가 `게시` 버튼을 눌렀다고 API 요청 안에서 `next build`가 끝날 때까지 기다리지 않는다.

```txt
POST /api/posts/{id}/publish
    |
    +-- 게시 리비전과 Release 생성
    +-- BuildJobs에 작업 등록
    +-- 202 Accepted 반환

백그라운드 빌드 워커
    |
    +-- 대기 작업 가져오기
    +-- Next.js 정적 빌드
    +-- 결과 검증
    +-- 원자적 배포
    +-- 성공/실패 기록
```

### `BuildJobs`

| 필드 | 설명 |
|---|---|
| `Id` | 작업 ID |
| `ReleaseId` | 대상 릴리스 |
| `Status` | `Queued`, `Running`, `Succeeded`, `Failed` |
| `StartedAt`, `FinishedAt` | 작업 시간 |
| `ErrorMessage` | 실패 요약 |
| `RetryCount` | 재시도 횟수 |

관리자 화면은 배포 상태를 폴링하거나 Server-Sent Events로 받아 다음과 같이 보여 준다.

```txt
초안 저장됨
게시 대기 중
정적 페이지 생성 중
배포 완료
배포 실패: 로그 보기 / 다시 시도
```

## 3.10 정적 결과물 배포

정적 결과물을 현재 서비스 디렉터리에 직접 덮어쓰지 않는다.

```txt
/srv/blog/releases/
  release-100/
  release-101/
  release-102/

/srv/blog/current -> /srv/blog/releases/release-102/
```

새 릴리스는 별도 디렉터리에서 완성하고 검증한다. 검증이 끝나면 `current` 심볼릭 링크를 새 릴리스로 원자적으로 전환한다. 실패한 빌드는 현재 공개 사이트에 영향을 주지 않는다.

롤백은 `current`를 직전 성공 릴리스로 되돌리는 방식으로 처리한다.

유지 정책 예시는 다음과 같다.

- 최근 성공 릴리스 5개 유지
- 실패한 릴리스는 로그만 일정 기간 유지
- DB의 게시 이력은 삭제하지 않음
- 롤백 후 필요하면 해당 릴리스를 기준으로 다시 게시

## 3.11 포스트 수정 시나리오

### 새 포스트 등록

```txt
새 포스트 생성
    -> Draft 저장
    -> 미리보기
    -> 게시 요청
    -> 리비전 고정
    -> Next.js 정적 빌드
    -> 공개
```

### 공개 포스트 수정

```txt
현재 공개 버전 v3 유지
    |
    +-- 관리자가 새 초안 v4 편집
    +-- 자동 저장
    +-- 미리보기
    +-- 게시 성공 후 v4로 공개 전환
```

v4 빌드가 실패하면 방문자는 계속 v3를 본다.

### 포스트 삭제

삭제는 세 단계로 구분한다.

1. `Archived`: 목록과 검색에서 숨김
2. `Deleted`: 관리자 복구 가능 상태
3. `Purged`: 보존 기간 이후 영구 삭제

공개 포스트 삭제도 새 릴리스를 생성해야 정적 결과물에서 해당 HTML이 제거된다. 필요하면 삭제된 URL을 안내 페이지나 다른 포스트로 리다이렉트한다.

## 3.12 콘텐츠 리소스 관리

포스트 이미지와 첨부 파일도 특정 컴퓨터의 로컬 경로에 의존하지 않게 한다.

- 관리 화면에서 이미지 업로드
- 백엔드가 파일 형식, 크기, 파일명 검증
- 콘텐츠에는 파일의 영구 ID 또는 공개 URL 삽입
- 게시 스냅샷에 사용 중인 리소스 목록 포함
- Next.js 빌드가 정적 결과물로 복사하거나 Nginx 업로드 경로 사용
- 사용되지 않는 파일은 즉시 삭제하지 않고 보존 기간 후 정리

초기 EC2 단일 서버에서는 `/srv/blog/uploads`를 사용할 수 있다. 이후 S3와 CloudFront로 옮기더라도 콘텐츠 원문의 리소스 ID가 바뀌지 않도록 저장 구조를 설계한다.

## 3.13 빌드 성능 전략

모든 게시마다 전체 사이트를 다시 생성하는 방식은 초기 블로그 규모에서는 가장 단순하고 안전하다.

포스트 수가 늘어나 빌드 시간이 문제가 되면 다음 순서로 개선한다.

1. Markdown 파싱 결과 캐시
2. 변경되지 않은 이미지 처리 결과 재사용
3. 카테고리·검색 인덱스만 선택적으로 재생성
4. Next.js 캐시 또는 부분 빌드 검토
5. 필요하면 정적 HTML과 ISR 혼합

첫 버전부터 복잡한 증분 빌드를 직접 구현하지 않는다. 전체 빌드가 운영 가능한 동안에는 불변 릴리스 전체 빌드가 일관성과 롤백 측면에서 유리하다.

## 3.14 Git과 콘텐츠의 역할 분리

| 대상 | 관리 주체 |
|---|---|
| Next.js 및 ASP.NET Core 코드 | Git |
| DB 스키마 마이그레이션 | Git |
| UI 컴포넌트와 MDX 허용 컴포넌트 | Git |
| 포스트 원문과 메타데이터 | ASP.NET Core + SQLite |

코드 배포와 포스트 게시도 분리한다.

- **콘텐츠 게시:** 현재 애플리케이션으로 새 정적 포스트 릴리스 생성

코드가 바뀌어 모든 정적 페이지를 다시 생성해야 할 때는 최신 게시 스냅샷으로 새 릴리스를 빌드한다.

## 3.15 카테고리 설계 원칙

카테고리는 포스트에 저장되는 단순 문자열이 아니라 독립된 계층형 데이터로 관리한다.

```txt
Root
├─ Practice
│  ├─ Next.js
│  │  ├─ MDX 문법
│  │  └─ 블로그 개선 계획
│  └─ ASP.NET Core
├─ Theory
│  ├─ Network
│  └─ ComputerScience
└─ Project
```

카테고리와 포스트의 관계는 다음 원칙을 따른다.

- 카테고리는 다른 카테고리를 부모로 가질 수 있음
- 하나의 카테고리에 여러 포스트가 포함됨
- 포스트는 기본적으로 하나의 대표 카테고리를 가짐
- 태그는 카테고리와 분리하여 다대다 관계로 관리
- 카테고리 이름, URL Slug, 화면 순서를 별도로 관리
- 카테고리를 이동해도 포스트 ID와 리비전은 변경되지 않음
- URL 변경 시 기존 주소를 리다이렉트로 보존

첫 버전에서는 포스트당 대표 카테고리 하나만 허용한다. 여러 주제 연결은 태그로 해결한다. 포스트를 여러 카테고리에 동시에 연결하면 대표 URL, 탐색 경로와 정렬 정책이 복잡해지므로 실제 요구가 생긴 뒤 확장한다.

## 3.16 카테고리 데이터 모델

### `Categories`

| 필드 | 형식 | 설명 |
|---|---|---|
| `Id` | UUID | 변경되지 않는 카테고리 ID |
| `ParentId` | UUID, nullable | 상위 카테고리, 최상위는 `null` |
| `Name` | TEXT | 화면에 표시할 이름 |
| `Slug` | TEXT | URL에 사용할 경로 조각 |
| `Description` | TEXT | 카테고리 설명 |
| `SortOrder` | INTEGER | 같은 부모 아래 표시 순서 |
| `AccessLevel` | TEXT | 기본 읽기 권한 |
| `DefaultPostAccessLevel` | TEXT | 새 포스트의 기본 공개 범위 |
| `IsVisible` | INTEGER | 메뉴와 목록 노출 여부 |
| `CreatedBy` | UUID | 생성 관리자 |
| `CreatedAt`, `UpdatedAt` | TEXT | UTC 시각 |
| `DeletedAt` | TEXT | 소프트 삭제 시각 |
| `Version` | INTEGER | 동시성 제어 값 |

같은 부모 아래에서는 `Slug`가 중복될 수 없도록 복합 고유 인덱스를 둔다.

```txt
UNIQUE (ParentId, Slug) WHERE DeletedAt IS NULL
```

예를 들어 다음 두 경로는 허용한다.

```txt
/Practice/Next.js
/Theory/Next.js
```

부모가 다르기 때문에 `Next.js` Slug가 같아도 전체 경로는 다르다.

### 계층 저장 방식

SQLite 초기 버전에서는 `ParentId`를 이용하는 **인접 목록(Adjacency List)** 방식을 사용한다.

장점:

- 구조가 단순함
- 카테고리 이동은 `ParentId` 변경으로 처리
- EF Core에서 표현하기 쉬움
- 현재 블로그 수준의 깊이와 개수에 충분함

전체 하위 트리는 SQLite 재귀 CTE로 조회한다.

```sql
WITH RECURSIVE category_tree AS (
  SELECT Id, ParentId, Name, Slug, 0 AS Depth
  FROM Categories
  WHERE Id = @rootId

  UNION ALL

  SELECT c.Id, c.ParentId, c.Name, c.Slug, t.Depth + 1
  FROM Categories c
  JOIN category_tree t ON c.ParentId = t.Id
  WHERE c.DeletedAt IS NULL
)
SELECT * FROM category_tree;
```

카테고리 수가 매우 많아져 조회 성능이 문제가 될 때만 Materialized Path 또는 Closure Table을 검토한다.

## 3.17 카테고리 경로

카테고리의 전체 URL은 자신의 `Slug`만 저장하지 않고 부모 경로를 따라 계산한다.

```txt
Category
  Id: category-nextjs
  Name: Next.js
  Slug: Next.js
  Parent: Practice

계산된 경로
  /Practice/Next.js
```

성능과 빌드 편의를 위해 계산된 전체 경로를 `CategoryPaths` 또는 캐시 컬럼으로 보관할 수 있다. 단, 원본 계층은 `ParentId`이며 경로 캐시는 카테고리 이동 시 트랜잭션 안에서 갱신한다.

URL 대소문자와 문자 정책은 처음부터 고정한다.

- 화면 이름에는 한글, 공백, 특수문자 일부 허용
- Slug는 URL에 안전한 문자만 허용
- 앞뒤 `/` 제거
- `.`과 `..` 금지
- 예약 경로 `admin`, `api`, `board`, `preview`, `uploads` 금지
- 같은 부모 아래 대소문자만 다른 Slug 중복 금지

현재 URL과의 호환을 위해 영문 대소문자를 유지할 수 있지만, 서버와 정적 빌드가 동일한 비교 규칙을 사용해야 한다.

## 3.18 카테고리별 포스트 관계

`Posts`의 문자열 `Category` 필드는 제거하고 `CategoryId` 외래 키로 연결한다.

```txt
Categories (1) ------ (N) Posts
```

포스트의 URL은 다음 두 방식 중 하나로 설계할 수 있다.

### 카테고리 경로 포함

```txt
/{categoryPath}/{postSlug}
/Practice/Next.js/blog-improvement-roadmap
```

장점:

- 현재 블로그 URL 구조와 잘 맞음
- 포스트의 주제를 URL에서 확인 가능

단점:

- 카테고리를 이동하면 포스트 URL도 변경됨
- 하위 포스트 전체의 리다이렉트 관리 필요

### 카테고리와 독립된 URL

```txt
/posts/{postSlug}
```

장점:

- 카테고리를 옮겨도 포스트 URL이 유지됨
- 링크 안정성이 높음

단점:

- 현재 URL과 차이가 큼
- 전체 사이트에서 Slug가 유일해야 함

현재 경로를 유지하는 것이 중요하므로 첫 버전은 **카테고리 경로 포함 방식**을 사용한다. 대신 내부 참조는 URL이 아니라 `PostId`로 관리하고, 이동 전 URL은 자동으로 리다이렉트한다.

## 3.19 카테고리 관리 화면

관리자 화면 `/admin/categories`는 트리 형태로 구성한다.

```txt
[+ 최상위 카테고리]

Practice
  ├─ Next.js          포스트 12개  [추가] [수정] [이동] [삭제]
  └─ ASP.NET Core     포스트  4개  [추가] [수정] [이동] [삭제]
Theory
  ├─ Network          포스트  8개
  └─ ComputerScience  포스트 10개
```

관리 기능:

- 최상위 카테고리 추가
- 선택한 카테고리 아래에 하위 카테고리 추가
- 이름, Slug, 설명 수정
- 드래그 또는 이동 창으로 부모 변경
- 같은 부모 아래 순서 변경
- 메뉴 노출 여부 변경
- 기본 읽기 권한 설정
- 포함된 직접 포스트와 전체 하위 포스트 수 표시
- 삭제 전 영향 범위 확인

트리 UI에서 드래그 앤 드롭을 제공하더라도 키보드와 버튼으로 이동할 수 있는 대체 UI를 함께 둔다.

## 3.20 카테고리 추가

추가 절차:

```txt
부모 카테고리 선택
    -> 이름 입력
    -> Slug 자동 제안
    -> 설명과 기본 권한 설정
    -> 서버 검증
    -> DB 저장
    -> 새 정적 릴리스 대기
```

서버 검증 항목:

- 관리자 권한
- 부모 카테고리 존재 여부
- 최대 계층 깊이
- 같은 부모 아래 Slug 중복
- 예약 Slug
- 이름과 설명 길이
- 부모 카테고리의 삭제 상태

권장 최대 깊이는 4~5단계다. 기술적으로 무제한 계층을 허용하더라도 지나치게 깊은 메뉴는 탐색성과 URL 가독성을 해친다.

카테고리만 추가하고 포스트가 없다면 공개 메뉴에 바로 표시하지 않을 수 있다. `IsVisible`과 “빈 카테고리 표시” 정책을 분리한다.

## 3.21 카테고리 수정

### 이름만 수정

`Name`만 변경하고 `Slug`를 유지하면 공개 URL은 바뀌지 않는다. 가장 안전한 수정이다.

### Slug 수정

Slug 변경은 해당 카테고리와 모든 하위 카테고리·포스트의 공개 URL에 영향을 준다.

서버는 변경 전에 다음 영향을 계산하여 관리자에게 보여 준다.

```txt
변경 전: /Practice/Next.js
변경 후: /Practice/nextjs

영향:
- 하위 카테고리 2개
- 공개 포스트 12개
- 생성할 리다이렉트 15개
```

승인 후 하나의 트랜잭션에서 다음 작업을 수행한다.

1. 카테고리 Slug 변경
2. 해당 하위 트리의 경로 캐시 갱신
3. 이전 카테고리 및 포스트 경로를 리다이렉트 테이블에 기록
4. 새 정적 사이트 릴리스 생성

### 설명, 순서, 표시 상태 수정

URL에는 영향을 주지 않지만 카테고리 목록과 내비게이션 HTML이 바뀌므로 정적 재빌드가 필요하다. 여러 카테고리를 연속 수정할 때 매번 빌드하지 않도록 변경을 모아 한 번에 게시할 수 있다.

## 3.22 카테고리 이동

카테고리 이동은 `ParentId`를 변경하는 작업이다.

다음 이동은 금지한다.

- 자기 자신을 부모로 지정
- 자신의 하위 카테고리 아래로 이동
- 삭제된 카테고리 아래로 이동
- 최대 깊이를 초과하는 이동
- 대상 부모 아래에서 Slug가 충돌하는 이동
- 권한상 관리할 수 없는 카테고리로 이동

이동 전후 예시:

```txt
변경 전
Practice
└─ Next.js

변경 후
Theory
└─ Next.js
```

이동하면 하위 포스트의 `CategoryId`는 그대로 유지된다. 카테고리의 부모만 바뀌며, 계산된 공개 URL과 리다이렉트가 갱신된다.

대규모 하위 트리 이동은 API 요청 안에서 정적 빌드까지 기다리지 않는다. DB 변경과 리다이렉트 생성 후 새 릴리스를 빌드 큐에 등록한다.

## 3.23 카테고리 삭제

카테고리는 즉시 물리 삭제하지 않고 소프트 삭제한다. 삭제 시 하위 카테고리와 포스트 처리 방법을 반드시 선택하게 한다.

### 비어 있는 카테고리

하위 카테고리와 포스트가 없으면 바로 소프트 삭제할 수 있다.

### 포스트가 있는 카테고리

다음 선택지를 제공한다.

1. 다른 카테고리로 포스트 이동 후 삭제
2. 포스트를 `미분류(Uncategorized)`로 이동 후 삭제
3. 포스트까지 보관 처리 후 삭제
4. 삭제 취소

포스트가 남아 있는데 카테고리만 제거하여 외래 키가 끊기는 상태는 허용하지 않는다.

### 하위 카테고리가 있는 카테고리

다음 선택지를 제공한다.

1. 하위 카테고리 전체를 다른 부모 아래로 이동
2. 하위 카테고리를 삭제 대상의 부모로 한 단계 올림
3. 전체 하위 트리를 보관 처리
4. 삭제 취소

“전체 하위 트리 삭제”는 영향 범위를 보여 주고 카테고리 이름을 다시 입력하는 확인 절차를 둔다.

### DB 삭제 정책

- `Categories.ParentId`: 기본적으로 `RESTRICT`
- `Posts.CategoryId`: 기본적으로 `RESTRICT`
- 애플리케이션 서비스가 이동 또는 보관을 먼저 수행
- 실수로 연쇄 물리 삭제되는 `CASCADE DELETE`는 사용하지 않음
- 보존 기간 이후에도 게시 이력과 리다이렉트에 참조된 카테고리는 바로 제거하지 않음

## 3.24 미분류 카테고리

시스템 카테고리 `Uncategorized`를 하나 둔다.

- 일반 관리자 화면에서 삭제 불가
- 부모 변경 불가
- 카테고리 없이 가져온 기존 포스트의 임시 위치
- 카테고리 삭제 시 선택 가능한 이동 대상
- 공개 메뉴에서는 숨길 수 있음

`CategoryId = null`을 허용하는 것보다 미분류 카테고리를 사용하는 편이 목록, 권한, 정적 경로 생성 로직을 단순하게 만든다.

## 3.25 카테고리 복구

소프트 삭제된 카테고리는 관리자 휴지통에서 복구할 수 있다.

복구 검사:

- 원래 부모가 존재하는지
- 같은 부모 아래 동일 Slug가 새로 생겼는지
- 원래 하위 포스트가 다른 카테고리로 이동했는지
- 복구 후 URL 충돌이 발생하는지

충돌이 있으면 새 부모 또는 새 Slug를 선택한 뒤 복구한다. 삭제 당시 함께 보관된 하위 트리와 포스트를 일괄 복구할지 선택할 수 있게 한다.

## 3.26 카테고리 정렬

같은 부모 아래의 카테고리는 `SortOrder`로 정렬한다.

권장 정렬 규칙:

```txt
SortOrder ASC
Name ASC
Id ASC
```

드래그 정렬 후 모든 행을 다시 번호 매기지 않도록 100, 200, 300처럼 간격을 두거나 LexoRank 형태를 사용할 수 있다. 초기 규모에서는 정수 간격 방식으로 충분하다.

포스트 정렬은 카테고리 정렬과 분리한다.

| 포스트 정렬 | 용도 |
|---|---|
| `PublishedAt DESC` | 기본 최신순 |
| `Title ASC` | 제목순 |
| `ManualOrder` | 강의나 시리즈 순서 |
| `Pinned DESC` | 상단 고정 |

카테고리마다 기본 포스트 정렬 방식을 설정할 수 있다.

## 3.27 카테고리 권한 상속

카테고리에 기본 읽기 권한과 새 포스트의 기본 권한을 설정한다.

```txt
Theory: Public
└─ InternalStudy: Authenticated
   └─ DraftNotes: Private
```

권한 정책:

- 새 하위 카테고리는 부모 권한을 기본값으로 제안
- 새 포스트는 소속 카테고리의 기본 권한을 상속
- 포스트가 명시적인 권한을 가지면 카테고리 기본값보다 우선
- 하위 카테고리가 부모보다 더 공개적으로 설정될 때 경고
- 관리자는 모든 카테고리 접근 가능

권한 상속 값을 매 요청마다 트리 탐색으로 계산하지 않도록 유효 권한을 캐시할 수 있지만, 최종 판정은 ASP.NET Core에서 수행한다.

## 3.28 카테고리 API

```txt
GET    /api/categories/tree
GET    /api/categories/{id}
POST   /api/categories
PATCH  /api/categories/{id}
POST   /api/categories/{id}/move
POST   /api/categories/reorder
DELETE /api/categories/{id}
POST   /api/categories/{id}/restore
GET    /api/categories/{id}/delete-impact
GET    /api/categories/{id}/posts
```

삭제 전 영향 조회 응답 예시:

```json
{
  "categoryId": "0190...",
  "directPostCount": 12,
  "descendantCategoryCount": 2,
  "descendantPostCount": 5,
  "publishedPostCount": 14,
  "affectedPaths": [
    "/Practice/Next.js",
    "/Practice/Next.js/blog-improvement-roadmap"
  ],
  "allowedStrategies": [
    "move",
    "promote-children",
    "archive-tree"
  ]

```

카테고리 변경 API에도 `Version`을 전달하여 다른 관리자 화면의 수정 내용을 실수로 덮어쓰지 않게 한다.

## 3.29 리다이렉트 관리

### `RouteRedirects`

| 필드 | 설명 |
|---|---|
| `Id` | 리다이렉트 ID |
| `OldPath` | 이전 공개 경로 |
| `NewPath` | 새 공개 경로 |
| `StatusCode` | 일반적으로 301 |
| `Reason` | 카테고리 이동, Slug 변경, 포스트 이동 |
| `CreatedAt` | 생성 시각 |

카테고리 또는 포스트 경로가 변경될 때 기존 경로를 자동 등록한다.

다음 상태는 금지한다.

- 리다이렉트 순환
- 자기 자신으로 리다이렉트
- 여러 단계를 불필요하게 거치는 체인
- 서로 다른 포스트가 같은 새 경로를 사용

새 리다이렉트를 만들 때 기존 체인을 최종 경로로 압축한다.

```txt
/old-a -> /old-b -> /new

정리 후
/old-a -> /new
/old-b -> /new
```

Next.js 정적 빌드는 `RouteRedirects`를 읽어 정적 리다이렉트 페이지 또는 Nginx용 리다이렉트 맵을 생성한다.

## 3.30 Next.js의 카테고리 정적 생성

게시 릴리스에는 카테고리 트리와 각 카테고리에 포함된 공개 포스트 목록을 함께 고정한다.

Next.js가 생성할 결과:

- 카테고리별 목록 페이지
- 상위·하위 탐색 메뉴
- Breadcrumb
- 카테고리별 페이지네이션
- 카테고리 RSS 또는 사이트맵 항목
- 이전 URL 리다이렉트
- 빈 카테고리의 404 또는 안내 페이지

빌드 시 검증:

- 모든 공개 포스트가 유효한 카테고리를 참조하는지
- 중복 RoutePath가 없는지
- 카테고리 순환이 없는지
- 삭제된 카테고리가 공개 스냅샷에 포함되지 않았는지
- 리다이렉트가 유효한 최종 경로를 가리키는지
- 권한이 없는 포스트가 공개 목록에 포함되지 않았는지

포스트나 카테고리 변경이 작업 DB에 저장되었더라도 게시 릴리스를 만들기 전까지는 현재 정적 사이트에 반영하지 않는다.

## 3.31 기존 폴더 구조 가져오기

현재 `posts` 디렉터리 구조를 초기 카테고리 트리로 가져온다.

```txt
posts/
  Practice/
    Next.js/
      mdxgrammar.mdx

변환
Categories: Practice -> Next.js
Post: mdxgrammar
RoutePath: /Practice/Next.js/mdxgrammar
```

가져오기 절차:

1. 폴더를 위에서 아래로 탐색
2. 각 폴더를 카테고리로 생성
3. MD/MDX 파일을 포스트로 생성
4. Frontmatter를 포스트 메타데이터로 변환
5. 기존 URL을 `RoutePath`로 보존
6. 중복 Slug와 잘못된 파일명을 보고서로 출력
7. 미리보기 및 검증 후 실제 DB에 반영

`index.mdx` 처리 정책은 별도로 둔다.

- 카테고리 소개 페이지로 변환
- 또는 일반 포스트로 유지
- 동일 카테고리 URL과 충돌하지 않게 규칙 고정

권장 방식은 `index.mdx`의 본문을 카테고리 설명용 콘텐츠로 가져오고, 별도의 포스트가 필요하면 명시적인 Slug를 부여하는 것이다.

## 3.32 카테고리 구현 순서

1. `Categories`와 `CategoryId` 스키마 추가
2. 미분류 시스템 카테고리 생성
3. 폴더 기반 기존 카테고리 가져오기 도구 구현
4. 카테고리 트리 조회 API
5. 관리자 트리 UI와 추가·수정
6. 이동 및 순서 변경
7. 삭제 영향 분석과 안전한 삭제 전략
8. 경로 변경 리다이렉트 생성
9. Next.js 카테고리 목록과 Breadcrumb 정적 생성
10. 권한 상속과 일반 사용자 관리 범위 확장

# 4. 인증과 사용자 식별

## 4.1 관리자 로그인

초기 버전에서는 관리자 계정 하나부터 시작한다.

- 관리자 ID와 비밀번호로 로그인
- 비밀번호는 평문으로 저장하지 않고 강한 해시로 저장
- ASP.NET Core 쿠키 인증 사용
- 쿠키에 `HttpOnly`, `Secure`, `SameSite` 설정
- 상태 변경 요청에 CSRF 방어 적용
- 로그인 실패 횟수 제한
- 관리자 페이지와 쓰기 API에서 서버 권한을 다시 검사

화면에서 버튼을 숨기는 것은 편의 기능일 뿐 보안 장치가 아니다. 모든 생성·수정·삭제 요청은 ASP.NET Core가 최종 권한을 검사해야 한다.

## 4.2 일반 사용자

일반 사용자 기능이 필요해지는 시점에 회원가입 또는 관리자의 초대 방식으로 확장한다.

초기 단계에서는 다음 중 하나를 선택한다.

1. 관리자 계정만 실제 로그인 가능하게 구현
2. `User` 테이블과 역할 구조는 미리 만들되 일반 사용자 가입은 비활성화

두 번째 방식이 이후 확장에 유리하다.

## 4.3 게스트 IP 식별

게스트 자유게시판 글에는 작성 당시 IP를 저장하거나, 개인정보 노출을 줄이기 위해 IP의 해시 값을 저장한다.

IP는 계정처럼 신뢰할 수 있는 고유 식별자가 아니다.

- 같은 공유기·회사·통신망 사용자는 동일 IP를 사용할 수 있음
- 모바일 네트워크에서는 IP가 자주 바뀔 수 있음
- 프록시 또는 VPN으로 변경 가능
- IPv6 주소가 변경될 수 있음

따라서 IP는 스팸 방지와 운영 참고용으로 사용하고, 게스트 글 수정·삭제에는 별도의 **수정 비밀번호** 또는 **작성 토큰**을 사용한다.

권장 방식은 다음과 같다.

- 글 작성 시 게스트가 수정 비밀번호 입력
- 서버에는 수정 비밀번호의 해시만 저장
- IP 원문은 제한된 기간만 저장하거나 HMAC으로 가명 처리
- 관리자만 제한적으로 IP 관련 정보를 확인
- Nginx가 전달한 헤더는 신뢰 가능한 프록시 구성을 통해서만 사용

| 자유게시판 글 작성 | 허용 | 허용 | 허용 | 허용 |
| 본인 게시판 글 수정·삭제 | 허용 | 허용 | 허용 | 수정 비밀번호 필요 |
| 타인 게시판 글 수정·삭제 | 허용 | 관리 범위 내 허용 | 거부 | 거부 |
| PDF 등록·삭제 | 허용 | 관리 범위 내 허용 | 정책에 따라 허용 | 거부 |
| PDF 주석 읽기 | 허용 | 허용 | 공개 범위에 따라 허용 | 공개 범위에 따라 허용 |
| 개인 PDF 주석 작성 | 허용 | 허용 | 허용 | 초기 버전에서는 거부 |
| 역할 및 최고 권한 설정 | 허용 | 거부 | 거부 | 거부 |
| 위임된 콘텐츠 권한 설정 | 허용 | 허용 | 거부 | 거부 |

## 5.2 포스트별 권한

역할만으로는 세밀한 공개 범위를 표현하기 어렵기 때문에 포스트에 접근 수준을 둔다.

| 접근 수준 | 의미 |
|---|---|
| `Public` | 누구나 읽을 수 있음 |
| `Authenticated` | 로그인한 사용자만 읽을 수 있음 |
| `Private` | 작성자와 관리자만 읽을 수 있음 |
| `Custom` | 지정한 사용자 또는 역할만 접근 가능 |

쓰기 권한은 다음 순서로 판정한다.

1. 관리자인가?
2. 콘텐츠 작성자인가?
3. 해당 콘텐츠에 명시적인 쓰기 권한이 있는가?
4. 모두 아니면 거부

## 5.3 권한 관리 목표

권한 시스템은 다음 질문에 서버가 일관되게 답할 수 있어야 한다.

- 이 사용자가 카테고리를 메뉴에서 볼 수 있는가?
- 이 사용자가 특정 포스트의 존재를 알 수 있는가?
- 포스트 본문을 읽을 수 있는가?
- 해당 카테고리에 새 포스트를 만들 수 있는가?
- 포스트 원문, 메모와 그림을 수정할 수 있는가?
- 초안을 공개할 수 있는가?
- 포스트를 이동하거나 삭제할 수 있는가?
- 다른 사용자의 권한을 변경할 수 있는가?

UI의 버튼 노출, Next.js 라우트, ASP.NET Core API가 서로 다른 규칙을 사용하지 않도록 모든 최종 권한 판정은 백엔드의 공통 `AuthorizationService`에서 수행한다.

## 5.4 권한 종류

권한을 단순한 읽기·쓰기 두 개로만 나누면 게시와 삭제처럼 위험도가 다른 작업을 구분하기 어렵다.

| 권한 | 내부 이름 | 설명 |
|---|---|---|
| 목록 확인 | `List` | 카테고리 또는 포스트 제목이 목록에 노출됨 |
| 읽기 | `Read` | 포스트 본문과 공개 주석 조회 |
| 생성 | `CreatePost` | 카테고리 아래 새 포스트 작성 |
| 수정 | `Edit` | 포스트 원문과 메타데이터 수정 |
| 주석 수정 | `EditAnnotations` | 메모와 그림 생성·수정·삭제 |
| 게시 | `Publish` | 초안을 정적 공개 릴리스에 포함 |
| 이동 | `Move` | 다른 카테고리로 이동 |
| 삭제 | `Delete` | 포스트 또는 카테고리 소프트 삭제 |
| 권한 관리 | `ManagePermissions` | 다른 사용자와 역할의 권한 변경 |
| 카테고리 관리 | `ManageCategory` | 카테고리 이름, Slug, 순서, 하위 구조 변경 |

`Write`라는 화면용 묶음 권한을 제공할 수 있지만, DB와 서버에서는 위 권한으로 분해한다.

```txt
Writer preset
  = List + Read + CreatePost + Edit + EditAnnotations

Publisher preset
  = Writer + Publish

CategoryManager preset
  = Publisher + Move + Delete + ManageCategory
```

프리셋은 관리 UI의 편의 기능이며 저장 시 실제 개별 권한으로 변환한다.

## 5.5 권한 대상

권한을 받을 수 있는 주체는 다음과 같다.

| 주체 | 의미 |
|---|---|
| `Role:Guest` | 로그인하지 않은 불꽃숭이 |
| `Role:User` | 로그인한 모든 불꽃숭이 |
| `Role:Admin` | 위임된 범위를 관리하는 파이숭이 |
| `Role:SuperAdmin` | 시스템 전체를 관리하는 초염몽 |
| `User:{id}` | 특정 사용자 |

초기 버전은 역할 단위 권한만 제공하고, 이후 특정 사용자 권한을 추가할 수 있다. DB 구조는 처음부터 역할과 사용자 주체를 모두 표현할 수 있게 만든다.

향후 팀 기능이 필요해지면 `Group:{id}`를 추가할 수 있지만, 첫 버전에는 포함하지 않는다.

## 5.6 권한 효과

각 권한 규칙에는 세 가지 상태가 있다.

| 효과 | 의미 |
|---|---|
| `Inherit` | 상위 카테고리 또는 기본 역할 정책 사용 |
| `Allow` | 명시적으로 허용 |
| `Deny` | 명시적으로 거부 |

화면에서는 체크박스 하나보다 다음과 같은 3상태 선택을 사용한다.

```txt
○ 상속
● 허용
× 거부
```

명시적 `Deny`는 같은 범위의 `Allow`보다 우선한다. 단, `SuperAdmin` 역할은 시스템 복구를 위해 모든 콘텐츠에 접근할 수 있는 최종 권한을 가진다. `Admin`은 위임된 관리 범위의 ACL을 따르며 전역 우회 권한을 갖지 않는다.

## 5.7 카테고리 권한

카테고리 권한은 다음 두 역할을 한다.

1. 카테고리 자체를 읽고 관리할 권한
2. 하위 카테고리와 포스트가 상속할 기본 권한

예시:

```txt
Practice
  Guest: List Allow, Read Allow
  User:  CreatePost Deny

Practice/Internal
  Guest: List Deny, Read Deny
  User:  List Allow, Read Allow

Practice/Internal/Draft
  User:  Edit Allow
  User:  Publish Deny
```

상위 카테고리에서 권한을 바꾸면, 하위에서 별도로 재정의하지 않은 카테고리와 포스트에 영향을 준다.

### 카테고리 권한 항목

- 이 카테고리를 메뉴와 목록에서 볼 수 있는 역할
- 이 카테고리 아래 공개 포스트를 읽을 수 있는 역할
- 새 포스트를 만들 수 있는 역할
- 하위 카테고리를 만들 수 있는 역할
- 기존 포스트를 이 카테고리로 이동할 수 있는 역할
- 카테고리 정보와 순서를 수정할 수 있는 역할
- 카테고리를 삭제할 수 있는 역할
- 권한 규칙을 변경할 수 있는 역할

## 5.8 포스트 권한

포스트는 소속 카테고리 권한을 기본값으로 상속한다. 예외가 필요한 포스트에만 별도 ACL을 둔다.

예시:

```txt
Category: Practice/Next.js
  Guest Read: Allow
  User Edit: Deny

Post: 비공개 작업 계획
  Guest List: Deny
  Guest Read: Deny
  User Read: Allow
  User Edit: Deny
```

포스트 권한 관리 항목:

- 목록 노출
- 본문 읽기
- 원문과 메타데이터 수정
- 메모와 그림 수정
- 게시 및 게시 취소
- 다른 카테고리로 이동
- 소프트 삭제와 복구
- 다른 사용자의 권한 변경

### `List`와 `Read` 분리

`Read`가 거부된 포스트를 목록에 제목만 보여 줄지 정책이 필요하다.

권장 기본 정책:

- `List = Deny`: 제목, 설명, URL 존재 모두 숨김
- `List = Allow`, `Read = Deny`: 제목과 잠금 표시만 노출 가능
- `Read = Allow`: `List`도 암묵적으로 허용

비공개 관리자 포스트는 게스트에 대해 `List`와 `Read`를 모두 거부한다.

## 5.9 소유자 권한

포스트에는 `OwnerId`가 있다. 소유자는 기본적으로 다음 권한을 가진다.

- `List`
- `Read`
- `Edit`
- `EditAnnotations`

소유자라고 해서 자동으로 `Publish`, `Delete`, `ManagePermissions`를 허용하지 않는다. 일반 사용자가 자신의 글은 수정할 수 있지만 관리자 승인 없이 공개하거나 삭제할 수 없게 구성할 수 있다.

소유자 기본 권한도 정책으로 관리한다.

| 역할 | 소유자 기본 권한 |
|---|---|
| 초염몽 `SuperAdmin` | 모든 권한 |
| 파이숭이 `Admin` | 위임된 범위의 읽기, 수정, 주석 수정, 게시 및 관리 |
| 불꽃숭이 `User` | 본인 콘텐츠의 읽기, 수정, 주석 수정 |
| 불꽃숭이 `Guest` | 자유게시판 전용 수정 비밀번호 정책 |

게스트 자유게시판 글은 일반 포스트 ACL과 별도로 게스트 수정 비밀번호를 사용한다.

## 5.10 상속 및 우선순위

권한은 가까운 리소스의 명시적 규칙이 상위 기본값보다 우선하도록 계산한다.

```txt
시스템 역할 기본값
    -> 상위 카테고리 ACL
    -> 하위 카테고리 ACL
    -> 포스트 ACL
    -> 특정 사용자 ACL
```

권한 하나에 대한 판정 순서:

1. 사용자가 비활성 또는 차단 상태면 거부
2. `SuperAdmin`이면 허용
3. 해당 포스트의 특정 사용자 `Deny` 확인
4. 해당 포스트의 특정 사용자 `Allow` 확인
5. 해당 포스트의 역할 `Deny` 확인
6. 해당 포스트의 역할 `Allow` 확인
7. 가까운 카테고리부터 상위 방향으로 역할 및 사용자 규칙 확인
8. 소유자 기본 권한 확인
9. 시스템 역할 기본값 확인
10. 어떤 규칙도 없으면 거부

기본값은 **거부(Default Deny)** 다. 새로운 기능이나 권한 종류를 추가했을 때 기존 사용자가 자동으로 권한을 얻지 않도록 한다.

### 우선순위 예시

```txt
Practice
  Role:User / Read = Allow

Practice/Private
  Role:User / Read = Deny

Post A
  User:kim / Read = Allow
```

- 일반 불꽃숭이: `Post A`를 제외한 `Private` 포스트 읽기 거부
- 사용자 `kim`: `Post A` 읽기 허용
- 초염몽: 항상 허용

특정 사용자 허용이 카테고리 역할 거부를 덮을 수 있는 정책을 위와 같이 명시한다. 보안상 절대 공개하면 안 되는 영역은 사용자 예외를 허용하지 않는 `LockedDown` 정책을 별도로 둘 수 있다.

## 5.11 ACL 데이터 모델

카테고리와 포스트별로 별도 권한 테이블을 만들기보다 공통 ACL 테이블을 사용한다.

### `AccessControlEntries`

| 필드 | 설명 |
|---|---|
| `Id` | ACL 행 ID |
| `ResourceType` | `Category`, `Post`, `PdfDocument` |
| `ResourceId` | 대상 리소스 ID |
| `SubjectType` | `Role`, `User` |
| `SubjectId` | `Guest`, `User`, `Admin`, `SuperAdmin` 또는 사용자 ID |
| `Permission` | `Read`, `Edit`, `Publish` 등 |
| `Effect` | `Allow`, `Deny` |
| `CreatedBy` | 규칙을 만든 관리자 |
| `CreatedAt`, `UpdatedAt` | 변경 시각 |

`Inherit`는 행을 저장하지 않는 방식으로 표현한다. UI에서 상속을 선택하면 해당 ACL 행을 삭제한다.

중복 규칙을 방지하는 고유 인덱스:

```txt
UNIQUE (
  ResourceType,
  ResourceId,
  SubjectType,
  SubjectId,
  Permission
)
```

### `PermissionAuditLogs`

| 필드 | 설명 |
|---|---|
| `Id` | 감사 로그 ID |
| `ActorId` | 변경 수행 사용자 |
| `ResourceType`, `ResourceId` | 변경 대상 |
| `BeforeJson` | 변경 전 규칙 |
| `AfterJson` | 변경 후 규칙 |
| `Reason` | 변경 사유 |
| `CreatedAt` | 변경 시각 |

권한 변경은 보안상 중요한 작업이므로 누가 언제 어떤 규칙을 바꿨는지 기록한다.

## 5.12 권한 프리셋

관리 UI에서 모든 권한을 매번 하나씩 설정하지 않도록 프리셋을 제공한다.

| 프리셋 | Guest | User | 용도 |
|---|---|---|---|
| 공개 읽기 | `List`, `Read` | `List`, `Read` | 일반 블로그 포스트 |
| 로그인 전용 | 거부 | `List`, `Read` | 회원 전용 자료 |
| 관리자 전용 | 거부 | 거부 | 개인 초안과 관리 문서 |
| 사용자 작성 | `List`, `Read` | `List`, `Read`, `CreatePost`, `Edit` | 사용자 게시 영역 |
| 읽기 전용 보관 | `List`, `Read` | `List`, `Read` | 수정이 끝난 문서 |

프리셋 적용 시 기존 사용자별 예외 규칙을 유지할지 삭제할지 확인한다.

## 5.13 권한 관리 UI

### 카테고리 권한 화면

```txt
Practice / Internal

             목록  읽기  글 생성  수정  게시  이동  삭제  권한관리
불꽃숭이 Guest  거부  거부    거부    거부  거부  거부  거부    거부
불꽃숭이 User   허용  허용    상속    상속  거부  거부  거부    거부
파이숭이 Admin  허용  허용    허용    허용  상속  상속  상속    상속
초염몽 SuperAdmin 허용 허용   허용    허용  허용  허용  허용    허용

[하위 항목에 상속] [프리셋 적용] [변경 영향 확인] [저장]
```

각 셀은 `상속`, `허용`, `거부` 중 하나를 선택한다.

함께 표시할 정보:

- 현재 값
- 어느 상위 카테고리에서 상속되었는지
- 최종 유효 권한
- 직접 설정과 상속 값의 시각적 구분
- 변경으로 영향을 받는 하위 카테고리와 포스트 수

### 포스트 권한 화면

포스트 편집 화면의 `권한` 탭에서 설정한다.

```txt
기본 정책: Practice/Next.js에서 상속
공개 범위: 공개 읽기

역할별 예외
- Guest / Read: 상속
- User / Edit: 허용
- User / Publish: 거부

사용자별 예외
- kim / Edit: 허용
```

“카테고리 기본값으로 되돌리기” 기능은 해당 포스트의 ACL 행을 삭제한다.

## 5.14 권한 변경 영향 분석

카테고리 권한을 저장하기 전에 영향을 미칠 리소스를 계산한다.

```json
{
  "categoryId": "0190...",
  "changedPermissions": [
    {
      "subject": "Role:Guest",
      "permission": "Read",
      "from": "Allow",
      "to": "Deny"
    }
  ],
  "affectedCategoryCount": 3,
  "affectedPostCount": 42,
  "currentlyPublishedPostCount": 35,
  "requiresStaticRebuild": true
}
```

공개 포스트가 비공개로 바뀌면 새 정적 릴리스에서 HTML, 검색 인덱스, RSS, 사이트맵, 카테고리 목록을 모두 제거해야 한다.

## 5.15 권한 관리 API

```txt
GET  /api/categories/{id}/permissions
PUT  /api/categories/{id}/permissions
GET  /api/categories/{id}/permissions/effective
POST /api/categories/{id}/permissions/impact

GET  /api/posts/{id}/permissions
PUT  /api/posts/{id}/permissions
GET  /api/posts/{id}/permissions/effective
POST /api/posts/{id}/permissions/impact

GET  /api/users/{userId}/accessible-resources
GET  /api/permission-audit-logs
```

권한 변경 요청 예시:

```json
{
  "resourceVersion": 12,
  "reason": "회원 전용 카테고리로 변경",
  "entries": [
    {
      "subjectType": "Role",
      "subjectId": "Guest",
      "permission": "List",
      "effect": "Deny"
    },
    {
      "subjectType": "Role",
      "subjectId": "Guest",
      "permission": "Read",
      "effect": "Deny"
    },
    {
      "subjectType": "Role",
      "subjectId": "User",
      "permission": "Read",
      "effect": "Allow"
    }
  ]
}
```

이 API는 `ManagePermissions` 권한을 요구한다. 요청자가 자기 자신의 권한을 올리거나 마지막 관리자 접근 권한을 제거하지 못하도록 추가 검증한다.

## 5.16 ASP.NET Core 권한 판정

컨트롤러마다 역할 문자열을 직접 비교하지 않는다.

```csharp
await authorizationService.AuthorizeAsync(
    user,
    resource: post,
    permission: Permissions.Edit
);
```

정책 핸들러가 다음 정보를 조합한다.

- 현재 사용자와 역할
- 사용자 활성 상태
- 포스트 소유자
- 포스트 ACL
- 소속 카테고리와 상위 카테고리 ACL
- 시스템 기본 정책

조회 API도 권한을 적용한다.

- 목록 쿼리에서 `List` 가능한 데이터만 반환
- 상세 API에서 `Read` 검사
- 존재를 숨겨야 하는 비공개 리소스는 `403` 대신 `404` 반환 가능
- 수정 요청은 `Edit`
- 메모와 그림 요청은 `EditAnnotations`
- 게시 요청은 `Publish`
- ACL API는 `ManagePermissions`

권한 판정 결과를 짧게 캐시할 수 있지만, ACL이나 역할이 변경되면 관련 캐시를 즉시 무효화한다.

## 5.17 Next.js와 정적 페이지 권한

정적 HTML은 URL을 아는 누구나 읽을 수 있으므로 **공개 권한이 있는 포스트만 정적 파일로 생성**한다.

| 공개 범위 | 제공 방식 |
|---|---|
| Guest `Read = Allow` | 정적 HTML 생성 |
| 로그인 사용자 전용 | 런타임 인증 페이지에서 제공 |
| 특정 사용자 전용 | 런타임 인증 페이지에서 제공 |
| 관리자 전용 | 관리자/미리보기 경로에서만 제공 |

로그인 전용 포스트를 정적 HTML로 생성한 뒤 화면에서 숨기는 방식은 사용하지 않는다. 파일 자체가 공개 서버에 배치되므로 보안이 보장되지 않는다.

게시 릴리스 생성 시 백엔드가 다음을 분리한다.

```txt
Public manifest
  -> Next.js 정적 빌드 대상

Protected content
  -> ASP.NET Core 권한 검사 후 런타임 제공
```

권한 변경으로 공개 포스트가 비공개가 되면 반드시 새 정적 릴리스를 배포하여 기존 HTML과 관련 검색 데이터를 제거한다.

## 5.18 카테고리 목록 노출

카테고리 자체의 `List` 권한과 포함 포스트 권한을 함께 고려한다.

- 카테고리 `List = Deny`: 메뉴와 Breadcrumb에서 숨김
- 카테고리 `List = Allow`, 읽을 수 있는 포스트 없음: 빈 카테고리 정책 적용
- 부모 `List = Deny`, 하위 `List = Allow`: 직접 URL 접근은 허용할 수 있지만 일반 메뉴 경로가 끊기므로 설정 경고
- 공개 정적 메뉴에는 Guest가 볼 수 있는 카테고리만 포함
- 로그인 후 메뉴에는 해당 사용자의 유효 권한으로 카테고리 추가

가능하면 부모보다 하위 카테고리가 더 공개적인 역전 구조를 피한다.

## 5.19 메모와 그림 권한

포스트 본문과 주석 편집 권한을 분리한다.

예시:

- 강의 자료 본문은 관리자만 수정
- 불꽃숭이 일반 사용자는 개인 메모와 그림 작성 가능
- 파이숭이 관리자는 위임된 범위의 공용 메모와 그림 관리 가능
- 공용 메모와 그림은 관리자 또는 허용된 편집자만 수정
- 불꽃숭이는 공개된 메모와 그림만 읽기

주석 레이어별 판정:

| 레이어 | 읽기 | 쓰기 |
|---|---|---|
| `Published` | 포스트 `Read` 권한 | 직접 수정 불가 |
| `Document` | 포스트 `Read` 권한 | `EditAnnotations` 필요 |
| `Personal` | 소유자와 관리자 | 소유자와 관리자 |

포스트를 읽을 권한이 없는 사용자는 개인 주석 API에도 접근할 수 없다.

## 5.20 위험 작업 보호

다음 작업은 일반 수정 권한보다 강하게 보호한다.

- 카테고리 전체 권한 변경
- 공개 포스트를 비공개로 변경
- 비공개 포스트를 공개로 변경
- 하위 항목에 권한 일괄 적용
- 마지막 관리자 권한 제거
- 대량 포스트 이동 또는 삭제
- 다른 사용자의 `ManagePermissions` 부여

보호 방법:

- 최근 로그인 또는 비밀번호 재확인
- 영향 범위 미리보기
- 카테고리 이름 재입력
- 감사 로그
- 소프트 삭제와 롤백
- 대량 작업의 백그라운드 처리

## 5.21 권한 테스트 명세

역할별 API 통합 테스트를 작성한다.

필수 테스트:

- Guest가 공개 포스트를 읽을 수 있음
- Guest가 비공개 포스트의 존재를 확인할 수 없음
- User가 허용된 카테고리에 포스트를 생성할 수 있음
- User가 `Publish` 없이 초안을 공개할 수 없음
- 포스트 ACL이 카테고리 상속 값을 재정의함
- 특정 사용자 예외가 올바르게 적용됨
- `Deny`가 같은 범위의 `Allow`보다 우선함
- Admin은 잘못된 ACL 상태에서도 복구 가능
- 권한 변경 후 캐시가 무효화됨
- 비공개 전환된 포스트가 다음 정적 릴리스에서 제거됨
- 권한 없는 사용자가 메모·그림 API를 호출할 수 없음
- 마지막 관리자 권한을 제거할 수 없음

UI 테스트에서는 버튼이 숨겨지는지만 확인하지 않고, 직접 API 요청도 서버에서 거부되는지 검증한다.

## 5.22 권한 구현 순서

1. 고정 역할 `SuperAdmin`, `Admin`, `User`, `Guest` 정의
2. 권한 상수와 기본 거부 정책 구현
3. 카테고리 역할별 기본 ACL
4. 포스트의 카테고리 권한 상속
5. ASP.NET Core 공통 `AuthorizationService`
6. 포스트별 역할 예외
7. 권한 관리 UI와 영향 분석
8. 감사 로그
9. 특정 사용자 ACL
10. 개인 주석 레이어 권한
11. 권한별 정적·동적 페이지 분리

# 8. 포스트 관리 기능

## 8.1 관리자 화면

관리자 전용 `/admin` 영역을 만든다.

- 포스트 목록과 검색
- 초안, 공개, 보관 상태 필터
- 새 포스트 작성
- 기존 포스트 수정
- 미리보기
- 공개 및 비공개 전환
- 포스트 삭제와 복구
- Slug 및 카테고리 관리
- 변경 이력 확인

## 8.2 기존 파일 기반 포스트 이전

기존 `posts` 폴더를 즉시 제거하지 않는다.

1. 기존 MDX 파일을 읽는 기능 유지
2. 파일을 DB로 가져오는 일회성 마이그레이션 도구 작성
3. 파일 포스트와 DB 포스트가 동일한 URL 체계를 사용하도록 통합
4. 데이터 검증 후 DB를 기본 원본으로 전환
5. 필요하면 DB 내용을 파일로 내보내는 백업 기능 제공

초기에는 관리자 MDX만 허용한다. DB에 저장한 MDX를 서버에서 컴파일할 때 허용 컴포넌트 목록을 제한한다.

# 9. 슬라이드 저장 전략

## 9.1 저장 단위

포스트 본문, 슬라이드 구성, 메모, 그림을 각각 독립적인 데이터로 저장한다.

포스트 원문을 수정했다고 메모와 그림을 모두 덮어쓰지 않도록 안정적인 슬라이드 키를 유지한다.

## 9.2 자동 저장

편집 UI에는 다음 상태를 표시한다.

```txt
저장되지 않음 -> 저장 중 -> 저장됨
                   |
                   +-> 저장 실패 -> 다시 시도
```

권장 자동 저장 시점은 다음과 같다.

- 텍스트 입력 종료 후 500~1000ms
- 메모 드래그 또는 크기 조절 종료 시
- 그림 획 하나가 끝났을 때
- 슬라이드 이동 직전
- 브라우저 탭을 닫기 전에는 보조적으로 저장 시도

`beforeunload` 요청만 믿으면 안 된다. 평소에 짧은 간격으로 저장하고, 클라이언트 임시 복구본을 `IndexedDB`에 보관하면 네트워크 장애에도 대응할 수 있다.

## 9.3 동시 편집

초기 버전은 실시간 공동 편집을 목표로 하지 않는다.

- 각 데이터에 `Version` 값 사용
- 수정 시 현재 버전 전달
- 서버 버전과 다르면 `409 Conflict` 반환
- 사용자에게 새로고침, 덮어쓰기, 복사 후 병합 선택 제공

## 9.4 주석 데이터의 계층

메모와 그림을 통틀어 **주석(Annotation)** 으로 정의한다.

```txt
Post 또는 PdfDocument
    |
    +-- Slide
          |
          +-- AnnotationLayer
                 |
                 +-- Memo
                 +-- Drawing
                 +-- 이후 확장: 도형, 화살표, 이미지, 레이저 포인터
```

`AnnotationLayer`는 주석의 소유권과 공개 범위를 표현한다.

| 레이어 종류 | 용도 |
|---|---|
| `Document` | 포스트 또는 PDF에 포함되는 공용 주석 |
| `Personal` | 특정 사용자의 개인 필기 |
| `Published` | 정적 사이트에 포함할 확정 주석 스냅샷 |

초기 관리자 전용 버전에서는 `Document` 레이어만 구현할 수 있다. 이후 일반 사용자 기능을 추가할 때 `Personal` 레이어를 같은 데이터 구조로 확장한다.

## 9.5 공통 좌표계

화면 픽셀 좌표를 그대로 저장하면 창 크기, 전체화면, 인쇄, PDF 확대 비율이 달라질 때 위치가 어긋난다. 모든 주석은 슬라이드의 논리 크기를 기준으로 저장한다.

기준 좌표는 두 방식 중 하나를 사용한다.

### 정규화 좌표

```txt
x = 실제 X / 슬라이드 너비
y = 실제 Y / 슬라이드 높이
```

`x`, `y`, `width`, `height`를 `0.0~1.0` 범위로 저장한다.

```json
{
  "x": 0.25,
  "y": 0.18,
  "width": 0.3,
  "height": 0.2
}
```

### 고정 논리 캔버스

슬라이드 기준 크기를 `1920 × 1080`처럼 고정하고 모든 좌표를 이 논리 공간에 저장한다.

```json
{
  "x": 480,
  "y": 194.4,
  "width": 576,
  "height": 216,
  "canvasWidth": 1920,
  "canvasHeight": 1080
}
```

현재 메모 위치가 퍼센트 기반이고 그림 캔버스도 크기 변환이 필요하므로, DB에는 정규화 좌표를 저장하는 방식을 우선 권장한다. 계산 과정에서는 소수점 오차가 누적되지 않도록 충분한 정밀도를 유지한다.

화면에 표시할 때는 다음처럼 변환한다.

```txt
screenX = normalizedX * currentSlideWidth
screenY = normalizedY * currentSlideHeight
```

PDF는 페이지마다 비율이 다르므로 `PdfPages.Width`, `PdfPages.Height`, `Rotation`도 함께 사용한다.

## 9.6 메모 저장 모델

메모 하나를 독립된 행으로 저장한다. 슬라이드 전체 메모를 JSON 배열 하나로 저장하면 메모 하나를 수정할 때 전체 배열을 덮어써야 하고 동시성 충돌 범위도 커진다.

권장 `SlideMemos` 구조:

| 필드 | 형식 | 설명 |
|---|---|---|
| `Id` | UUID | 클라이언트에서도 즉시 생성 가능한 ID |
| `LayerId` | UUID | 소속 주석 레이어 |
| `SlideId` | UUID | 대상 슬라이드 |
| `Text` | TEXT | 메모 본문 |
| `X`, `Y` | REAL | 정규화된 좌상단 위치 |
| `Width`, `Height` | REAL | 정규화된 크기 |
| `IsCollapsed` | INTEGER | 접힘 여부 |
| `ZIndex` | INTEGER | 겹침 순서 |
| `StyleJson` | TEXT | 배경색, 글자색, 글자 크기 등 |
| `Version` | INTEGER | 낙관적 동시성 버전 |
| `CreatedBy` | UUID | 작성자 |
| `CreatedAt`, `UpdatedAt` | TEXT | UTC 시각 |
| `DeletedAt` | TEXT | 소프트 삭제 시각 |

메모 스타일은 초기에 컬럼을 과도하게 늘리지 않고 JSON으로 저장할 수 있다.

```json
{
  "backgroundColor": "#ffffff",
  "textColor": "#111827",
  "fontSize": 20,
  "textAlign": "left"
}
```

자주 검색하거나 권한 판정에 사용하는 값은 JSON에 넣지 않는다. `SlideId`, `LayerId`, `CreatedBy`, `DeletedAt`에는 인덱스를 둔다.

### 접힘 상태

`IsCollapsed`는 편집 UI의 상태다. 다음 정책 중 하나를 선택한다.

- 공용 레이어: 접힘 상태도 모든 사용자에게 동일하게 저장
- 개인 레이어: 사용자별 접힘 상태 저장
- 공개 정적 페이지: 항상 펼친 상태로 출력하고 관리자 UI에서만 접힘 상태 사용

현재 목적에는 관리자 작업 편의를 위해 접힘 상태를 저장하되, PDF 및 정적 HTML 출력에서는 메모 내용을 항상 펼쳐 렌더링하는 방식이 적합하다.

## 9.7 그림 저장 모델

그림은 이미지 한 장이 아니라 **획(Stroke)** 의 목록으로 저장한다.

획 하나의 기본 구조는 다음과 같다.

```json
{
  "id": "0190f0d2-...",
  "tool": "pen",
  "color": "#ef4444",
  "size": 4,
  "opacity": 1,
  "points": [
    { "x": 0.1521, "y": 0.2388, "pressure": 0.51 },
    { "x": 0.1538, "y": 0.2402, "pressure": 0.57 },
    { "x": 0.1559, "y": 0.2427, "pressure": 0.6 }
  ]
}
```

모든 점은 정규화 좌표로 저장한다. 펜 압력을 지원하지 않는 입력 장치는 `pressure`를 생략하거나 기본값을 사용한다.

### 저장 단위 선택

초기 구현에서는 슬라이드별 그림 문서 하나를 두고 압축된 JSON으로 저장한다.

### `SlideDrawingDocuments`

| 필드 | 설명 |
|---|---|
| `Id` | 그림 문서 ID |
| `LayerId` | 주석 레이어 |
| `SlideId` | 대상 슬라이드 |
| `StrokeDataJson` | 획 배열 JSON |
| `StrokeCount` | 획 수 |
| `Version` | 동시성 버전 |
| `UpdatedBy` | 마지막 수정 사용자 |
| `UpdatedAt` | 수정 시각 |

개인 블로그 규모에서는 이 구조가 단순하고 충분하다. 획 수가 매우 많아지거나 여러 사용자가 동시에 그려야 할 때만 획별 행 또는 이벤트 테이블로 분리한다.

그림 JSON은 SQLite의 TEXT로 저장하고, API 응답에는 HTTP gzip 또는 Brotli 압축을 적용한다. PNG 데이터 URL이나 Base64 캔버스 이미지를 DB에 반복 저장하지 않는다.

### 획 데이터 최적화

- 포인터 이동 이벤트를 전부 저장하지 않고 일정 거리 또는 시간 기준으로 샘플링
- 직선에 가까운 중간 점 단순화
- 소수점 자릿수 제한
- 지우개는 배경색 선이 아니라 대상 획 삭제 또는 마스크 데이터로 표현
- 실행 취소는 클라이언트의 획 스택에서 처리
- 일정 획 수를 넘으면 백그라운드에서 미리보기 PNG 생성 가능

원본 JSON은 다시 편집하기 위한 데이터이고, PNG는 목록 미리보기나 PDF 출력 성능을 위한 파생 캐시다. PNG를 원본 데이터로 취급하지 않는다.

## 9.8 작업 데이터와 공개 스냅샷

메모와 그림도 포스트 원문과 동일하게 **작업 중인 상태**와 **현재 공개 중인 상태**를 분리한다.

```txt
Working Annotation Layer
    |
    +-- 관리자 자동 저장
    +-- 메모 이동/크기/본문 수정
    +-- 그림 획 추가/삭제
    |
    +-- 포스트 게시
            |
            v
Published Annotation Snapshot
            |
            v
Next.js 정적 HTML 및 정적 주석 데이터
```

관리자가 메모를 이동할 때마다 공개 사이트를 다시 빌드하지 않는다. 작업 레이어에 자동 저장한 뒤, 포스트를 게시할 때 원문 리비전과 주석 스냅샷을 하나의 릴리스에 묶는다.

### `AnnotationSnapshots`

| 필드 | 설명 |
|---|---|
| `Id` | 스냅샷 ID |
| `LayerId` | 원본 레이어 |
| `ReleaseId` | 공개 릴리스 |
| `SlideId` | 대상 슬라이드 |
| `MemoSnapshotJson` | 확정 메모 목록 |
| `DrawingSnapshotJson` | 확정 그림 데이터 |
| `CreatedAt` | 생성 시각 |

스냅샷은 생성 후 수정하지 않는다. 롤백 시 해당 릴리스의 포스트 원문, 슬라이드, 메모, 그림이 함께 복원된다.

## 9.9 정적 HTML에 주석 반영

공개 메모와 그림의 출력 방식은 데이터 성격에 따라 구분한다.

### 메모

공개 메모는 Next.js 빌드 시 HTML 요소로 생성한다.

- 검색이나 인쇄에서 텍스트 유지
- JavaScript가 없어도 내용 표시
- 정규화 좌표를 CSS 퍼센트로 변환
- 공개 페이지에서는 편집 버튼과 리사이즈 핸들 제거

### 그림

그림은 두 가지 결과물을 생성할 수 있다.

1. 정적 SVG
2. 투명 PNG

획 데이터로 SVG를 생성하면 확대 시 선명하고 파일 크기를 줄일 수 있다. 브러시 표현이나 합성 기능이 복잡하면 PNG를 사용한다.

권장 초기 방식:

- 편집 화면: JSON 획 데이터를 Canvas에 렌더링
- 정적 페이지: 빌드 시 SVG 또는 투명 PNG 생성
- 인쇄: 동일한 정적 결과물을 슬라이드 위에 합성

공개 HTML에 전체 편집용 획 JSON을 넣을 필요가 없으면 렌더링 결과만 포함하여 전송량을 줄인다.

## 9.10 주석 API

### 초기 로딩

```txt
GET /api/slides/{slideId}/annotations?layer=document
```

응답 예시:

```json
{
  "layerId": "0190...",
  "layerVersion": 18,
  "memos": [
    {
      "id": "0191...",
      "text": "핵심 내용",
      "x": 0.25,
      "y": 0.18,
      "width": 0.3,
      "height": 0.2,
      "isCollapsed": false,
      "version": 4
    }
  ],
  "drawing": {
    "version": 7,
    "strokes": []
  }
}
```

### 메모 API

```txt
POST   /api/slides/{slideId}/memos
PATCH  /api/memos/{memoId}
DELETE /api/memos/{memoId}
```

`PATCH`는 변경된 필드만 보낸다.

```json
{
  "version": 4,
  "changes": {
    "x": 0.31,
    "y": 0.22,
    "width": 0.28
  }
}
```

### 그림 API

초기 버전에서는 문서 전체 저장 방식을 사용한다.

```txt
PUT /api/slides/{slideId}/drawing
```

```json
{
  "version": 7,
  "strokes": []
}
```

추후 그림 데이터가 커지면 획 단위 API로 확장할 수 있다.

```txt
POST   /api/drawings/{drawingId}/strokes
DELETE /api/drawings/{drawingId}/strokes/{strokeId}
```

## 9.11 클라이언트 자동 저장 큐

메모 본문 입력과 위치 이동 요청이 서로 덮어쓰지 않도록 브라우저에서 슬라이드별 저장 큐를 사용한다.

```txt
UI 변경
    |
    +-- React 상태 즉시 반영
    +-- IndexedDB 임시 복구본 기록
    +-- 저장 큐에 변경 등록
            |
            +-- 같은 메모의 연속 변경 병합
            +-- debounce
            +-- API 저장
                    |
                    +-- 성공: 서버 Version 갱신
                    +-- 실패: 큐 유지 및 재시도
```

저장 정책:

- 메모 텍스트: 마지막 입력 후 700ms
- 메모 이동·리사이즈: 드래그 중에는 로컬 반영, 포인터를 놓을 때 저장
- 접기·펼치기: 즉시 저장
- 그림: 한 획이 끝나면 큐에 등록, 짧은 시간 동안 여러 획 병합
- 지우기: 확인 후 즉시 저장
- 슬라이드 이동: 현재 큐 전송을 시작하되 UI를 장시간 막지 않음

각 변경에는 클라이언트에서 생성한 `MutationId`를 포함한다. 네트워크 재시도로 같은 요청이 두 번 전달되어도 서버가 중복 적용하지 않도록 한다.

## 9.12 장애 복구

서버 저장 전에 브라우저가 종료될 수 있으므로 작업 중 데이터의 복구 경로를 둔다.

- 슬라이드별 최신 작업을 IndexedDB에 임시 저장
- 서버 저장 성공 시 해당 로컬 복구본 제거 또는 버전 갱신
- 재접속 시 서버 버전과 로컬 버전 비교
- 로컬에 더 새로운 변경이 있으면 복구 여부 안내
- 로그아웃 또는 다른 사용자 로그인 시 개인 복구 데이터 분리

SQLite 저장은 메모 또는 그림 문서 단위의 짧은 트랜잭션으로 처리한다. 포스트 게시 스냅샷을 만들 때는 포스트 리비전, 슬라이드 목록, 메모, 그림의 참조가 모두 확정되도록 하나의 논리적 트랜잭션으로 묶는다.

## 9.13 데이터 크기와 보존

초기 운영 기준 예시는 다음과 같다.

- 메모 본문 최대 길이 제한
- 슬라이드당 메모 개수 제한
- 획당 최대 점 개수 제한
- 슬라이드당 최대 획 수와 JSON 크기 제한
- 소프트 삭제된 메모는 일정 기간 후 정리
- 공개 스냅샷은 유지 중인 릴리스와 함께 보존
- 오래된 자동 저장 임시 데이터는 주기적으로 정리

메모와 그림 데이터가 커져도 포스트 목록 API에는 포함하지 않는다. 현재 슬라이드의 주석만 지연 로딩하고, 다음 슬라이드 한두 장을 미리 불러온다.

## 9.14 구현 순서

1. 현재 메모 모델에 서버 ID, 정규화 좌표, `Version` 추가
2. 슬라이드별 메모 조회·저장 API 구현
3. 메모 자동 저장 상태와 실패 재시도 UI 구현
4. 그림 캔버스 출력을 획 JSON 모델로 변환
5. 그림 문서 조회·저장 API 구현
6. IndexedDB 임시 복구 큐 구현
7. 게시 시 주석 스냅샷 생성
8. Next.js 정적 빌드에 공개 메모와 그림 반영
9. PDF 페이지가 동일한 주석 모델을 사용하도록 연결
10. 일반 사용자용 개인 레이어 확장

# 10. 자유게시판 운영 정책

자유 작성 기능은 자동화된 스팸과 악성 콘텐츠의 대상이 되기 쉽다. 최소한 다음 방어가 필요하다.

- IP 및 브라우저 세션 기준 요청 속도 제한
- 게시글 크기와 링크 개수 제한
- Markdown 렌더링 시 위험한 HTML 제거
- 게스트 글 작성 CAPTCHA 도입 가능성 검토
- 신고 및 관리자 숨김 기능
- 금칙어 또는 반복 도배 탐지
- 서버 로그에 비밀번호와 원문 IP를 남기지 않기
- 이미지 직접 업로드는 첫 버전에서 제외하거나 별도 검증

IP만으로 작성자를 확정하거나 차단하지 않고 여러 신호 중 하나로 사용한다.

# 11. PDF 슬라이드 기능

## 11.1 업로드

- 관리자 또는 허용된 사용자만 업로드
- 확장자뿐 아니라 파일 시그니처 검사
- 최대 파일 크기 제한
- 무작위 내부 파일명 사용
- 웹 실행 경로 밖에 원본 저장
- 페이지 수와 크기 추출
- 암호화 PDF와 손상된 PDF 처리
- 필요 시 악성 파일 검사

SQLite에는 PDF 바이너리를 넣지 않고 파일 경로와 메타데이터만 저장한다. PDF 원본은 EC2의 별도 업로드 디렉터리에 저장한다.

## 11.2 페이지 렌더링

프런트엔드에서는 PDF.js 기반 뷰어를 사용한다.

- 페이지를 한 장의 슬라이드로 취급
- 확대·축소 시 메모와 그림 좌표 동기화
- 페이지 회전 반영
- 현재 페이지별 주석 지연 로딩
- PDF 원본 위에 메모 레이어와 그림 캔버스 배치

메모와 그림 좌표는 페이지 원본 너비와 높이를 기준으로 정규화한다.

## 11.3 내보내기

두 가지 방식을 구분한다.

- **웹 뷰어 인쇄:** 브라우저에서 PDF 페이지와 주석을 함께 인쇄
- **새 PDF 생성:** 서버에서 원본 PDF 위에 메모와 그림을 합성하여 다운로드

새 PDF 생성은 난도가 높으므로 웹 뷰어와 주석 저장을 먼저 구현한 뒤 후속 단계로 진행한다.

# 12. SQLite 운영 방침

SQLite는 단일 EC2 인스턴스에서 시작하는 개인 블로그에 적합하다.

- 설정이 단순함
- 별도 DB 서버 불필요
- 파일 단위 백업 가능
- 읽기 중심 서비스에 충분한 성능

운영 설정은 다음을 권장한다.

- WAL 모드 사용
- Foreign Key 활성화
- 짧은 트랜잭션 유지
- DB 파일을 Git 저장소 밖에 배치
- 애플리케이션 프로세스 하나만 쓰기 담당
- 정기 백업과 복구 테스트
- 배포 전 마이그레이션 수행

SQLite DB 파일을 여러 EC2 인스턴스가 네트워크 파일 시스템으로 동시에 공유하지 않는다. 트래픽 증가, 다중 서버, 빈번한 동시 쓰기가 필요해지면 PostgreSQL로 이전한다.

# 13. EC2 배포 구조

## 13.1 디렉터리 예시

```txt
/srv/blog/
  frontend/        Next.js 배포 파일
  backend/         ASP.NET Core 배포 파일
  data/
    blog.db         SQLite 데이터베이스
  uploads/
    pdf/            PDF 원본
  backups/          암호화 또는 접근 제한된 백업
```

`ec2-user`는 배포 작업을 수행하되, 가능하면 실제 서비스는 권한이 제한된 전용 시스템 사용자로 실행한다.

## 13.2 프로세스 관리

- Next.js는 systemd 또는 검증된 프로세스 관리자로 실행
- ASP.NET Core는 systemd 서비스로 실행
- 두 서비스 모두 외부 포트에 직접 공개하지 않음
- Nginx만 80/443 포트 공개
- 서비스 재시작 정책과 로그 순환 설정
- `/health` API로 상태 확인

## 13.3 Nginx 주요 설정

- Let’s Encrypt HTTPS
- `/api`를 ASP.NET Core로 전달
- 나머지 요청을 Next.js로 전달
- `X-Forwarded-For`, `X-Forwarded-Proto` 설정
- ASP.NET Core에서 신뢰할 프록시 범위 제한
- PDF 업로드 크기에 맞춘 `client_max_body_size`
- 로그인과 게시판 작성 API에 rate limit
- 보안 헤더 적용

# 14. 백업과 복구

백업 대상은 함께 관리해야 한다.

- SQLite DB
- PDF 업로드 파일
- 환경 설정과 배포 버전 정보

권장 정책은 다음과 같다.

- 매일 SQLite 온라인 백업
- 업로드 파일 증분 백업
- S3 등 EC2 외부 위치에 보관
- 최근 일간·주간·월간 백업 유지
- 백업 파일 암호화
- 정기적인 실제 복구 테스트

DB만 복구하고 PDF 파일을 잃거나, PDF만 남고 메타데이터를 잃는 상황이 없도록 동일한 백업 세대로 묶는다.

# 18. 주요 결정 사항

개발을 시작하기 전에 다음 항목을 확정한다.

- ASP.NET Core가 포스트 원문의 유일한 저장소가 될 시점
- 기존 MDX의 임의 React 컴포넌트를 DB 포스트에서도 허용할지 여부
- 일반 사용자 가입을 공개할지 초대제로 운영할지 여부
- 게스트 글의 보존 기간과 IP 정보 보관 정책
- PDF 업로드 허용 역할과 최대 파일 크기
- 메모와 그림을 작성자별 개인 데이터로 볼지 문서의 공용 데이터로 볼지 여부
- 삭제 데이터의 복구 가능 기간
- SQLite에서 PostgreSQL로 이전할 판단 기준

# 19. 최종 방향

개선의 핵심은 현재의 정적 블로그를 한 번에 버리는 것이 아니라 다음 순서로 책임을 분리하는 것이다.

```txt
파일 기반 읽기 전용 블로그
    -> 관리자 인증과 DB 포스트
    -> 슬라이드 변경 내용 영구 저장
    -> 공개 쓰기 가능한 자유게시판
    -> PDF 페이지 기반 슬라이드
    -> 일반 사용자와 세부 권한
```

Next.js는 사용자 경험과 렌더링에 집중하고, ASP.NET Core는 데이터 무결성·인증·권한·파일 처리를 담당한다. SQLite는 단일 EC2에서 시작하기에 적절하지만, DB 파일과 업로드 파일의 백업을 처음부터 운영 설계에 포함한다.

특히 게스트 IP는 인증 수단이 아니라 보조 식별 정보로만 사용하고, 게스트 수정 비밀번호, 입력 정화, 속도 제한을 함께 적용한다. 이 원칙을 지키면 현재 블로그 기능을 유지하면서 관리형 콘텐츠와 사용자 작성 기능을 안전하게 확장할 수 있다.
