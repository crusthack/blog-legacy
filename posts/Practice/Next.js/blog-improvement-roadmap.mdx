# 1. 문서 목적

현재 블로그는 저장소의 MDX 파일을 Next.js가 읽어 정적 페이지로 제공한다. 포스트를 수정하려면 VS Code로 파일을 편집하고 Git 커밋, Push, Pull과 배포를 직접 수행해야 한다.

A 컴퓨터에서 작업하다가 B 컴퓨터로 이동할 때 다음 문제가 발생한다.

- 작업 내용을 커밋하고 원격 저장소에 올려야 함
- 다른 컴퓨터에서 최신 내용을 다시 내려받아야 함
- 커밋 누락과 충돌을 직접 처리해야 함
- 어떤 파일이 최신 버전인지 확인해야 함
- 슬라이드 메모와 그림은 브라우저 메모리에만 있어 다른 기기에서 이어서 작업할 수 없음

개선의 핵심 목적은 **포스트 관리를 VS Code와 특정 개발 컴퓨터로부터 분리하는 것**이다.

```txt
현재
로컬 파일 수정
  -> Git commit/push
  -> 다른 컴퓨터에서 pull
  -> 충돌 확인
  -> 애플리케이션 재배포

개선 후
브라우저에서 관리자 로그인
  -> 서버의 최신 포스트 편집
  -> 자동 저장
  -> 미리보기
  -> 정적 사이트 게시
```

Git은 애플리케이션 코드와 DB 마이그레이션을 관리한다. 포스트 원문과 수정 이력은 ASP.NET Core와 SQLite가 관리한다.

# 2. 확정된 요구사항

## 2.1 기술 구성

| 영역 | 기술 |
|---|---|
| 프런트엔드 | Next.js App Router |
| 백엔드 | ASP.NET Core |
| 데이터베이스 | SQLite |
| 리버스 프록시 | Nginx |
| 서버 | AWS EC2 |
| 콘텐츠 문법 | Markdown |

## 2.2 역할

화면에는 세 등급을 표시하지만 서버 내부 역할은 네 개로 구분한다.

| 표시 등급 | 내부 역할 | 설명 |
|---|---|---|
| 초염몽 | `SuperAdmin` | 시스템 전체를 관리하는 최고 관리자 |
| 파이숭이 | `Admin` | 일반 포스트와 위임받은 콘텐츠를 관리하는 관리자 |
| 불꽃숭이 | `User` | 로그인한 일반 사용자 |
| 불꽃숭이 | `Guest` | 로그인하지 않은 사용자 |

`User`와 `Guest`는 같은 불꽃숭이 등급이지만 로그인 여부와 소유권 판정 방식이 다르므로 서버에서는 구분한다.

## 2.3 포스트 종류

| 종류 | 내부 값 | 작성자 | 저장 내용 |
|---|---|---|---|
| 시스템 포스트 | `SystemPost` | 초염몽 | Markdown, 슬라이드, 메모, 그림 |
| 일반 포스트 | `CommunityPost` | 불꽃숭이 | Markdown과 최소 메타데이터 |

일반 포스트는 별도 자유게시판 테이블을 사용하지 않는다. `Posts.PostType = CommunityPost`인 포스트를 자유게시판 목록에 표시한다.

## 2.4 콘텐츠 문법

신규 DB 포스트는 작성자 역할과 관계없이 Markdown만 지원한다.

허용:

- 제목과 문단
- 굵게, 기울임, 취소선
- 순서 및 비순서 목록
- 인용문
- 링크
- 인라인 코드와 코드 블록
- 표
- 수평선
- 체크박스

금지:

- MDX
- JSX
- import/export
- 임의 React 컴포넌트
- script, iframe, style
- 이벤트 핸들러
- `javascript:` URL
- 실행 가능한 Raw HTML

기존 저장소의 MDX 포스트는 마이그레이션 기간에 읽기 전용으로 유지한다. 웹에서 수정하려면 안전한 Markdown으로 변환해야 한다.

## 2.5 메모와 그림

메모와 그림은 초염몽이 소유한 `SystemPost`에서만 저장한다.

| 대상 | Markdown | 메모·그림 |
|---|---:|---:|
| 초염몽 시스템 포스트 | 허용 | 허용 |
| 파이숭이 관리 포스트 | 허용 | 수정 불가 |
| 불꽃숭이 일반 포스트 | 허용 | 지원하지 않음 |

일반 포스트에는 슬라이드, 메모, 그림 레코드를 만들지 않는다.

## 2.6 공개 범위

| 공개 범위 | 내부 값 | 읽기 조건 |
|---|---|---|
| 공개 | `Public` | 누구나 |
| 코드 보호 | `PasswordProtected` | 열람 코드 또는 초염몽 |
| 개인 | `OwnerOnly` | 초염몽만 |

# 3. 전체 아키텍처

```txt
사용자 브라우저
    |
    v
Nginx :80 / :443
    |
    +-- 공개 및 관리자 UI -> Next.js :3000
    |
    +-- /api/* -> ASP.NET Core :5000
    |
    +-- 허용된 정적 리소스

ASP.NET Core
    |
    +-- 인증 및 권한
    +-- 포스트와 카테고리 CRUD
    +-- 주석과 PDF 관리
    +-- 정적 빌드 작업 관리
    |
    v
SQLite + 업로드 파일 저장소
```

## 3.1 Next.js 책임

- 공개 블로그 렌더링
- 관리자 로그인과 편집 UI
- Markdown 편집기와 미리보기
- 슬라이드, 메모와 그림 UI
- PDF 페이지 뷰어
- 정적 포스트 생성
- 권한에 따른 UI 노출
- ASP.NET Core API 호출

## 3.2 ASP.NET Core 책임

- 로그인과 세션 관리
- 역할 및 리소스 권한 검사
- 포스트, 카테고리와 리비전 관리
- 일반 포스트 소유권 비밀번호 검증
- 비공개 포스트 열람 코드 검증
- 메모와 그림 영구 저장
- PDF 업로드와 검증
- Markdown 입력 검증
- 게시 스냅샷과 빌드 작업 관리
- 감사 로그
- SQLite 트랜잭션

## 3.3 Nginx 책임

- HTTPS 종료
- Next.js와 ASP.NET Core 리버스 프록시
- 실제 클라이언트 IP 전달
- 업로드 크기 제한
- 요청 속도 제한
- 보안 헤더
- 정적 리소스 제공

## 3.4 배포 구조 선택

첫 버전은 하나의 Next.js 애플리케이션으로 시작한다.

- 공개 포스트는 빌드 시 prerender
- 관리자와 보호 포스트는 런타임 렌더링
- 공개 페이지 요청마다 SQLite를 조회하지 않음

콘텐츠 게시와 코드 배포를 완전히 분리할 필요가 생기면 공개 정적 사이트와 관리자 UI를 별도 애플리케이션으로 분리한다.

# 4. 포스트 생명주기

## 4.1 편집 상태

| 상태 | 설명 |
|---|---|
| `Draft` | 작성 중 |
| `Review` | 검토 중 |
| `Published` | 공개 버전 존재 |
| `Archived` | 목록에서 숨긴 보관 상태 |
| `Deleted` | 소프트 삭제 |

## 4.2 일반 포스트 운영 상태

| 상태 | 설명 |
|---|---|
| `Published` | 작성 완료 후 기본 공개 |
| `Pending` | 스팸 의심, 정책 검사 또는 수동 검토가 필요한 예외 상태 |
| `Hidden` | 운영 정책으로 숨김 |
| `Rejected` | 게시 거부 |
| `Deleted` | 소프트 삭제 |

일반 포스트의 기본 운영 상태는 `Published`, 기본 공개 범위는 `Public`이다. 작성 요청의 Markdown 검증과 속도 제한을 통과하면 자동으로 공개 빌드 작업을 등록한다.

스팸 탐지, 금칙어, 과도한 링크 또는 요청 속도 제한에 걸린 포스트만 `Pending`으로 전환할 수 있다. 파이숭이와 초염몽은 공개된 일반 포스트를 사후에 `Hidden`, `Rejected`, `Deleted`로 변경할 수 있다.

게스트 요청 하나마다 전체 정적 빌드를 즉시 실행하면 빌드 자원 고갈 공격에 악용될 수 있다. 일반 포스트 공개 작업은 짧은 집계 구간으로 묶고, 같은 시간에 작성된 여러 포스트를 릴리스 하나로 생성한다.

- 작성 요청에는 IP 및 세션별 속도 제한 적용
- 공개 빌드 요청은 30~60초 동안 집계
- 이미 대기 중인 일반 포스트 변경은 최신 대기 릴리스에 병합
- 동시에 실행하는 정적 빌드는 하나로 제한
- 빌드에 실패하면 포스트는 DB에 유지하고 재시도 상태 표시

## 4.3 자동 저장과 게시 분리

자동 저장 성공은 공개 완료를 의미하지 않는다.

```txt
초안 저장됨
  -> 공개 버전과 변경 사항 있음
  -> 게시 대기
  -> 정적 빌드 중
  -> 게시 완료

빌드 실패
  -> 기존 공개 버전 유지
```

## 4.4 수정 이력

`Posts`는 현재 상태와 식별 정보를 저장한다. 실제 원문 버전은 `PostRevisions`에 저장한다.

자동 저장마다 영구 리비전을 만들지 않는다.

- 작업 초안: 현재 편집 내용을 계속 갱신
- 리비전: 수동 저장, 게시 또는 의미 있는 시점에 생성
- 게시 버전: 공개 릴리스에 연결된 불변 리비전

# 5. 읽기·수정·삭제 시나리오

## 5.1 읽기

### 개인 포스트

`todo` 같은 개인 포스트는 `OwnerOnly`로 설정한다.

```txt
개인 포스트 진입
  -> 초염몽 로그인 확인
  -> 초염몽이면 허용
  -> 그 외에는 404 또는 거부
```

개인 포스트는 검색, RSS, 사이트맵과 카테고리 개수에도 노출하지 않는다.

### 비공개 포스트

```txt
비공개 포스트 진입
  -> 초염몽이면 즉시 허용
  -> 유효한 열람 세션이 있으면 허용
  -> 열람 코드 입력
      -> 일치하면 포스트 한정 열람 세션 발급
      -> 불일치하면 거부
```

파이숭이는 관리 역할만으로 비공개 본문을 열람할 수 없다.

### 공개 포스트

`Public` 포스트는 로그인 여부와 관계없이 누구나 읽을 수 있다.

| 공개 범위 | 초염몽 | 파이숭이 | 불꽃숭이 User | 불꽃숭이 Guest |
|---|---:|---:|---:|---:|
| `OwnerOnly` | 허용 | 거부 | 거부 | 거부 |
| `PasswordProtected` | 허용 | 코드 필요 | 코드 필요 | 코드 필요 |
| `Public` | 허용 | 허용 | 허용 | 허용 |

## 5.2 수정

### 초염몽

초염몽은 모든 시스템 포스트와 일반 포스트를 수정할 수 있다.

- Markdown 원문
- 제목과 메타데이터
- 카테고리와 공개 범위
- 시스템 포스트의 메모와 그림

### 파이숭이

파이숭이는 다음 운영 작업을 수행한다.

- 일반 포스트 모니터링과 필요 시 공개 복구
- 일반 포스트 숨김과 삭제
- 위임받은 시스템 공개 포스트의 Markdown 관리

파이숭이는 다음 작업을 할 수 없다.

- 초염몽 개인 포스트 수정
- 별도 권한 없는 비공개 포스트 수정
- 시스템 포스트 메모와 그림 수정
- 최고 관리자 역할 및 권한 변경

### 불꽃숭이

불꽃숭이는 자신이 작성한 `CommunityPost`만 수정할 수 있다.

```txt
수정 요청
  -> 로그인 OwnerId가 일치하거나
  -> 포스트 소유권 비밀번호 검증
  -> 포스트 한정 소유권 세션 발급
  -> Markdown 수정 허용
```

열람 코드만으로는 포스트를 수정할 수 없다.

## 5.3 삭제

| 대상 | 초염몽 | 파이숭이 | 작성자 불꽃숭이 | 다른 불꽃숭이 |
|---|---:|---:|---:|---:|
| 시스템 개인 포스트 | 허용 | 거부 | 거부 | 거부 |
| 시스템 비공개 포스트 | 허용 | 거부 | 거부 | 거부 |
| 시스템 공개 포스트 | 허용 | 위임 범위에서 허용 | 거부 | 거부 |
| 일반 포스트 | 허용 | 허용 | 비밀번호 확인 후 허용 | 거부 |

모든 삭제는 먼저 소프트 삭제한다.

- 목록과 검색에서 제거
- 다음 정적 릴리스에서 HTML 제거
- RSS와 사이트맵에서 제거
- 연결된 공개 주석 비활성화
- 30일 동안 초염몽이 복구 가능
- 영구 삭제는 별도 확인 필요

# 6. 인증과 소유권

## 6.1 초염몽과 파이숭이 로그인

- 비밀번호 평문 저장 금지
- 검증된 적응형 비밀번호 해시
- 로그인 유지용 Refresh Token 유효기간 30일
- API 호출용 Access Token 유효기간 30분
- Access Token 만료 전 또는 `401` 응답 시 자동 갱신
- Refresh Token은 `HttpOnly`, `Secure`, 적절한 `SameSite` 쿠키에 저장
- Access Token은 브라우저 메모리에만 저장하고 `localStorage`에 저장하지 않음
- 상태 변경 요청의 CSRF 검증
- 로그인 실패 횟수 제한
- 관리자 권한은 서버에서 최종 검사

초기에는 초염몽 계정과 필요한 파이숭이 계정만 만든다.

### 토큰 수명

| 토큰 | 유효기간 | 용도 | 저장 위치 |
|---|---:|---|---|
| Refresh Token | 30일 | 로그인 유지와 Access Token 재발급 | `HttpOnly` 보안 쿠키 |
| Access Token | 30분 | ASP.NET Core API 인증 | 브라우저 메모리 |

로그인 성공 시 서버는 두 토큰을 발급한다.

```txt
로그인
  -> Access Token 발급: 30분
  -> Refresh Token 발급: 30일
  -> API 호출
      -> Access Token 만료 임박
      -> Refresh API 호출
      -> 새 Access Token과 Refresh Token 발급
```

### 자동 갱신

Next.js API 클라이언트는 다음 규칙으로 토큰을 갱신한다.

- Access Token 만료 1~2분 전에 백그라운드 갱신
- 만료를 미리 감지하지 못하면 API의 `401` 응답 후 한 번 갱신
- 같은 시점에 여러 API가 실패해도 Refresh 요청은 하나만 실행
- 갱신 성공 후 실패했던 API 요청을 한 번만 재시도
- Refresh Token도 만료되었거나 폐기되었으면 로그인 화면으로 이동
- 무한 Refresh 또는 무한 API 재시도 금지

### Refresh Token 회전

Refresh Token을 사용할 때마다 새 토큰으로 교체한다.

- DB에는 Refresh Token 원문 대신 해시 저장
- 이전 Refresh Token은 즉시 폐기
- 이미 사용한 Refresh Token이 재사용되면 해당 토큰 계열 전체 폐기
- 로그아웃 시 현재 토큰 계열 폐기
- 비밀번호 변경, 계정 비활성화와 역할 강등 시 모든 로그인 토큰 폐기
- 사용자별 활성 세션 목록과 전체 로그아웃 기능 제공 가능

30일은 Refresh Token의 절대 만료기간으로 사용한다. 자동 갱신이 반복되더라도 최초 로그인으로부터 30일이 지나면 다시 로그인하게 하는 정책을 우선 적용한다.

## 6.2 일반 포스트 소유권

일반 사용자는 포스트 작성 시 소유권 비밀번호를 입력한다.

서버에는 `OwnerPasswordHash`만 저장한다.

- 포스트마다 독립적인 Salt
- HTTPS에서만 전송
- URL이나 로그에 비밀번호 기록 금지
- 포스트와 IP 기준 검증 속도 제한
- 성공하면 해당 포스트에만 유효한 소유권 세션 발급

소유권 세션으로 가능한 작업:

- 해당 포스트 수정
- 해당 포스트 소프트 삭제

불가능한 작업:

- 다른 포스트 수정
- 역할과 ACL 변경
- 카테고리 관리
- 메모와 그림 생성

## 6.3 열람 코드와 소유권 비밀번호

두 비밀번호를 분리한다.

| 자격정보 | 목적 |
|---|---|
| `AccessCode` | 비공개 포스트 읽기 |
| `OwnerPassword` | 일반 포스트 수정·삭제 |

열람 코드는 여러 독자에게 공유될 수 있으므로 소유권 비밀번호와 같게 사용하지 않는다.

## 6.4 비밀번호 분실

계정이 없는 일반 사용자의 소유권 비밀번호는 직접 복구할 수 없다.

- 작성 화면에서 복구 불가능 정책 안내
- 초염몽은 운영 판단으로 포스트 삭제 또는 소유권 초기화 가능
- 초기화 작업은 감사 로그에 기록
- 파이숭이는 비밀번호 원문 확인과 강제 변경 불가

## 6.5 IP 식별

IP는 인증 수단이 아니다.

- 공유 네트워크에서 여러 사용자가 같은 IP 사용 가능
- 모바일 IP는 변경 가능
- VPN과 프록시로 우회 가능

IP는 스팸 방지와 운영 참고용으로만 사용한다. 원문 저장 대신 HMAC 기반 `IpHash` 사용을 권장한다.

# 7. 권한 모델

## 7.1 권한 종류

| 권한 | 설명 |
|---|---|
| `List` | 제목과 목록 노출 |
| `Read` | 본문 조회 |
| `CreatePost` | 카테고리 아래 포스트 작성 |
| `Edit` | Markdown과 메타데이터 수정 |
| `EditAnnotations` | 시스템 포스트 메모와 그림 수정 |
| `Publish` | 공개 릴리스에 포함 |
| `Move` | 다른 카테고리로 이동 |
| `Delete` | 소프트 삭제 |
| `ManageCategory` | 카테고리 구조 변경 |
| `ManagePermissions` | ACL 변경 |

## 7.2 권한 효과

각 권한은 다음 세 상태를 가진다.

- `Inherit`: 상위 카테고리 또는 역할 기본값 사용
- `Allow`: 명시적 허용
- `Deny`: 명시적 거부

기본값은 거부다.

## 7.3 판정 우선순위

1. 비활성 또는 차단 사용자면 거부
2. `SuperAdmin`이면 허용
3. 포스트의 특정 사용자 규칙
4. 포스트의 역할 규칙
5. 가까운 카테고리부터 상위 ACL
6. 포스트 소유자 기본 권한
7. 시스템 역할 기본값
8. 일치하는 규칙이 없으면 거부

파이숭이는 위임받은 범위만 관리하며 전역 권한 우회 기능을 갖지 않는다.

## 7.4 주석 권한

메모 또는 그림 저장 시 다음 조건을 모두 만족해야 한다.

```txt
PostType == SystemPost
Post.OwnerRole == SuperAdmin
CurrentUser.Role == SuperAdmin
```

권한 검사는 UI뿐 아니라 ASP.NET Core 주석 서비스에서 수행한다.

## 7.5 정적 페이지와 권한

정적 HTML 파일은 URL을 아는 누구나 읽을 수 있으므로 `Public` 포스트만 정적으로 생성한다.

- `Public`: 정적 HTML
- `PasswordProtected`: 런타임 인증 후 렌더링
- `OwnerOnly`: 관리자 런타임 경로

비공개 포스트를 정적 생성한 뒤 JavaScript로 가리는 방식은 사용하지 않는다.

# 8. 카테고리

## 8.1 구조

카테고리는 독립된 계층형 데이터다.

```txt
Practice
├─ Next.js
└─ ASP.NET Core

Theory
├─ Network
└─ ComputerScience
```

원칙:

- `ParentId`로 부모 카테고리 지정
- 포스트는 하나의 대표 `CategoryId` 사용
- 여러 주제 연결은 태그 사용
- 이름과 URL Slug 분리
- 최대 깊이 5
- 같은 부모 아래 Slug 중복 금지
- 시스템 예약 경로 금지

## 8.2 URL

시스템 포스트는 기존 카테고리 경로를 유지한다.

```txt
/{categoryPath}/{postSlug}
```

일반 포스트는 시스템 경로 선점을 막기 위해 별도 경로를 사용한다.

```txt
/community/{postId}/{slug}
```

카테고리 이동이나 Slug 변경 시 기존 경로를 301 리다이렉트로 보존한다.

## 8.3 추가와 수정

추가 시 검증:

- 부모 존재 여부
- 최대 깊이
- 같은 부모 아래 Slug 중복
- 예약 Slug
- 이름과 설명 길이

수정 유형:

- 이름만 변경: URL 유지
- Slug 변경: 하위 경로 영향 분석 및 리다이렉트 생성
- 부모 변경: 하위 카테고리와 포스트 경로 갱신
- 순서 변경: 정적 메뉴 재생성

## 8.4 이동

금지되는 이동:

- 자기 자신 아래로 이동
- 자신의 하위 카테고리 아래로 이동
- 삭제된 카테고리 아래로 이동
- 최대 깊이 초과
- 대상 부모 아래 Slug 충돌

카테고리 이동 시 포스트 `CategoryId`는 유지하고 계산 경로만 갱신한다.

## 8.5 삭제

카테고리는 소프트 삭제한다.

비어 있지 않은 카테고리는 다음 처리 중 하나를 선택해야 한다.

- 포스트를 다른 카테고리로 이동
- 포스트를 `Uncategorized`로 이동
- 하위 카테고리를 부모로 한 단계 올림
- 전체 하위 트리를 보관
- 삭제 취소

DB 외래 키는 `RESTRICT`를 기본으로 사용한다. 실수로 전체 포스트가 연쇄 삭제되는 `CASCADE DELETE`는 사용하지 않는다.

## 8.6 미분류

시스템 카테고리 `Uncategorized`를 둔다.

- 삭제 불가
- 부모 변경 불가
- 기존 파일 마이그레이션의 임시 위치
- 카테고리 삭제 시 포스트 이동 대상

## 9.10 전체 관계도

```txt
Users
├─ RefreshTokens
├─ Posts.OwnerId
├─ AuditLogs.ActorUserId
└─ AccessControlEntries.SubjectId

Categories
├─ Categories.ParentId
├─ Posts.CategoryId
└─ AccessControlEntries

Posts
├─ PostRevisions
├─ Slides
├─ AccessControlEntries
└─ ReleasePosts

PdfDocuments
└─ PdfPages
   └─ Slides

Slides
├─ SlideMemos
├─ SlideDrawingDocuments
└─ AnnotationSnapshots

Releases
├─ ReleasePosts
├─ AnnotationSnapshots
└─ BuildJobs
```

핵심 관계:

- 카테고리는 자기 참조 구조로 계층을 만든다.
- 시스템 포스트와 일반 포스트는 같은 `Posts` 테이블을 사용한다.
- `CommunityPost`에는 `Slides`를 만들지 않는다.
- 포스트 리비전은 수정 이력을 저장하고 공개 릴리스는 특정 리비전을 참조한다.
- 시스템 포스트의 메모와 그림만 주석 스냅샷에 포함한다.
- PDF 파일은 DB 밖에 두고 페이지와 주석 메타데이터만 DB에 저장한다.
- 삭제는 기본적으로 소프트 삭제하고 외래 키는 우발적인 연쇄 삭제를 막는다.

## 9.11 SQLite 공통 규칙

```sql
PRAGMA foreign_keys = ON;
PRAGMA journal_mode = WAL;
PRAGMA busy_timeout = 5000;
```

규칙:

- 기본 키는 애플리케이션에서 생성한 UUID 문자열
- 시각은 UTC ISO 8601 문자열
- Boolean은 `INTEGER`의 `0`, `1`
- Enum은 `TEXT`와 `CHECK` 제약
- JSON은 `TEXT`에 저장하고 ASP.NET Core에서 스키마 검증
- 비밀번호와 토큰 원문 저장 금지
- 금액이나 고정 소수점 값은 없으므로 좌표에 `REAL` 사용
- 모든 쓰기는 짧은 트랜잭션으로 수행
- 물리 삭제는 보존 기간 종료 후 별도 정리 작업에서 수행

## 9.12 사용자와 로그인 토큰 DDL

```sql
CREATE TABLE users (
    id                  TEXT PRIMARY KEY,
    username            TEXT NOT NULL COLLATE NOCASE,
    password_hash       TEXT NOT NULL,
    display_name        TEXT NOT NULL,
    role                TEXT NOT NULL
                        CHECK (role IN ('SuperAdmin', 'Admin', 'User')),
    is_active           INTEGER NOT NULL DEFAULT 1
                        CHECK (is_active IN (0, 1)),
    credential_version  INTEGER NOT NULL DEFAULT 1,
    created_at          TEXT NOT NULL,
    updated_at          TEXT NOT NULL,
    deleted_at          TEXT,
    UNIQUE (username)
);

CREATE TABLE refresh_tokens (
    id                  TEXT PRIMARY KEY,
    user_id             TEXT NOT NULL,
    family_id           TEXT NOT NULL,
    token_hash          TEXT NOT NULL,
    expires_at          TEXT NOT NULL,
    replaced_by_id      TEXT,
    revoked_at          TEXT,
    revoke_reason       TEXT,
```

## 9.21 스키마 삭제 정책

| 데이터 | 삭제 방식 | 물리 삭제 시점 |
|---|---|---|
| 사용자 | 비활성화 후 소프트 삭제 | 운영 정책에 따라 |
| 포스트 | 소프트 삭제 | 기본 30일 이후 |
| 카테고리 | 하위 이동 후 소프트 삭제 | 참조가 없을 때 |
| 메모 | 소프트 삭제 | 포스트 정리 시 |
| 그림 | 포스트와 함께 정리 | 보존 기간 이후 |
| PDF | 소프트 삭제 및 파일 격리 | 보존 기간 이후 |
| 리비전 | 유지 | 포스트 영구 삭제 시 검토 |
| 릴리스 | 최근 성공본 유지 | 릴리스 보존 정책 |
| 감사 로그 | 불변 | 보안 로그 보존 기간 이후 |
| Refresh Token | 폐기 표시 | 만료 후 정리 |

SQLite 외래 키는 기본적으로 `RESTRICT`를 사용한다. 애플리케이션 서비스가 참조 데이터를 명시적으로 정리한 뒤 물리 삭제한다.

## 9.23 정기 무결성 검사

SQLite 제약만으로 표현하기 어려운 규칙을 백그라운드 검사 작업에서 확인한다.

- `current_revision_id`가 같은 포스트의 리비전인지
- `published_revision_id`가 같은 포스트의 리비전인지
- `CommunityPost`에 슬라이드가 연결되지 않았는지
- 주석의 최종 소유자가 초염몽인지
- 공개 릴리스에 `Public + Published` 포스트만 포함됐는지
- 리다이렉트 순환이 없는지
- 카테고리 순환이 없는지
- 파일 시스템의 PDF와 DB 메타데이터가 일치하는지
- 만료된 토큰과 Idempotency 레코드가 정리됐는지
- 배포된 릴리스의 Artifact 경로가 실제로 존재하는지

문제가 발견되면 자동으로 파괴적인 수정부터 하지 않고 감사 로그와 운영 경고를 생성한다.

# 10. 메모와 그림 저장

## 10.1 좌표

창 크기와 PDF 확대 비율이 달라져도 위치가 유지되도록 `0.0~1.0` 정규화 좌표를 저장한다.

```txt
x = 실제 X / 슬라이드 너비
y = 실제 Y / 슬라이드 높이

screenX = x * 현재 슬라이드 너비
screenY = y * 현재 슬라이드 높이
```

## 10.2 그림 획

```json
{
  "id": "0190f0d2-...",
  "tool": "pen",
  "color": "#ef4444",
  "size": 4,
  "opacity": 1,
  "points": [
    { "x": 0.15, "y": 0.24, "pressure": 0.51 },
    { "x": 0.16, "y": 0.25, "pressure": 0.57 }
  ]
}
```

- 좌표 정규화
- 포인터 점 샘플링
- 직선 중간 점 단순화
- 소수점 자릿수 제한
- 실행 취소는 획 단위

## 10.3 자동 저장

```txt
UI 변경
  -> React 상태 즉시 반영
  -> IndexedDB 복구본
  -> 슬라이드별 저장 큐
  -> API 저장
      -> 성공: Version 갱신
      -> 실패: 큐 유지 및 재시도
```

저장 시점:

- 메모 텍스트: 마지막 입력 후 약 700ms
- 메모 이동과 크기 조절: 포인터를 놓을 때
- 접기와 펼치기: 즉시
- 그림: 획이 끝난 뒤
- 슬라이드 이동: 현재 큐 전송 시작

## 10.4 동시성

- 각 메모와 그림 문서에 `Version`
- 클라이언트가 읽은 버전을 수정 요청에 포함
- 서버 버전과 다르면 `409 Conflict`
- 요청마다 `MutationId`를 포함하여 중복 저장 방지

## 10.5 작업 데이터와 공개 스냅샷

작업 중 주석과 공개 주석을 분리한다.

```txt
Working
  -> 초염몽 자동 저장
  -> 포스트 게시
  -> 불변 AnnotationSnapshot
  -> Next.js 정적 결과
```

공개 메모는 HTML로, 그림은 SVG 또는 투명 PNG로 생성한다.

# 11. 정적 게시

## 11.1 게시 스냅샷

빌드 중 데이터가 바뀌지 않도록 게시할 포스트 리비전, 카테고리와 시스템 주석을 `ReleaseId`로 고정한다.

```txt
게시 클릭
  -> 리비전 확정
  -> Release 생성
  -> 정적 빌드 큐 등록
  -> Next.js가 ReleaseId로 데이터 조회
  -> 결과 검증
  -> 성공한 결과만 배포
```

## 11.2 빌드 작업

API 요청 안에서 `next build` 완료를 기다리지 않는다.

| 상태 | 설명 |
|---|---|
| `Queued` | 대기 |
| `Running` | 빌드 중 |
| `Succeeded` | 성공 |
| `Failed` | 실패 |

한 환경에서 빌드 하나만 실행한다. 대기 중인 변경은 최신 릴리스 하나로 병합한다.

일반 포스트 작성은 기본 공개 정책을 사용하지만 게스트가 직접 빌드 프로세스를 실행하지는 않는다. ASP.NET Core가 검증을 마친 포스트만 내부 빌드 큐에 등록하고 여러 요청을 하나의 릴리스로 합친다.

## 11.3 정적 생성 대상

- 공개 포스트
- 포스트 목록
- 카테고리와 태그 목록
- 페이지네이션
- 검색 인덱스
- 사이트맵
- RSS
- Open Graph 메타데이터
- 공개 메모와 그림
- 리다이렉트

보호 또는 개인 포스트는 정적 생성하지 않는다.

## 11.4 배포와 롤백

새 빌드는 기존 공개 결과물을 덮어쓰지 않고 별도 릴리스로 만든다.

```txt
/srv/blog/releases/
  release-100/
  release-101/

/srv/blog/current -> release-101
```

검증 후 `current`를 원자적으로 교체한다. 실패하면 기존 릴리스를 유지한다.

# 12. API 초안

## 12.1 인증

```txt
POST /api/auth/login
POST /api/auth/refresh
POST /api/auth/logout
POST /api/auth/logout-all
GET  /api/auth/me
```

- `/login`: 30분 Access Token과 30일 Refresh Token 발급
- `/refresh`: Refresh Token 회전 후 새 토큰 쌍 발급
- `/logout`: 현재 토큰 계열 폐기
- `/logout-all`: 사용자의 모든 Refresh Token 폐기

## 12.2 포스트

```txt
GET    /api/posts
GET    /api/posts/{id}
POST   /api/posts
PATCH  /api/posts/{id}
DELETE /api/posts/{id}
POST   /api/posts/{id}/publish
POST   /api/posts/{id}/restore
```

## 12.3 일반 포스트 소유권

```txt
POST /api/posts/{id}/claim
POST /api/posts/{id}/unlock
```

- `claim`: 소유권 비밀번호 검증
- `unlock`: 비공개 열람 코드 검증

## 12.4 카테고리

```txt
GET    /api/categories/tree
POST   /api/categories
PATCH  /api/categories/{id}
POST   /api/categories/{id}/move
POST   /api/categories/reorder
DELETE /api/categories/{id}
POST   /api/categories/{id}/restore
GET    /api/categories/{id}/delete-impact
```

## 12.5 주석

모든 변경 API는 `SuperAdmin + SystemPost` 정책을 요구한다.

```txt
GET    /api/slides/{slideId}/annotations
POST   /api/slides/{slideId}/memos
PATCH  /api/memos/{memoId}
DELETE /api/memos/{memoId}
PUT    /api/slides/{slideId}/drawing
```

## 12.6 PDF

```txt
GET    /api/pdfs
POST   /api/pdfs
GET    /api/pdfs/{id}

DELETE /api/pdfs/{id}
GET    /api/pdfs/{id}/pages/{page}/annotations
```

PDF 변경 API는 초염몽만 호출할 수 있다.

## 12.7 오류 형식

RFC 9457 Problem Details 계열의 공통 형식을 사용한다.

```json
{
  "title": "포스트 버전 충돌",
  "status": 409,
  "code": "POST_VERSION_CONFLICT",
  "traceId": "..."
}
```

필수 오류 코드:

- `AUTH_REQUIRED`
- `PERMISSION_DENIED`
- `POST_NOT_FOUND`
- `OWNER_PASSWORD_INVALID`
- `ACCESS_CODE_INVALID`
- `POST_VERSION_CONFLICT`
- `CATEGORY_SLUG_CONFLICT`
- `MARKDOWN_POLICY_VIOLATION`
- `BUILD_FAILED`

# 17. 보안과 운영

## 17.1 비밀정보

Git에 저장하지 않는다.

- 관리자 초기 비밀번호
- 쿠키 암호화 키
- CSRF와 토큰 서명 키
- IP HMAC 키
- 빌드 API 토큰
- 백업 암호화 키

## 17.2 CSRF와 CORS

- Next.js와 API를 동일 Origin으로 제공
- 프로덕션 CORS는 동일 Origin만 허용
- 상태 변경 요청에 CSRF 검증
- 쿠키에 `HttpOnly`, `Secure`, `SameSite`
- 소유권 쿠키는 포스트 ID와 자격정보 버전에 제한

## 17.3 감사 로그

기록 대상:

- 로그인 성공과 실패
- 소유권 비밀번호와 열람 코드 실패
- 포스트 생성, 수정, 삭제와 복구
- 일반 포스트 승인과 숨김
- 카테고리 이동과 삭제
- 권한 변경
- 게시와 빌드 실패
- PDF 업로드와 삭제

비밀번호, 쿠키와 민감한 본문은 로그에 기록하지 않는다.

## 17.4 입력 제한

초기 예시:

| 항목 | 제한 |
|---|---|
| 제목 | 1~150자 |
| 설명 | 최대 500자 |
| 일반 Markdown | 최대 200KB |
| 시스템 Markdown | 최대 1MB |
| Slug | 최대 100자 |
| 카테고리 깊이 | 최대 5 |
| 포스트별 메모 | 최대 100개 |
| 그림 JSON | 슬라이드별 제한 |
| PDF | 파일 크기와 페이지 수 제한 |

정확한 값은 실제 사용량을 측정해 조정한다.

- Raw HTML과 위험 URL 실행 차단

- 롤백으로 이전 릴리스 복원 가능

## 20.4 운영

- 카테고리 이동 후 이전 URL 리다이렉트
- DB와 PDF 백업 복원 성공
- 비밀번호와 쿠키가 로그에 남지 않음
- 속도 제한이 반복 공격을 차단

# 22. 최종 원칙

```txt
SystemPost
├─ Markdown
├─ Slide
├─ Memo
└─ Drawing

CommunityPost
├─ Markdown
├─ OwnerPasswordHash
└─ 운영 상태
```

구현 전체에서 다음 원칙을 유지한다.

1. DB 포스트는 Markdown만 저장한다.
2. 메모와 그림은 초염몽 시스템 포스트에서만 저장한다.
3. 공개 포스트만 정적 HTML로 생성한다.
4. 소유권 비밀번호와 비공개 열람 코드를 분리한다.
5. UI가 아니라 ASP.NET Core가 최종 권한을 판정한다.
6. 자동 저장과 공개 게시를 분리한다.
7. 빌드 실패는 현재 공개 사이트에 영향을 주지 않는다.
8. 삭제는 소프트 삭제하고 복구 기간을 제공한다.

# 23. 코딩 에이전트 실행 프롬프트

## 23.1 사용 방법

전체 기능을 한 번에 구현하도록 요청하지 않는다.

1. 먼저 마스터 프롬프트를 전달
2. 에이전트가 현재 저장소 구조와 기존 변경 사항을 조사
3. Phase 프롬프트를 하나씩 전달
4. 각 Phase의 테스트와 완료 기준 확인
5. 실패나 미완료 항목을 해결한 뒤 다음 Phase 진행

각 Phase는 독립적인 커밋 단위로 유지하는 것을 권장한다.

```txt
Phase 조사
  -> 구현 계획 확인
  -> 스키마/코드 변경
  -> 테스트
  -> 문서 갱신
  -> 사용자 검토
  -> 다음 Phase
```

## 23.2 마스터 프롬프트

다음 내용을 코딩 에이전트의 첫 요청으로 사용한다.

```txt
현재 Next.js 블로그를 Next.js + ASP.NET Core + SQLite 기반의
서버 관리형 블로그로 확장한다.

반드시 먼저 저장소 전체 구조, package.json, Next.js App Router,
현재 포스트 로딩 방식, 슬라이드/메모/그림 구현, 빌드와 배포 설정을
읽고 기존 기능을 파악하라.

기준 명세:
posts/Practice/Next.js/blog-improvement-roadmap.mdx

이 명세를 구현의 단일 기준으로 사용하라.
명세와 기존 코드가 충돌하면 기존 동작을 임의로 삭제하지 말고
차이를 보고한 뒤 호환 가능한 단계적 전환 방식을 선택하라.

핵심 정책:
1. 신규 DB 포스트는 Markdown만 지원한다.
2. MDX, JSX, import/export와 임의 React 컴포넌트는 허용하지 않는다.
3. 기존 MDX 포스트는 마이그레이션 전까지 읽기 전용으로 유지한다.
4. SystemPost는 초염몽 SuperAdmin이 관리한다.
5. 메모와 그림은 SuperAdmin 소유 SystemPost에서만 저장한다.
6. CommunityPost는 Markdown과 최소 메타데이터만 저장한다.
7. CommunityPost의 기본 공개 범위는 Public, 상태는 Published다.
8. 일반 사용자는 포스트별 소유권 비밀번호로 수정·삭제 권한을 증명한다.
9. 공개 포스트만 정적 HTML로 생성한다.
10. OwnerOnly와 PasswordProtected 본문은 정적 결과물에 포함하지 않는다.
11. Access Token은 30분, Refresh Token은 최초 로그인부터 30일이다.
12. Refresh Token은 회전하고 재사용을 탐지한다.
13. 최종 권한 판정은 ASP.NET Core에서 수행한다.
14. SQLite는 WAL 모드와 Foreign Key를 사용한다.
15. 삭제는 기본적으로 소프트 삭제한다.

작업 규칙:
- 한 번에 요청받은 Phase만 구현하라.
- 기존 사용자 변경과 관련 없는 파일을 되돌리지 마라.
- 파괴적인 Git 명령을 사용하지 마라.
- 파일 검색은 rg를 우선 사용하라.
- 기존 코딩 스타일과 디렉터리 구조를 우선 존중하라.
- 보안 기능을 UI 숨김만으로 구현하지 마라.
- 비밀번호, 토큰과 Secret을 코드나 로그에 남기지 마라.
- API, DB, UI 변경을 함께 검증하라.
- 스키마 변경은 EF Core Migration으로 작성하라.
- 구현 후 lint, typecheck, test, build 중 가능한 검증을 실행하라.
- 외부 네트워크 문제로 검증이 실패하면 코드 문제와 구분해 보고하라.
- 완료하지 못한 항목과 남은 위험을 명확히 보고하라.

첫 응답에서는 코드를 수정하지 말고 다음을 보고하라.
1. 현재 아키텍처 요약
2. 명세와 현재 코드의 차이
3. 이번 Phase에서 수정할 파일 후보
4. DB/API/UI 변경 계획
5. 테스트 계획
6. 위험 요소와 호환성 전략

사용자의 확인 또는 명시적인 구현 요청 후 변경을 시작하라.
```

```txt
- 30일 Refresh Token 설정
- Refresh 회전
- 폐기 토큰 재사용 탐지
- 로그아웃 이후 Refresh 실패
- 비활성 계정 접근 거부

- 인증 관련 통합 테스트 통과
```
