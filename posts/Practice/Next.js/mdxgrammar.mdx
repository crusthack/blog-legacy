# Markdown 문법

## Markdown 개요 
- Markdown(이하 md)은 html로 변환하기 위한 텍스트 형식입니다. 
- 마크다운은 라인 단위로 파싱하여 사람이 읽고 쓰기 편리한 텍스트 문법을 제공합니다. 또한 HTML로 변환하기 편리한 구조를 제공합니다. 
- 주로 github에서 `README`로 설명문을 제공하는 데에 쓰입니다.\
github에서의 md 렌더링을 GFM(GitHub Flavored Markdown)이라고 합니다. 
- 블로그에서 사용하는 마크다운 문법을 정리합니다. 

## 일반 텍스트 (p태그)
```md
일반 텍스트입니다.
줄바꿈 적용 안 됩니다. 

<p>일반 텍스트입니다. 줄바꿈 적용 안 됩니다.</p>
```
- 단순 텍스트 라인은 공백라인 이전까지를 p 태그로 묶어서 변환합니다.

## 헤더 (h태그)
```md
# h1 tag    => <h1>h1 tag</h1>
## h2 tag   => <h2>h2 tag</h2>
### h3 tag  => <h3>h3 tag</h3>
#### h4 tag => <h4>h4 tag</h4>
##### h5 tag => <h5>h5 tag</h5>
###### h6 tag => <h6>h6 tag</h6>
```
- `#`으로 시작하는 라인을 # 개수에 따라 hn 태그로 변환합니다.

## 줄바꿈 (br태그)
```
first line\
second line
  <p>
    first line<br />
    second line
  </p>
```
- html은 기본적으로 줄바꿈(line feed)을 지원하지 않으니, md에서 줄바꿈을 해줘도 줄바꿈으로 표현이 안 됩니다.
- 라인의 마지막을 역슬래시로 끝내면, br 태그로 변환합니다. 
- 혹은 라인 마지막을 공백 문자 2개로 끝내도 됩니다. 

## 인용문 (blockquote 태그)
```
> A greater than…
- >리스트 안에 있어도 처리됨. 

<blockquote>
  <p>A greater than…</p>
</blockquote>
```
- \>로 시작하는 문장을 인용문으로 처리합니다. 
- >1. 인용문은 다른 문법과 복합적인 사용이 가능합니다.

## 리스트 
### 순서 없는 리스트(ul 태그) 
```
- 순서 없는 리스트 앞에 점이 붙음 
- 같은 리스트로 묶임 
+ 새로운 리스트 
* 새로운 리스트 표현 

<ul>
  <li>순서 없는 리스트 앞에 점이 붙음</li>
  <li>같은 리스트로 묶임</li>
</ul>

<ul>
  <li>새로운 리스트</li>
</ul>  

<ul>
  <li>새로운 리스트 표현</li>
</ul>
```
- `-` `+` `*` 각 문자로 시작하는 라인은 ul 태그로 묶입니다. 
- 다른 문자를 사용하면 새로운 리스트로 처리됩니다.

### 순서 있는 리스트(ol 태그)
```
1. 1번 원소
2. 2번 원소
3. 3번 원소

  <ol>
    <li>1번 원소</li>
    <li>2번 원소</li>
    <li>3번 원소</li>
  </ol>
```
- 숫자로 시작하는 라인은 ol 태그로 묶입니다.

## 텍스트 서식(기울임, 강조, 취소선)

- *기울임꼴*, **굵게**, ***굵은 기울임꼴***, ~~취소선~~

# MDX 문법 

## 13. MDX란 무엇인가

MDX 파일에서는 Markdown과 JSX를 한 문서에서 사용할 수 있다.

```mdx
# 사용자 정보

일반적인 **Markdown 문단**입니다.

<UserCard name="CrustHack" />
```

MDX의 핵심 사용 방식은 두 가지다.

1. Markdown 문서 안에 JSX 컴포넌트를 직접 배치한다.
2. Markdown이 생성하는 기본 HTML 요소를 사용자 컴포넌트로 교체한다.

## 14. Markdown 요소를 컴포넌트로 교체하기

Markdown의 링크는 기본적으로 `<a>`로 변환된다.

```md
[MDX](https://mdxjs.com/ "MDX")
```

일반적인 JSX 결과는 다음 구조와 같다.

```jsx
<p>
  <a href="https://mdxjs.com/" title="MDX">MDX</a>
</p>
```

MDX 렌더러에 `components` 객체를 전달하면 `<a>` 대신 사용자 컴포넌트를 사용할 수 있다.

```tsx
import Readme from './readme.mdx';
import { FancyLink } from './components/FancyLink';

export default function Page() {
  return <Readme components={{ a: FancyLink }} />;
}
```

자주 교체하는 기본 요소는 다음과 같다.

| Markdown 표현 | 기본 요소 | 교체 예시 |
| --- | --- | --- |
| `[링크](url)` | `a` | 내부 링크 컴포넌트 |
| `![이미지](url)` | `img` | 최적화 이미지 컴포넌트 |
| `` `code` `` | `code` | 인라인 코드 컴포넌트 |
| 코드 블록 | `pre`, `code` | 복사 버튼이 있는 코드 블록 |
| `# 제목` | `h1` | 앵커가 포함된 제목 |
| `> 인용문` | `blockquote` | 경고 또는 안내 상자 |
| 표 | `table`, `thead`, `tbody`, `tr`, `th`, `td` | 반응형 표 |

기본 Markdown에서 교체할 수 있는 대표 요소는 다음과 같다.

```text
a, blockquote, br, code, em, h1, h2, h3, h4, h5, h6,
hr, img, li, ol, p, pre, strong, ul
```

`remark-gfm`을 사용하면 다음 요소도 추가로 다룰 수 있다.

```text
del, input, section, sup, table, tbody, td, th, thead, tr
```

## 15. MDX에서 JSX 컴포넌트 사용하기

컴포넌트는 HTML 태그와 구분되도록 대문자로 시작한다.

```mdx
<SeminarInfo
  title="Markdown과 MDX"
  date="2026-06-26"
  topic="문서 작성 문법"
  speakers={['Alice', 'Bob']}
/>
```

문자열 속성은 따옴표를 사용하고, 숫자·불리언·배열·객체·표현식은 중괄호를 사용한다.

```mdx
<Example
  label="문자열"
  count={3}
  enabled={true}
  tags={['markdown', 'mdx']}
  options={{ compact: true }}
/>
```

자식 내용을 받는 컴포넌트는 여는 태그와 닫는 태그를 모두 작성한다.

```mdx
<Callout>
  이 영역은 컴포넌트의 `children`으로 전달됩니다.
</Callout>
```

JSX 중괄호 안에서는 JavaScript 표현식을 사용할 수 있다.

```mdx
<p>계산 결과: {2 + 3}</p>
```

다만 문서가 데이터나 복잡한 로직에 과도하게 의존하면 일반 텍스트로서의 가독성과 유지보수성이 떨어진다. 복잡한 처리는 컴포넌트 내부로 옮기고 MDX에서는 선언적인 속성만 전달하는 편이 좋다.

## 16. 이 블로그에서 사용할 수 있는 MDX 컴포넌트

현재 블로그의 MDX 설정에는 다음과 같은 사용자 컴포넌트가 등록되어 있다.

| 컴포넌트 | 용도 |
| --- | --- |
| `CategoryPostList` | 카테고리 게시물 목록 출력 |
| `FancyShowcase` | 시각적 예제 또는 소개 카드 |
| `SeminarInfo` | 세미나 정보 표시 |
| `JavaScriptPlayground` | JavaScript 실행 예제 |
| `PythonPlayground` | Python 실행 예제 |
| `CipherPlayground` | 암호화 예제 |

예를 들어 현재 카테고리의 게시물 목록은 다음과 같이 삽입할 수 있다.

```mdx
<CategoryPostList
  title="같은 카테고리의 글"
  showDescription={true}
  limit={5}
/>
```

등록되지 않은 컴포넌트를 사용하면 빌드 또는 렌더링 오류가 발생한다. 새 컴포넌트를 추가할 때는 컴포넌트 파일을 만든 뒤 MDX 컴포넌트 매핑에도 등록해야 한다.

## 17. 수식

이 블로그는 `remark-math`와 `rehype-katex`를 사용하므로 인라인 수식과 블록 수식을 작성할 수 있다.

```md
질량과 에너지의 관계는 $E = mc^2$이다.
```

블록 수식은 `$$`로 감싼다.

```md
$$
I = \int_a^b f(x)\,dx
$$
```

렌더링 결과:

질량과 에너지의 관계는 $E = mc^2$이다.

$$
I = \int_a^b f(x)\,dx
$$

## 18. Frontmatter

게시물 맨 위의 YAML 영역은 제목, 날짜, 설명 같은 메타데이터를 정의한다.

```yaml
---
title: 'Markdown과 MDX 문법'
date: '2026-06-26'
description: 'Markdown과 MDX 문법을 정리합니다.'
titleSlide: true
manualSlides: false
---
```

frontmatter는 반드시 파일의 첫 줄에서 시작해야 한다.

| 필드 | 의미 |
| --- | --- |
| `title` | 게시물 제목 |
| `date` | 작성 또는 수정 날짜 |
| `description` | 게시물 요약 |
| `titleSlide` | 슬라이드 제목 페이지 사용 여부 |
| `manualSlides` | 수동 슬라이드 분할 사용 여부 |
| `background` | 게시물 또는 슬라이드 배경 설정 |

## 19. Markdown과 MDX 작성 원칙

문서를 안정적으로 유지하려면 다음 기준을 지키는 것이 좋다.

1. 일반 문서는 가능한 한 Markdown으로 작성한다.
2. Markdown으로 표현하기 어려운 기능만 HTML 또는 MDX 컴포넌트로 구현한다.
3. 제목 단계를 건너뛰지 않는다.
4. 코드에는 언어를 명시하고, 긴 코드에는 파일명을 붙인다.
5. 링크 텍스트는 목적지를 설명하도록 작성한다.
6. 이미지에는 의미 있는 대체 텍스트를 제공한다.
7. 복잡한 JavaScript 로직은 MDX 본문이 아니라 컴포넌트로 분리한다.
8. JSX 태그는 반드시 올바르게 닫는다.
9. `<`, `{`, `}`처럼 MDX 파서가 해석할 수 있는 문자를 일반 문장에 쓸 때는 코드 표기나 이스케이프를 사용한다.
10. 작성 후 포스트 뷰와 슬라이드 뷰를 모두 확인한다.
# MDX 블로그 커스텀 문법 

이 블로그의 MDX 처리는 `next-mdx-remote/rsc`의 `MDXRemote`를 중심으로 구성된다. 원본 `.mdx` 문자열은 Markdown AST, HTML AST, React 컴포넌트 렌더링 단계를 차례로 지나며, 커스텀 문법은 대부분 remark/rehype 플러그인이나 MDX 컴포넌트 매핑에서 추가된다.

## 20. MDXRemote 렌더링 파이프라인

전체 흐름은 다음과 같다.

```text
MDX source
→ remark 단계: Markdown/mdast 변환 및 문법 확장
→ rehype 단계: HTML/hast 변환 및 HTML 노드 보강
→ MDXRemote: React 컴포넌트로 렌더링
→ components 매핑: pre, img, a, 위젯 컴포넌트 치환
```

`lib/post/mdxPlugins.ts`는 remark/rehype 플러그인 목록을 한 곳에서 관리한다.

```ts
export const mdxPlugins = {
  remarkPlugins: [
    remarkGfm,
    remarkToc,
    remarkMath,
    remarkNormalizeCodeMeta,
    remarkGridBlock,
  ],
  rehypePlugins: [
    rehypeSlug,
    rehypeKatex,
    [rehypePrettyCode, prettyCodeOptions],
    rehypeInjectTitle,
  ],
};
```

`lib/post/mdx.tsx`는 이 설정을 `MDXRemote` 옵션으로 넘긴다.

```tsx
export const mdxOptions = {
  mdxOptions: mdxPlugins,
};
```

문법을 추가할 때는 어느 단계에서 처리할지 먼저 정해야 한다.

| 목적 | 수정 위치 |
| --- | --- |
| Markdown 원문 문법을 새로 해석 | `lib/remark/*` 플러그인 추가 |
| HTML 변환 후 노드 속성이나 구조 보강 | `lib/rehype/*` 플러그인 추가 |
| 기존 Markdown 요소의 렌더링 교체 | `createPostMdxComponents`, `createSlideMdxComponents` |
| JSX 컴포넌트를 MDX에서 직접 사용 | MDX 컴포넌트 import 후 components 매핑에 등록 |

## 21. remark 단계에서 추가한 문법

remark는 Markdown을 mdast로 다루는 단계다. 이 단계에서는 아직 HTML 요소가 아니라 Markdown 의미 구조를 다룬다. 따라서 `![ ... ]!` 같은 새 문법을 만들거나 코드블럭 메타를 정규화하는 작업은 remark 플러그인에서 처리하는 것이 자연스럽다.

현재 remark 플러그인은 다음 순서로 적용된다.

| 플러그인 | 역할 |
| --- | --- |
| `remarkGfm` | 표, 체크박스, 취소선 등 GitHub Flavored Markdown 문법 추가 |
| `remarkToc` | TOC 마커 기반 목차 생성 지원 |
| `remarkMath` | `$...$`, `$$...$$` 수식 문법 파싱 |
| `remarkNormalizeCodeMeta` | 코드블럭 메타에서 파일명/제목을 추출해 `title`로 정규화 |
| `remarkGridBlock` | `![ ... ]!` 커스텀 그리드 문법을 `GridBlock`, `GridItem` JSX 노드로 변환 |

### 코드블럭 메타 정규화

`remarkNormalizeCodeMeta`는 코드블럭에 붙은 여러 파일명 표기법을 하나의 `title` 메타로 맞춘다.

~~~~mdx
```tsx title="app/page.tsx"
export default function Page() {
  return <main>Hello</main>;
}
```
~~~~

다음 표기들도 같은 의미로 처리된다.

~~~~mdx
```tsx:app/page.tsx
export default function Page() {
  return <main>Hello</main>;
}
```
~~~~

~~~~mdx
```tsx file="app/page.tsx"
export default function Page() {
  return <main>Hello</main>;
}
```
~~~~

~~~~mdx
```tsx [app/page.tsx]
export default function Page() {
  return <main>Hello</main>;
}
```
~~~~

이 처리를 remark 단계에서 하는 이유는 코드블럭의 `lang`, `meta` 정보가 mdast `code` 노드에 남아 있기 때문이다. 이후 `rehypePrettyCode`가 이 정보를 사용해 하이라이팅된 HTML 구조를 만들고, `CodeBlock` 컴포넌트가 상단 제목 바와 복사 버튼을 렌더링한다.

### 그리드 블록 문법

`remarkGridBlock`은 블로그 전용 문법인 `![ ... ]!`를 처리한다.

```mdx
![
왼쪽 셀 | 가운데 셀 | 오른쪽 셀
]!
```

이 문법은 렌더링 전에 mdast를 순회하면서 다음과 같은 MDX JSX 노드로 바뀐다.

```mdx
<GridBlock cols="3">
  <GridItem>왼쪽 셀</GridItem>
  <GridItem>가운데 셀</GridItem>
  <GridItem>오른쪽 셀</GridItem>
</GridBlock>
```

행을 나눌 때는 단독 `,` 라인을 사용한다.

```mdx
![
1행 1열 | 1행 2열
,
2행 전체 너비
]!
```

셀 안에 문단, 리스트, 코드블럭 같은 블록 콘텐츠를 넣고 싶으면 단독 `|` 라인을 셀 구분자로 쓴다.

````mdx
![
설명 문단
|
- 목록 1
- 목록 2
|
***tsx
export function Example() {
  return <div />;
}
***
]!
````

그리드 내부 코드블럭은 `***언어`와 `***`로 감싼다. 이 문법은 `preprocessGridSource()`에서 실제 백틱 코드펜스로 바뀐다. 일반 Markdown 파서가 그리드 내부의 코드블럭과 그리드 구분자를 동시에 안정적으로 인식하도록 하기 위한 전처리다.

## 22. rehype 단계에서 보강하는 HTML

rehype는 Markdown이 HTML AST로 변환된 뒤의 단계다. 이 시점부터는 `h1`, `pre`, `code`, `span`, `table` 같은 HTML에 가까운 노드를 다룬다.

현재 rehype 플러그인은 다음 순서로 적용된다.

| 플러그인 | 역할 |
| --- | --- |
| `rehypeSlug` | heading에 GitHub 스타일 `id`를 추가 |
| `rehypeKatex` | remark에서 파싱한 수식 노드를 KaTeX HTML로 변환 |
| `rehypePrettyCode` | 코드블럭을 Shiki 기반 하이라이팅 HTML로 변환 |
| `rehypeInjectTitle` | 코드블럭 제목 정보를 `pre` 노드에도 주입 |

`rehypeSlug`는 렌더링되는 heading에 `id`를 붙인다.

```mdx
## 코드블럭 제목과 파일명
```

렌더링 결과는 다음처럼 앵커 이동이 가능한 HTML이 된다.

```html
<h2 id="코드블럭-제목과-파일명">코드블럭 제목과 파일명</h2>
```

오른쪽 TOC는 별도 파서인 `getTocFromMarkdown()`이 원본 Markdown에서 heading을 추출해 만든다. 이때 코드블럭 내부의 `# 제목` 같은 예제는 제외해야 실제 렌더링된 heading과 TOC 항목이 어긋나지 않는다.

`rehypePrettyCode`는 코드블럭을 Shiki로 하이라이팅한다.

```ts
export const prettyCodeOptions = {
  theme: 'dark-plus',
  keepBackground: true,
  defaultLang: { block: 'tsx' },
  langAlias: {
    js: 'javascript',
    ts: 'typescript',
    cs: 'csharp',
    py: 'python',
    sh: 'bash',
    shell: 'bash',
  },
};
```

언어 별칭은 하이라이팅 단계에서 실제 Shiki 언어 이름으로 바뀐다. `rehypeInjectTitle`은 pretty-code가 만든 구조에서 제목 정보를 찾아 `pre`에도 `data-title` 계열 속성을 넣어준다. 이후 `CodeBlock` 컴포넌트가 이 속성을 읽어 코드블럭 상단 바에 언어와 파일명을 표시한다.

## 23. MDXRemote components 매핑

remark/rehype가 문서 구조를 바꾸는 단계라면, components 매핑은 최종 React 렌더링을 어떤 컴포넌트로 할지 결정하는 단계다.

일반 포스트 뷰에서는 다음 매핑을 사용한다.

| MDX/HTML 요소 | 실제 렌더링 |
| --- | --- |
| `pre` | `CodeBlock` |
| `img` | `MdxImage` |
| `a` | 내부 링크 basePath 보정 후 `<a>` |
| `ul`, `ol` | 블로그 스타일이 적용된 목록 |
| `CategoryPostList` | 현재 category/currentSlug가 주입된 글 목록 |
| `GridBlock`, `GridItem` | 그리드 레이아웃 |
| `FancyShowcase`, `JavaScriptPlayground`, `PythonPlayground`, `CipherPlayground`, `SeminarInfo` | MDX에서 직접 호출 가능한 위젯 |

슬라이드 뷰에서는 같은 MDX라도 별도 매핑을 사용한다. `h1`~`h5`, `p`, `ul`, `ol`, `table`, `pre`, `img`가 슬라이드 화면에 맞는 크기와 여백으로 교체된다.

```tsx
pre: (props) => (
  <CodeBlock {...props} isSlide={true} weight={allocatedWeight} />
),
img: (props) => (
  <MdxImage
    category={category}
    slug={slug}
    isSlide={true}
    weight={allocatedWeight}
    {...props}
  />
),
```

같은 Markdown 문서가 일반 포스트와 슬라이드에서 다르게 보이는 이유는 이 컴포넌트 매핑이 다르기 때문이다.

## 24. 새 커스텀 문법을 추가하는 기준

커스텀 문법을 추가할 때는 어느 단계에서 처리할지 먼저 결정해야 한다.

| 만들고 싶은 기능 | 적절한 위치 |
| --- | --- |
| `:::note` 같은 새 블록 문법 | remark 플러그인 |
| 특정 Markdown 패턴을 JSX 컴포넌트로 변환 | remark 플러그인 |
| heading, code, table의 HTML 속성 보강 | rehype 플러그인 |
| 코드 하이라이팅, 수식 렌더링 | rehype 플러그인 |
| 이미지 경로, 링크 경로, 목록 스타일 변경 | MDX components 매핑 |
| 복잡한 UI나 상호작용 추가 | React 컴포넌트 등록 |

문법을 새로 만드는 경우에는 가능하면 원본 Markdown에서 읽기 쉬운 형태를 유지해야 한다. 문서 작성자가 원문만 봐도 구조를 이해할 수 있어야 하고, 코드블럭·수식·표·그리드처럼 파서 상태가 복잡한 문법과 충돌하지 않아야 한다.

## 25. 커스텀 문법 작성 시 주의점

1. 코드 예제 안의 `# 제목`은 TOC에 들어가지 않도록 반드시 코드블럭으로 감싼다.
2. 중첩 코드펜스 예제를 문서화할 때는 바깥쪽에 `~~~~mdx` 같은 물결표 펜스를 쓰면 슬라이드 파서와 충돌을 줄일 수 있다.
3. 그리드 블록의 시작 `![`와 끝 `]!`는 반드시 단독 라인에 둔다.
4. 그리드 블록 안에서 코드블럭을 넣을 때는 백틱 대신 `***언어` 문법을 사용한다.
5. 상대 이미지는 현재 글의 `public/images/{category}/{slug}/` 폴더에 둔다.
6. MDX 컴포넌트 속성에서 문자열은 따옴표, 숫자/불리언/배열/객체는 `{}`를 사용한다.
7. 클라이언트 컴포넌트는 글 본문에서는 동작하지만, 인쇄나 정적 캡처에서는 상호작용 상태가 제한될 수 있다.

## 26. 사용 가능한 커스텀 문법 요약

이 블로그는 기본 Markdown/MDX 문법 위에 몇 가지 커스텀 렌더링 규칙을 추가로 사용한다. 대부분은 `lib/post/mdx.tsx`의 MDX 컴포넌트 매핑과 `lib/remark`, `lib/rehype` 플러그인에서 처리된다.
