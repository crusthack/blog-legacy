# Windows에서의 clang/llvm 환경 설정

- llvm 설치  
[LLVM](https://github.com/llvm/llvm-project)

- cmake 설치  
[CMAKE](https://cmake.org/download/)

- ninja 설치 후 llvm bin파일로 이동  
[Ninja](https://github.com/ninja-build/ninja)

- llvm - clang을 프론트로 사용하는 백엔드 컴파일러 툴체인, cpp 컴파일러 clang이 같이 설치됨.
- cmake - cpp 프로젝트 빌드 툴
- Ninja - cmake를 스크립트로 사용하는 빌드 툴

## 프로젝트 설정
### 디렉토리 구조
```txt
cpp/
├── CMakeLists.txt      (cmake 설정 파일)
├── src/                (소스 파일)
│   ├── main.cpp
│   ├── src...
└── build/              (컴파일 결과물 - 언제든 지워도 되는 곳)
```
- src폴더에 소스파일 두고서 cmakelist로 빌드 설정, build 폴더에 빌드 출력물 모음

### cmake 설정 예시
```txt
// cmake 버전 명시
cmake_minimum_required(VERSION 4.00)
project(cpp LANGUAGES CXX)

// C++ 26 표준 설정
set(CMAKE_CXX_STANDARD 26)

// src 폴더 내의 소스 파일 지정
add_executable(main 
    src/main.cpp 
    src/sub/sub.cpp
)

// 헤더 파일 경로 추가 (include 시에 앞에 폴더명 안 적어도 되게 해줌)
target_include_directories(main PRIVATE src/sub)
```

- 수동으로 소스파일 추가할 수도 있고, 자동으로 모든 소스파일 추적해서 추가하는 옵션도 있음. 
- 블로그 호환성을 위해 주석 //로 설정, 실제 파일은 #으로 주석처리 해야함

### 빌드 명령어
```cmd
mkdir build
cd build
// cmake 설정, 이전 디렉토리(..) 의 CMakeLists.txt 기반
cmake -G "Ninja" -DCMAKE_CXX_COMPILER=clang++ ..
cmake --build .
main.exe    
```

# Linux에서의 clang/llvm 환경 설정

Linux의 C++ 개발환경은 하나의 프로그램을 설치하는 것으로 끝나지 않는다. 소스 코드를 기계어로 변환하는 컴파일러, 목적 파일을 합치는 링커, 프로젝트의 빌드 규칙을 관리하는 CMake, 실제 빌드를 빠르게 실행하는 Ninja, 코드를 분석하는 clangd와 디버거가 하나의 도구 체인을 구성한다.

이 글에서는 다음 조합을 기준으로 개발환경을 구성한다.

```txt
운영체제        Linux
컴파일러        Clang / clang++
컴파일러 기반   LLVM
링커            시스템 링커 또는 LLD
프로젝트 설정   CMake
빌드 실행       Ninja
언어 서버       clangd
디버거          LLDB
코드 품질       clang-format, clang-tidy, Sanitizer
```

설정을 모두 마치면 다음 작업을 할 수 있다.

1. 터미널에서 단일 C++ 파일 컴파일
2. 여러 헤더와 소스 파일로 구성된 CMake 프로젝트 빌드
3. Debug, Release 결과물을 별도 디렉터리에서 관리
4. 변경된 파일만 Ninja로 빠르게 다시 빌드
5. clangd로 에디터 자동 완성과 실시간 오류 확인
6. LLDB로 브레이크포인트, 변수, 호출 스택 조사
7. Sanitizer와 clang-tidy로 런타임 오류와 코드 문제 탐지

- `clang` - C/C++ 컴파일러
- `llvm` - Clang이 사용하는 컴파일러 기반 도구 모음
- `lld` - LLVM 링커
- `clangd` - 에디터의 코드 완성, 오류 표시, 정의 이동을 지원하는 언어 서버
- `clang-format`, `clang-tidy` - 코드 포맷팅 및 정적 분석 도구
- `cmake`, `ninja` - 프로젝트 설정 및 빌드 도구

## 컴파일 도구 이해

C++ 프로젝트를 빌드할 때 CMake, Ninja, Clang은 서로 다른 역할을 담당한다. CMake나 Ninja가 C++ 코드를 직접 기계어로 번역하는 것은 아니다.

```txt
CMakeLists.txt
    │
    ▼
CMake ── build.ninja 생성
    │
    ▼
Ninja ── 필요한 컴파일 명령 실행
    │
    ├── clang++ ── .cpp를 .o 목적 파일로 컴파일
    │
    └── lld 또는 시스템 링커 ── 목적 파일을 실행 파일로 연결
```

### Clang

Clang은 C, C++, Objective-C 코드를 분석하고 컴파일하는 컴파일러 프론트엔드이다.

```bash
# C 소스 컴파일
clang main.c -o main

# C++ 소스 컴파일
clang++ main.cpp -o main
```

C++에서는 `clang`이 아니라 `clang++`를 사용한다. `clang++`는 C++ 표준 라이브러리를 링크하는 데 필요한 옵션을 자동으로 추가한다.

### LLVM

LLVM은 컴파일러를 만들기 위한 기반 기술과 여러 도구의 모음이다. Clang이 소스 코드를 분석한 뒤 LLVM의 중간 표현과 최적화 기능을 이용해 대상 CPU의 기계어를 생성한다.

- `clang`, `clang++` - C/C++ 컴파일러
- `llvm-ar` - 정적 라이브러리 생성 및 관리
- `llvm-objdump` - 목적 파일과 실행 파일 분석
- `llvm-nm` - 목적 파일의 심볼 확인
- `llvm-config` - 설치된 LLVM의 버전과 빌드 정보 확인

일반적인 C++ 개발에서는 LLVM 내부 단계를 직접 다루기보다 `clang++`를 통해 사용한다.

### 링커와 LLD

각 `.cpp` 파일은 먼저 `.o` 목적 파일로 컴파일된다. 링커는 여러 목적 파일과 라이브러리를 하나의 실행 파일로 연결한다.

```txt
main.cpp ── clang++ ── main.o ─┐
                               ├── linker ── main
sub.cpp  ── clang++ ── sub.o  ─┘
```

LLD는 LLVM 프로젝트의 링커이다. 반드시 사용해야 하는 것은 아니며, 별도 설정이 없으면 Clang은 시스템 기본 링커를 사용할 수 있다.

```bash
# LLD를 명시적으로 사용해 단일 파일 빌드
clang++ -fuse-ld=lld main.cpp -o main
```

### CMake

CMake는 컴파일러가 아니라 빌드 시스템 생성기이다. `CMakeLists.txt`를 읽고 현재 운영체제와 선택한 생성기에 맞는 빌드 파일을 만든다.

```bash
cmake -S . -B build -G Ninja \
  -DCMAKE_CXX_COMPILER=clang++
```

위 명령에서 CMake는 다음 작업을 수행한다.

1. `CMakeLists.txt` 읽기
2. Clang 컴파일러가 사용 가능한지 검사
3. 헤더 경로, 컴파일 옵션, 의존 관계 계산
4. `build/` 아래에 `build.ninja`와 캐시 파일 생성

CMake 설정 단계는 프로젝트를 어떻게 빌드할지 결정하지만 실제 모든 소스 파일을 직접 컴파일하지는 않는다.

### Ninja

Ninja는 CMake가 생성한 `build.ninja`를 읽고 실제 컴파일 명령을 실행하는 빌드 도구이다. 파일의 변경 시각과 의존 관계를 비교해 다시 빌드해야 하는 부분만 처리한다.

```bash
ninja -C build
```

예를 들어 `src/main.cpp`만 수정했다면 관련 목적 파일만 다시 컴파일하고 실행 파일을 다시 링크한다. 변경되지 않은 파일은 다시 컴파일하지 않으므로 전체 프로젝트를 매번 빌드하는 것보다 빠르다.

`build.ninja`는 CMake가 관리하는 생성 파일이므로 직접 편집하지 않는다. 빌드 구성을 변경하려면 `CMakeLists.txt`를 수정한다.

### cmake --build와 ninja의 차이

Ninja 생성기를 사용한 프로젝트에서는 다음 두 명령이 거의 같은 빌드를 수행한다.

```bash
cmake --build build
ninja -C build
```

- `cmake --build build` - CMake가 선택된 빌드 도구를 대신 실행한다. Ninja 외의 생성기로 바뀌어도 명령이 동일하다.
- `ninja -C build` - Ninja를 직접 실행한다. Ninja 전용 옵션과 진단 도구를 바로 사용할 수 있다.

일상적인 빌드에는 이식성이 좋은 `cmake --build build`를 사용하고, 상세 명령 출력이나 타깃 조사처럼 Ninja 기능이 필요할 때 `ninja -C build`를 사용하면 된다.

### clangd, clang-format, clang-tidy

이 도구들은 실행 파일을 만드는 빌드 도구는 아니지만 C++ 개발 과정에 함께 사용된다.

- `clangd` - 에디터에서 자동 완성, 오류 표시, 정의 이동 제공
- `clang-format` - 정해진 규칙에 맞게 코드 서식 정리
- `clang-tidy` - 잠재적인 버그와 좋지 않은 코드 패턴을 정적으로 검사

`clangd`와 `clang-tidy`가 실제 프로젝트의 헤더 경로와 컴파일 옵션을 알 수 있도록 CMake에서 `CMAKE_EXPORT_COMPILE_COMMANDS=ON`을 사용한다.

## 도구 설치

### Ubuntu / Debian

배포판이 제공하는 안정 버전을 설치하는 가장 간단한 방법이다.

```bash
sudo apt update
sudo apt install clang llvm lld lldb clangd clang-format clang-tidy cmake ninja-build
```

최신 LLVM이 꼭 필요하다면 [LLVM Debian/Ubuntu 공식 저장소](https://apt.llvm.org/)의 설치 스크립트를 사용할 수 있다. 특정 LLVM 버전이 필요하지 않다면 위의 배포판 패키지를 사용하는 편이 관리하기 쉽다.

### Fedora

```bash
sudo dnf install clang llvm lld lldb clang-tools-extra cmake ninja-build
```

### Arch Linux

```bash
sudo pacman -Syu clang llvm lld lldb cmake ninja
```

## 설치 확인

아래 명령이 모두 버전을 출력하면 기본 도구 설치가 끝난 것이다.

```bash
clang --version
clang++ --version
llvm-config --version
cmake --version
ninja --version
clangd --version
```

`clang`은 C 컴파일러이고 `clang++`는 C++ 표준 라이브러리까지 자동으로 연결하는 C++ 컴파일러이다. C++ 파일은 `clang++`로 빌드한다.

## 단일 C++ 파일로 먼저 확인

프로젝트 설정 전에 컴파일러가 정상 동작하는지 확인한다.

```bash
mkdir -p ~/cpp-test
cd ~/cpp-test

cat > main.cpp <<'EOF'
#include <iostream>

int main()
{
    std::cout << "hello, clang!!" << std::endl;
    return 0;
}
EOF

clang++ -std=c++23 -Wall -Wextra -Wpedantic main.cpp -o main
./main
```

터미널에 `hello, clang!!`가 출력되면 컴파일러와 기본 C++ 표준 라이브러리가 정상적으로 연결된 것이다.

## CMake 프로젝트 빌드

다음 디렉터리 구조를 사용한다.

```txt
cpp/
├── CMakeLists.txt
└── src/
    └── main.cpp
```

프로젝트 파일을 직접 생성하려면 다음 명령을 순서대로 실행한다.

```bash
mkdir -p cpp/src
cd cpp
```

`src/main.cpp`를 작성한다.

```c++:src/main.cpp
#include <iostream>

int main()
{
    std::cout << "hello, CMake + Clang!!" << std::endl;
    return 0;
}
```

프로젝트 루트의 `CMakeLists.txt`를 작성한다.

```cmake:CMakeLists.txt
cmake_minimum_required(VERSION 3.20)
project(cpp LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 23)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)

add_executable(main
    src/main.cpp
)

target_compile_options(main PRIVATE
    -Wall
    -Wextra
    -Wpedantic
)
```

- `CMAKE_CXX_STANDARD_REQUIRED ON` - 지정한 C++ 표준을 반드시 사용
- `CMAKE_CXX_EXTENSIONS OFF` - `gnu++23` 대신 표준 `c++23` 모드 사용
- `target_compile_options` - 현재 실행 파일에 경고 옵션 적용

```terminal
cmake -S . -B build -G Ninja \
    -DCMAKE_CXX_COMPILER=clang++-18
```
- cmake 처음 빌드 

## 헤더 파일과 소스 파일 추가

Ninja를 사용하는 현재 구성에서는 Makefile이나 `build.ninja`를 직접 수정하지 않는다. 프로젝트에 파일을 추가할 때는 `CMakeLists.txt`에서 실행 파일 타깃에 새 소스 파일을 등록한다.

예제로 덧셈 기능을 별도 파일로 분리한다.

```txt
cpp/
├── CMakeLists.txt
└── src/
    ├── main.cpp
    ├── calculator.cpp
    └── calculator.hpp
```

### 헤더 파일 작성

`src/calculator.hpp`에 함수 선언을 작성한다.

```c++:src/calculator.hpp
#pragma once

int add(int left, int right);
```

`#pragma once`는 하나의 소스 파일에서 같은 헤더가 여러 번 포함되는 것을 방지한다.

### 소스 파일 작성

`src/calculator.cpp`에 함수 구현을 작성한다.

```c++:src/calculator.cpp
#include "calculator.hpp"

int add(int left, int right)
{
    return left + right;
}
```

`src/main.cpp`에서 헤더를 포함하고 함수를 사용한다.

```c++:src/main.cpp
#include "calculator.hpp"

#include <iostream>

int main()
{
    std::cout << add(10, 20) << std::endl;
    return 0;
}
```

### CMakeLists.txt에 파일 등록

`add_executable`에 새 `.cpp` 파일을 추가한다.

```cmake:CMakeLists.txt
cmake_minimum_required(VERSION 3.20)
project(cpp LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 23)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)

add_executable(main
    src/main.cpp
    src/calculator.cpp
    src/calculator.hpp
)

target_include_directories(main PRIVATE
    ${CMAKE_CURRENT_SOURCE_DIR}/src
)

target_compile_options(main PRIVATE
    -Wall
    -Wextra
    -Wpedantic
)
```

- `.cpp` 파일은 컴파일 대상이므로 반드시 타깃에 등록한다.
- `.hpp` 헤더는 직접 컴파일되지 않으므로 생략해도 빌드는 가능하지만, 프로젝트 파일 목록을 명확하게 관리하기 위해 함께 등록할 수 있다.
- `target_include_directories`를 설정하면 `#include "src/calculator.hpp"` 대신 `#include "calculator.hpp"`로 작성할 수 있다.
- `PRIVATE`는 이 헤더 경로가 현재 `main` 타깃에서만 필요하다는 의미이다.

파일이 많아지면 `target_sources`로 소스 목록을 분리해 작성할 수도 있다.

```cmake:CMakeLists.txt
add_executable(main)

target_sources(main PRIVATE
    src/main.cpp
    src/calculator.cpp
    src/calculator.hpp
)
```

새 파일을 등록한 뒤에는 평소와 동일하게 빌드한다.

```bash
cmake --build build
./build/main
```

`CMakeLists.txt`가 변경되면 CMake로 생성된 Ninja 프로젝트는 빌드 과정에서 설정 변경을 감지하고 `build.ninja`를 자동으로 갱신한다. 일반적인 파일 추가에서는 빌드 디렉터리를 삭제할 필요가 없다.

### 하위 디렉터리의 헤더 사용

헤더를 `include/`에 따로 관리하려면 다음 구조를 사용할 수 있다.

```txt
cpp/
├── CMakeLists.txt
├── include/
│   └── calculator/
│       └── calculator.hpp
└── src/
    ├── main.cpp
    └── calculator.cpp
```

```cmake:CMakeLists.txt
add_executable(main
    src/main.cpp
    src/calculator.cpp
    include/calculator/calculator.hpp
)

target_include_directories(main PRIVATE
    ${CMAKE_CURRENT_SOURCE_DIR}/include
)
```

이 경우 소스에서는 `include/` 이후의 경로로 헤더를 포함한다.

```c++
#include <calculator/calculator.hpp>
```

`file(GLOB ...)`을 사용하면 소스 파일을 자동 수집할 수 있지만, 파일 추가와 삭제를 CMake가 예상하지 못하는 경우가 생길 수 있다. 작은 프로젝트에서는 위 예제처럼 파일을 명시적으로 등록하는 방법이 가장 이해하기 쉽고 안정적이다.

두 파일을 작성한 다음 프로젝트 최상위 디렉터리인 `cpp/`에서 다음 명령을 실행한다.

```bash
cd cpp
```

Clang과 Ninja를 사용하도록 빌드 디렉터리를 설정한다.

```bash
cmake -S . -B build -G Ninja \
  -DCMAKE_C_COMPILER=clang \
  -DCMAKE_CXX_COMPILER=clang++ \
  -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
```

설정이 끝나면 프로젝트를 빌드하고 실행한다.

```bash
cmake --build build
./build/main
```

- `-S .` - 현재 디렉터리에서 `CMakeLists.txt`를 찾음
- `-B build` - 생성 파일과 빌드 결과를 `build/`에 모음
- `-G Ninja` - Ninja 빌드 시스템 사용
- `CMAKE_CXX_COMPILER=clang++` - C++ 컴파일러를 Clang으로 고정
- `CMAKE_BUILD_TYPE=Debug` - 디버깅 정보를 포함한 빌드
- `CMAKE_EXPORT_COMPILE_COMMANDS=ON` - `clangd`가 프로젝트의 컴파일 옵션을 읽을 수 있도록 설정

컴파일러가 정말 Clang으로 설정됐는지는 다음 명령으로 확인할 수 있다.

```bash
grep CMAKE_CXX_COMPILER build/CMakeCache.txt
```

## Debug, Release 빌드 설정

같은 소스 코드라도 개발 중인지 배포할 프로그램인지에 따라 컴파일 방법이 달라진다. CMake에서는 이를 **빌드 타입(build type)** 으로 구분한다.

| 빌드 타입 | 최적화 | 디버깅 정보 | 주요 용도 |
|---|---:|---:|---|
| `Debug` | 거의 사용하지 않음 | 포함 | 기능 개발, 브레이크포인트와 변수 확인 |
| `Release` | 적극 사용 | 일반적으로 제외 | 성능 측정, 최종 배포 |
| `RelWithDebInfo` | 사용 | 포함 | 실제 성능에 가까운 상태에서 문제 분석 |
| `MinSizeRel` | 실행 파일 크기 중심 | 일반적으로 제외 | 파일 크기가 중요한 배포 환경 |

구체적인 컴파일 옵션은 컴파일러와 CMake 버전에 따라 달라질 수 있지만 일반적으로 다음과 같은 차이가 있다.

```txt
Debug
- 디버깅 심볼 포함
- 코드 최적화를 줄여 소스 코드와 실행 순서가 비교적 잘 일치
- 실행 속도가 느리고 실행 파일이 커질 수 있음

Release
- 실행 속도를 위한 최적화 적용
- assert를 비활성화하는 NDEBUG가 정의될 수 있음
- 함수가 인라인되거나 코드 순서가 바뀌어 디버깅하기 어려움

RelWithDebInfo
- 최적화와 디버깅 정보를 함께 사용
- 운영 환경과 비슷한 성능에서 호출 스택을 조사할 때 유용
- 최적화로 인해 일부 지역 변수가 보이지 않을 수 있음
```

Ninja는 **단일 구성 생성기**이므로 하나의 빌드 디렉터리는 한 번에 하나의 빌드 타입을 사용한다. Debug와 Release 결과가 섞이지 않도록 빌드 디렉터리를 분리하는 방법을 권장한다.

### Debug 설정과 빌드

```bash
cmake -S . -B build/debug -G Ninja \
  -DCMAKE_C_COMPILER=clang \
  -DCMAKE_CXX_COMPILER=clang++ \
  -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
```

```bash
cmake --build build/debug
./build/debug/main
```

Debug 실행 파일에는 LLDB가 소스 파일과 줄 번호, 함수, 변수를 찾는 데 필요한 디버깅 정보가 포함된다. 개발 중에는 이 구성을 기본으로 사용한다.

### Release 설정과 빌드

```bash
cmake -S . -B build/release -G Ninja \
  -DCMAKE_C_COMPILER=clang \
  -DCMAKE_CXX_COMPILER=clang++ \
  -DCMAKE_BUILD_TYPE=Release
```

```bash
cmake --build build/release
./build/release/main
```

Release 빌드는 성능과 최종 동작을 확인할 때 사용한다. Debug와 Release의 실행 결과가 같더라도 최적화되지 않은 Debug 빌드의 실행 시간을 최종 성능으로 판단하면 안 된다.

### 디버깅 정보가 포함된 최적화 빌드

최적화된 상태에서만 발생하는 문제를 조사하려면 `RelWithDebInfo`를 사용한다.

```bash
cmake -S . -B build/relwithdebinfo -G Ninja \
  -DCMAKE_C_COMPILER=clang \
  -DCMAKE_CXX_COMPILER=clang++ \
  -DCMAKE_BUILD_TYPE=RelWithDebInfo
cmake --build build/relwithdebinfo
```

### 현재 빌드 타입 확인

```bash
grep CMAKE_BUILD_TYPE build/debug/CMakeCache.txt
grep CMAKE_BUILD_TYPE build/release/CMakeCache.txt
```

`CMAKE_BUILD_TYPE`을 지정하지 않으면 단일 구성 생성기에서 빈 값으로 남을 수 있다. 의도하지 않은 옵션으로 빌드하지 않도록 새 빌드 디렉터리를 설정할 때 타입을 명시한다.

### CMakeLists.txt에서 기본 빌드 타입 설정

명령행에서 빌드 타입을 생략했을 때만 Debug를 기본값으로 사용하려면 `project()` 다음에 다음 코드를 추가할 수 있다.

```cmake:CMakeLists.txt
if(NOT CMAKE_BUILD_TYPE AND NOT CMAKE_CONFIGURATION_TYPES)
    set(CMAKE_BUILD_TYPE Debug CACHE STRING "Build type" FORCE)
    set_property(CACHE CMAKE_BUILD_TYPE PROPERTY STRINGS
        Debug
        Release
        RelWithDebInfo
        MinSizeRel
    )
endif()
```

명령행에서 `-DCMAKE_BUILD_TYPE=Release`를 전달하면 위 기본값보다 사용자가 지정한 Release가 우선한다.

## LLDB 디버거 사용법

LLDB는 LLVM 프로젝트의 디버거이다. 실행 중인 프로그램을 특정 줄에서 멈추고 변수 값, 호출 스택, 메모리와 프로그램 흐름을 조사할 수 있다.

디버거를 사용하려면 먼저 Debug 타입으로 빌드한다.

```bash
cmake --build build/debug
lldb ./build/debug/main
```

명령을 실행하면 LLDB 프롬프트가 나타난다.

```txt
(lldb)
```

### 기본 디버깅 순서

`main` 함수에 브레이크포인트를 설정하고 프로그램을 실행한다.

```txt
(lldb) breakpoint set --name main
(lldb) run
```

짧은 별칭도 사용할 수 있다.

```txt
(lldb) b main
(lldb) r
```

프로그램이 `main`에서 멈추면 한 줄씩 실행하며 상태를 확인한다.

```txt
(lldb) next
(lldb) step
(lldb) frame variable
(lldb) continue
(lldb) quit
```

- `next`, `n` - 현재 줄을 실행하고 다음 줄에서 멈춤. 호출된 함수 안으로 들어가지 않음
- `step`, `s` - 현재 줄의 함수 안으로 들어가서 멈춤
- `finish` - 현재 함수를 끝내고 호출한 위치로 돌아감
- `continue`, `c` - 다음 브레이크포인트까지 계속 실행
- `quit`, `q` - LLDB 종료

### 파일과 줄 번호에 브레이크포인트 설정

```txt
(lldb) breakpoint set --file main.cpp --line 8
(lldb) breakpoint set -f calculator.cpp -l 5
(lldb) breakpoint list
```

- `breakpoint set --file ... --line ...` - 지정한 파일과 줄에서 중단
- `breakpoint set --name add` - `add` 함수가 호출될 때 중단
- `breakpoint list` - 등록된 브레이크포인트 확인
- `breakpoint delete 1` - 1번 브레이크포인트 삭제
- `breakpoint disable 1` - 삭제하지 않고 일시적으로 비활성화

### 변수와 표현식 확인

현재 함수의 인자와 지역 변수를 모두 확인한다.

```txt
(lldb) frame variable
```

특정 변수만 확인한다.

```txt
(lldb) frame variable left
(lldb) frame variable right
```

C++ 표현식을 계산하거나 함수를 호출하려면 `expression`을 사용한다.

```txt
(lldb) expression left + right
(lldb) expression -- left = 100
```

`expression`은 프로그램 상태를 바꿀 수도 있으므로 단순히 값을 확인할 때는 부작용이 없는 `frame variable`을 먼저 사용한다.

### 호출 스택 확인

호출 스택은 현재 위치에 도달할 때까지 호출된 함수의 순서를 보여준다.

```txt
(lldb) backtrace
(lldb) bt
```

```txt
frame #0: add(...)
frame #1: main
```

다른 스택 프레임을 선택하면 호출한 함수의 변수를 확인할 수 있다.

```txt
(lldb) frame select 1
(lldb) frame variable
```

프로그램이 잘못된 메모리 접근으로 중단되면 먼저 `bt`로 어떤 함수 호출을 거쳐 오류 지점에 도달했는지 확인한다.

### 실행 인자 전달

프로그램이 명령행 인자를 받는다면 LLDB 실행 시 `--` 뒤에 전달할 수 있다.

```bash
lldb -- ./build/debug/main first second
```

LLDB 안에서 설정하는 방법도 있다.

```txt
(lldb) settings set target.run-args first second
(lldb) run
```

### 조건부 브레이크포인트

반복문이 특정 조건에 도달했을 때만 멈추도록 설정할 수 있다.

```txt
(lldb) breakpoint set --file main.cpp --line 15 --condition 'index == 10'
```

조건부 브레이크포인트는 반복문이 여러 번 실행되는 동안 문제가 발생하는 특정 상태만 조사할 때 유용하다.

### 자주 사용하는 LLDB 명령

| 명령 | 설명 |
|---|---|
| `run`, `r` | 프로그램 시작 |
| `continue`, `c` | 다음 중단 지점까지 실행 |
| `next`, `n` | 함수 안으로 들어가지 않고 다음 줄 실행 |
| `step`, `s` | 호출한 함수 안으로 이동 |
| `finish` | 현재 함수 실행을 마치고 호출자로 복귀 |
| `frame variable` | 현재 프레임의 변수 확인 |
| `expression 식` | C++ 표현식 평가 |
| `bt` | 호출 스택 출력 |
| `breakpoint list` | 브레이크포인트 목록 출력 |
| `help 명령` | 특정 명령의 도움말 출력 |
| `quit`, `q` | 디버거 종료 |

[LLDB 공식 튜토리얼](https://lldb.llvm.org/use/tutorial.html)에서 브레이크포인트, 스텝 실행, 변수와 프레임 조사에 대한 전체 명령을 확인할 수 있다.

## Sanitizer로 메모리 오류 찾기

LLDB가 멈춘 프로그램의 상태를 직접 조사하는 도구라면 Sanitizer는 실행 중 잘못된 메모리 접근이나 정의되지 않은 동작을 자동으로 감지하는 도구이다. 두 도구는 서로 대체하는 것이 아니라 함께 사용할 수 있다.

CMake에 디버깅용 Sanitizer 옵션을 추가한다.

```cmake:CMakeLists.txt
option(ENABLE_SANITIZERS "Enable AddressSanitizer and UndefinedBehaviorSanitizer" OFF)

if(ENABLE_SANITIZERS)
    target_compile_options(main PRIVATE
        -fsanitize=address,undefined
        -fno-omit-frame-pointer
    )
    target_link_options(main PRIVATE
        -fsanitize=address,undefined
    )
endif()
```

Sanitizer 전용 빌드 디렉터리를 설정한다.

```bash
cmake -S . -B build/sanitize -G Ninja \
  -DCMAKE_CXX_COMPILER=clang++ \
  -DCMAKE_BUILD_TYPE=Debug \
  -DENABLE_SANITIZERS=ON
cmake --build build/sanitize
./build/sanitize/main
```

- AddressSanitizer - 배열 범위 초과, 해제한 메모리 접근 등 탐지
- UndefinedBehaviorSanitizer - 정수 오버플로 일부, 잘못된 시프트 등 정의되지 않은 동작 탐지
- `-fno-omit-frame-pointer` - 오류 보고서의 호출 스택을 더 정확하게 표시

Sanitizer가 오류를 출력하면 오류 종류와 최초 발생 위치를 확인한 뒤, 같은 Debug 실행 파일을 LLDB로 열어 해당 줄에 브레이크포인트를 설정하면 원인을 더 자세히 조사할 수 있다.

## Ninja 사용법

`cmake -G Ninja`를 실행하면 CMake가 `build/build.ninja` 파일을 생성한다. 이 파일에는 소스 파일을 어떤 순서와 옵션으로 컴파일할지가 기록된다. 직접 수정하지 않고 `CMakeLists.txt`를 변경한 뒤 CMake가 다시 생성하도록 한다.

### Ninja를 사용하는 이유

Ninja는 빌드 속도와 증분 빌드에 집중해서 만들어진 작은 빌드 도구이다. C++ 코드를 직접 컴파일하지 않고, CMake가 생성한 명령을 필요한 순서에 맞춰 Clang에 전달한다.

- **증분 빌드가 빠름** - 변경된 소스 파일과 영향을 받는 타깃만 다시 빌드한다.
- **병렬 빌드** - 서로 의존하지 않는 컴파일 작업을 여러 CPU 코어에서 동시에 실행한다.
- **낮은 실행 오버헤드** - 빌드 파일을 읽고 변경 사항을 판단하는 시간이 짧다.
- **간결한 출력** - 기본 출력에는 현재 진행 중인 핵심 작업만 표시한다.
- **CMake와 연동이 쉬움** - `-G Ninja`만 지정하면 CMake가 `build.ninja`를 자동 생성한다.
- **여러 운영체제에서 사용 가능** - Linux뿐 아니라 Windows와 macOS에서도 같은 방식으로 사용할 수 있다.

예를 들어 여러 소스 파일 중 `main.cpp`만 수정하면 Ninja는 모든 파일을 다시 컴파일하지 않는다.

```txt
수정 전 빌드
main.cpp ── main.o ─┐
                    ├── main
sub.cpp  ── sub.o  ─┘

main.cpp만 수정한 뒤
main.cpp ── main.o 다시 생성 ─┐
                              ├── main 다시 링크
sub.cpp  ── 기존 sub.o 재사용 ─┘
```

Ninja가 반드시 필요한 것은 아니다. CMake는 Unix Makefiles 같은 다른 빌드 시스템도 생성할 수 있다.

```bash
# Ninja 사용
cmake -S . -B build -G Ninja

# Make 사용
cmake -S . -B build -G "Unix Makefiles"
```

작은 프로젝트에서는 체감 차이가 작을 수 있지만, 소스 파일과 타깃이 많아질수록 Ninja의 빠른 변경 감지와 병렬 실행이 유용하다. 이 글에서는 명령이 단순하고 Clang/CMake와 함께 사용하기 편리하므로 Ninja를 사용한다.

일반적으로는 빌드 도구에 상관없이 동일하게 사용할 수 있는 CMake 명령을 권장한다.

```bash
# 변경된 파일만 증분 빌드
cmake --build build

# main 타깃만 빌드
cmake --build build --target main

# 동시에 실행할 작업을 4개로 제한
cmake --build build --parallel 4

# 실제 컴파일 명령까지 자세히 출력
cmake --build build --verbose

# 빌드 결과물 정리
cmake --build build --target clean
```

Ninja를 직접 실행해도 같은 프로젝트를 빌드할 수 있다. `-C build`는 먼저 `build/` 디렉터리로 이동한 것처럼 동작한다.

```bash
# 기본 타깃 빌드
ninja -C build

# main 타깃만 빌드
ninja -C build main

# 동시에 실행할 작업을 4개로 제한
ninja -C build -j 4

# 실제 clang++ 명령까지 출력
ninja -C build -v

# 실행할 명령만 확인하고 실제 빌드는 하지 않음
ninja -C build -n

# 빌드 가능한 타깃 목록 확인
ninja -C build -t targets

# 빌드 결과물 정리
ninja -C build clean
```

소스 파일을 수정한 뒤에는 다시 `ninja -C build`만 실행하면 된다. Ninja는 변경된 파일과 그 파일에 의존하는 대상만 다시 빌드한다.

```bash
# src/main.cpp 수정 후
ninja -C build
./build/main
```

`CMakeLists.txt`에 소스 파일이나 타깃을 추가했다면 프로젝트 설정을 갱신한 뒤 빌드한다.

```bash
cmake -S . -B build
ninja -C build
```

- 평소 빌드: `cmake --build build` 또는 `ninja -C build`
- 컴파일 오류의 전체 명령 확인: `ninja -C build -v`
- 어떤 명령이 실행될지 미리 확인: `ninja -C build -n`
- 완전한 새 설정이 필요할 때만 `build/`를 삭제하고 CMake부터 다시 실행

[Ninja 공식 매뉴얼](https://ninja-build.org/manual.html)에서 명령행 옵션과 Ninja 도구 목록을 확인할 수 있다.

## clangd 에디터 연동

VS Code에서는 `C/C++` 확장 대신 또는 함께 `clangd` 확장을 설치할 수 있다. 프로젝트 루트에서 `compile_commands.json`을 찾지 못하는 에디터를 위해 심볼릭 링크를 생성한다.

```bash
ln -sf "$PWD/build/compile_commands.json" compile_commands.json
```

이후 VS Code를 프로젝트 루트에서 다시 열면 코드 완성, 오류 검사, 정의 이동이 CMake 설정을 기준으로 동작한다.

## 표준 라이브러리 선택

Clang은 컴파일러이고 C++ 표준 라이브러리는 별도의 구성 요소이다. Linux에서는 Clang을 설치해도 기본적으로 GCC 계열의 `libstdc++`를 사용하는 경우가 많다. 특별한 이유가 없다면 배포판 기본 구성을 그대로 사용하는 것이 가장 간단하다.

```bash
clang++ main.cpp -o main
```

LLVM의 C++ 표준 라이브러리인 `libc++`를 사용하려면 개발 패키지를 추가로 설치하고 옵션을 명시한다.

```bash
# Ubuntu / Debian
sudo apt install libc++-dev libc++abi-dev

# libc++를 사용해 컴파일
clang++ -stdlib=libc++ main.cpp -o main
```

CMake 프로젝트 전체에서 libc++를 사용하려면 타깃 단위로 옵션을 설정한다.

```cmake:CMakeLists.txt
target_compile_options(main PRIVATE -stdlib=libc++)
target_link_options(main PRIVATE -stdlib=libc++)
```

`libstdc++`와 `libc++` 중 하나가 무조건 더 좋은 것은 아니다. 프로젝트가 요구하는 라이브러리 호환성, 배포 환경, 지원하는 C++ 표준 기능을 기준으로 선택하고 한 프로젝트 안에서는 일관되게 사용한다.

## 프로젝트 의존성 관리

외부 라이브러리는 소스 파일을 직접 복사하기보다 패키지나 CMake 타깃으로 관리한다. 처음에는 배포판 패키지를 사용하는 방식이 가장 단순하다.

```bash
# Ubuntu / Debian에서 fmt 라이브러리 설치 예시
sudo apt install libfmt-dev
```

설치된 라이브러리는 `find_package`로 찾고 타깃에 연결한다.

```cmake:CMakeLists.txt
find_package(fmt REQUIRED)

target_link_libraries(main PRIVATE
    fmt::fmt
)
```

소스에서 헤더를 포함한다.

```c++
#include <fmt/format.h>
```

규모가 커지거나 여러 운영체제에서 같은 버전의 의존성이 필요하면 Conan, vcpkg 또는 CMake `FetchContent` 같은 도구를 검토한다. 한 프로젝트에서 여러 패키지 관리 방식을 무분별하게 섞으면 버전과 링크 설정을 추적하기 어려워지므로 주된 방식을 하나 정한다.

## 테스트 환경 추가

CMake에는 테스트 실행 도구인 CTest가 포함되어 있다. 먼저 간단한 테스트 실행 파일을 추가한다.

```txt
cpp/
├── CMakeLists.txt
├── include/
├── src/
└── tests/
    └── calculator_test.cpp
```

```c++:tests/calculator_test.cpp
#include "calculator.hpp"

#include <cassert>

int main()
{
    assert(add(10, 20) == 30);
    assert(add(-1, 1) == 0);
    return 0;
}
```

테스트 타깃을 `CMakeLists.txt`에 등록한다.

```cmake:CMakeLists.txt
include(CTest)

if(BUILD_TESTING)
    add_executable(calculator_test
        tests/calculator_test.cpp
        src/calculator.cpp
    )

    target_include_directories(calculator_test PRIVATE
        ${CMAKE_CURRENT_SOURCE_DIR}/src
    )

    add_test(
        NAME calculator_test
        COMMAND calculator_test
    )
endif()
```

빌드 후 CTest를 실행한다.

```bash
cmake --build build/debug
ctest --test-dir build/debug --output-on-failure
```

`--output-on-failure`는 성공한 테스트의 불필요한 출력은 줄이고 실패한 테스트의 메시지를 표시한다. 실제 프로젝트에서는 GoogleTest나 Catch2 같은 테스트 프레임워크를 연결할 수 있지만, CTest는 어떤 테스트 실행 파일을 언제 실행할지 관리하는 상위 도구로 계속 사용할 수 있다.

## 코드 포맷과 정적 분석

### clang-format

프로젝트 루트에 `.clang-format`을 생성한다.

```yaml:.clang-format
BasedOnStyle: LLVM
IndentWidth: 4
ColumnLimit: 100
```

파일 하나를 바로 수정한다.

```bash
clang-format -i src/main.cpp
```

프로젝트의 C++ 파일 전체에 적용한다.

```bash
find src include tests -type f \
  \( -name '*.cpp' -o -name '*.hpp' \) \
  -exec clang-format -i {} +
```

### clang-tidy

프로젝트 루트에 `.clang-tidy`를 생성한다.

```yaml:.clang-tidy
Checks: >
  clang-diagnostic-*,
  clang-analyzer-*,
  bugprone-*,
  performance-*,
  modernize-*
WarningsAsErrors: ''
HeaderFilterRegex: '.*'
```

`clang-tidy`가 실제 컴파일 옵션을 알 수 있도록 앞에서 생성한 `compile_commands.json`을 사용한다.

```bash
clang-tidy -p build/debug src/main.cpp
```

처음부터 모든 진단을 오류로 처리하면 기존 코드 수정량이 지나치게 커질 수 있다. 필요한 검사 그룹부터 적용하고 프로젝트 규칙이 안정된 뒤 범위를 넓힌다.

## Git에서 제외할 파일

CMake와 Ninja가 생성한 빌드 결과는 소스 코드가 아니므로 일반적으로 Git에 커밋하지 않는다. 프로젝트 루트의 `.gitignore`에 다음 내용을 추가한다.

```gitignore:.gitignore
build/
compile_commands.json
.cache/
```

다음 파일은 저장소에 포함한다.

- `CMakeLists.txt`
- 직접 작성한 `.cpp`, `.hpp` 파일
- `.clang-format`, `.clang-tidy`
- 테스트 코드와 프로젝트 문서

빌드 디렉터리를 저장소에 포함하지 않으면 다른 환경에서도 CMake 설정부터 깨끗하게 재생성할 수 있다.

## 일상적인 개발 순서

최초 한 번 Debug 빌드 디렉터리를 설정한다.

```bash
cmake -S . -B build/debug -G Ninja \
  -DCMAKE_C_COMPILER=clang \
  -DCMAKE_CXX_COMPILER=clang++ \
  -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
```

이후 평소에는 다음 순서를 반복한다.

```bash
# 1. 변경된 코드 포맷
clang-format -i src/main.cpp

# 2. 증분 빌드
cmake --build build/debug

# 3. 테스트
ctest --test-dir build/debug --output-on-failure

# 4. 실행
./build/debug/main
```

문제가 발생하면 LLDB로 실행한다.

```bash
lldb ./build/debug/main
```

배포 전에는 별도의 Release 빌드로 최종 동작과 성능을 확인한다.

```bash
cmake --build build/release
ctest --test-dir build/release --output-on-failure
./build/release/main
```

## 자주 발생하는 문제

### clang++를 찾을 수 없음

```bash
command -v clang++
clang++ --version
```

명령이 아무것도 출력하지 않으면 배포판에 맞는 `clang` 패키지를 다시 설치한다.

### CMake가 이전 컴파일러를 계속 사용함

CMake는 선택한 컴파일러를 빌드 디렉터리의 캐시에 저장한다. 컴파일러를 변경할 때는 새 빌드 디렉터리를 만드는 것이 안전하다.

```bash
cmake -S . -B build/clang -G Ninja \
  -DCMAKE_C_COMPILER=clang \
  -DCMAKE_CXX_COMPILER=clang++
```

### 헤더 파일을 찾을 수 없음

오류에 표시된 헤더가 프로젝트 헤더인지 외부 라이브러리 헤더인지 먼저 구분한다.

```txt
fatal error: 'calculator/calculator.hpp' file not found
```

프로젝트 헤더라면 `target_include_directories`가 실제 `include/` 경로를 가리키는지 확인한다. 외부 라이브러리라면 개발 패키지가 설치됐는지와 `target_link_libraries`에 올바른 CMake 타깃을 추가했는지 확인한다.

### undefined reference

헤더를 찾았지만 링크 단계에서 함수 구현을 찾지 못할 때 발생한다.

```txt
undefined reference to `add(int, int)`
```

- 구현이 있는 `.cpp` 파일을 타깃에 등록했는지 확인
- 필요한 라이브러리를 `target_link_libraries`에 연결했는지 확인
- 함수 선언과 구현의 이름, 매개변수 타입이 같은지 확인

### clangd만 헤더를 찾지 못함

터미널 빌드는 성공하지만 에디터에만 오류가 표시되면 `compile_commands.json` 경로를 확인한다.

```bash
ls -l build/debug/compile_commands.json
ln -sf "$PWD/build/debug/compile_commands.json" compile_commands.json
```

### Release에서는 브레이크포인트가 이상하게 이동함

Release 최적화 과정에서 코드가 제거되거나 순서가 바뀔 수 있다. 일반적인 디버깅에는 Debug를 사용하고, 최적화 상태가 필요한 문제에는 `RelWithDebInfo`를 사용한다.

## 빌드 설정을 바꿀 때

CMake 생성기나 컴파일러를 바꾼 뒤 기존 `build/`를 그대로 사용하면 이전 설정이 남아 오류가 날 수 있다. 이 경우 빌드 디렉터리만 다시 생성한다.

```bash
rm -rf build
cmake -S . -B build -G Ninja \
  -DCMAKE_C_COMPILER=clang \
  -DCMAKE_CXX_COMPILER=clang++ \
  -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
cmake --build build
```

`rm -rf build`는 프로젝트의 빌드 결과 디렉터리만 지우는 명령이다. 실행 전에 현재 위치가 프로젝트 루트이고 삭제 대상이 정확히 `build`인지 확인한다.

[CMake 공식 튜토리얼](https://cmake.org/cmake/help/latest/guide/tutorial/Before%20You%20Begin.html)에서도 `cmake -G Ninja -B build`, `cmake --build build`, `./build/실행파일` 순서의 out-of-source 빌드를 사용한다.
