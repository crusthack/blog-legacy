> 기존 Next.js MDX 블로그를 단순 정적 블로그가 아니라 웹에서 글을 작성하고 수정할 수 있는 콘텐츠 플랫폼으로 확장하기 위한 구조 제안서이다.

# 1. 프로젝트 목표

현재 블로그는 `posts` 디렉터리의 MDX 파일을 Next.js가 직접 읽어 정적/서버 렌더링하는 구조이다. 이 구조는 개인 블로그나 공개 문서에는 적합하지만, 다음 기능을 추가하려면 별도의 백엔드와 데이터 저장소가 필요하다.

- 로그인 기반 사용자 관리
- 웹 에디터를 통한 MD/MDX 작성 및 수정
- 글 읽기 권한 설정
- 외부인의 댓글 작성
- 게시판 형태의 사용자 포스트 작성
- 관리자 승인 및 권한 관리
- 글 수정 이력 관리
- 검색, 조회수, 신고, 알림 같은 확장 기능

따라서 이 프로젝트는 기존 정적 MDX 블로그를 Next.js 프론트엔드와 ASP.NET Core 백엔드를 사용하는 콘텐츠 플랫폼으로 확장하는 것을 목표로 한다.

# 2. 기본 방향

최종 구조는 Next.js 서버와 ASP.NET Core 서버를 분리하는 방식을 기본으로 한다.

```txt
Browser
  -> Reverse Proxy / CDN
      -> Next.js Server
      -> ASP.NET Core Web API
          -> Database
          -> File Storage
```

Next.js는 화면 렌더링과 사용자 경험을 담당하고, ASP.NET Core는 인증, 권한, 데이터 저장, 댓글, 게시판 같은 도메인 기능을 담당한다.

```txt
Next.js
  - 페이지 라우팅
  - SSR / SSG / ISR
  - MDX 렌더링
  - SEO
  - 에디터 UI
  - 게시판 UI
  - 사용자별 화면 구성

ASP.NET Core
  - 인증
  - 권한
  - 포스트 CRUD
  - 댓글 CRUD
  - 게시판
  - 파일 업로드
  - 승인/신고/관리 기능
  - DB 트랜잭션
```

# 3. 배포 구조 판단

## 3-1. GitHub Pages 정적 배포

GitHub Pages에 Next.js 정적 export 결과물을 배포하는 방식은 비용 면에서 장점이 있다.

```txt
Browser
  -> GitHub Pages
  -> ASP.NET Core API
```

이 방식은 공개 포스트, 랜딩 페이지, 오래된 아카이브 문서처럼 변경 빈도가 낮고 권한이 필요 없는 콘텐츠에 적합하다.

하지만 전체 서비스를 이 구조로 운영하면 다음 제한이 생긴다.

- SSR 기반 권한 처리를 할 수 없다.
- 로그인 사용자별 HTML 렌더링이 어렵다.
- ISR을 사용할 수 없다.
- 비공개 글 본문을 정적 HTML에 포함할 수 없다.
- 글 수정 후 GitHub Actions 빌드와 배포를 기다려야 한다.
- 사용자 작성 글이 많아질수록 빌드 비용과 배포 지연이 커진다.

따라서 GitHub Pages는 전체 서비스의 기본 배포 방식보다는 공개 정적 콘텐츠를 위한 보조 배포 방식으로 보는 것이 적절하다.

## 3-2. Next.js 서버 + ASP.NET Core 서버

이 프로젝트의 기본 배포 방식은 Next.js 서버와 ASP.NET Core 서버를 각각 실행하는 방식이다.

```txt
:3000  Next.js
:5000  ASP.NET Core
:443   Nginx / Caddy / IIS Reverse Proxy
```

외부에는 HTTPS 포트만 열고, Reverse Proxy가 요청을 분배한다.

```txt
https://example.com/        -> Next.js
https://example.com/api/... -> ASP.NET Core
```

이 구조의 장점은 다음과 같다.

- 공개 글은 Next.js에서 정적 생성 또는 캐시할 수 있다.
- 권한 글은 SSR 과정에서 권한 확인 후 렌더링할 수 있다.
- 글 수정 후 즉시 반영하거나 경로 단위로 캐시를 무효화할 수 있다.
- 로그인 사용자별 UI를 서버에서 구성할 수 있다.
- ASP.NET Core API를 모바일 앱이나 다른 클라이언트에서도 재사용할 수 있다.
- 인증, 권한, DB 트랜잭션을 프론트엔드 서버와 분리할 수 있다.

# 4. 콘텐츠 저장 방식

기존 구조에서는 MDX 파일이 Git 저장소의 `posts` 디렉터리에 존재한다.

```txt
posts/
  Theory/
  Practice/
  Project/
```

확장 후에는 ASP.NET Core와 DB가 포스트 원문을 소유한다.

```txt
Post
  id
  slug
  boardId
  authorId
  title
  summary
  contentMdx
  status
  visibility
  createdAt
  updatedAt
  publishedAt
```

Next.js는 더 이상 파일시스템에서 MDX를 직접 읽지 않고 ASP.NET Core API를 통해 포스트 데이터를 가져온다.

```ts
const post = await api.posts.getBySlug(slug)
```

ASP.NET Core는 권한 검사를 통과한 경우에만 MDX 원문과 메타데이터를 반환한다.

# 5. 렌더링 전략

콘텐츠의 성격에 따라 렌더링 방식을 다르게 가져간다.

```txt
공개 포스트
  -> SSG / ISR / CDN 캐시

오래된 공개 포스트
  -> 긴 캐시

최근 공개 포스트
  -> 짧은 ISR 또는 on-demand revalidation

회원 전용 포스트
  -> SSR + 권한 확인

역할 제한 포스트
  -> SSR + 권한 확인

초안 / 비공개 포스트
  -> 동적 렌더링

관리자 / 편집 페이지
  -> no-store
```

본문과 동적 기능은 분리한다.

```txt
PostBody
  -> 캐시 가능

CommentList
  -> 짧은 캐시 또는 동적 API

CommentForm
  -> 로그인/권한 기반 동적 처리

EditButton
  -> 사용자 권한 기반 표시
```

공개 글은 빠르게 제공하고, 댓글과 수정 권한 같은 기능은 API를 통해 동적으로 처리한다.

# 6. 인증과 권한

권한 판단의 최종 책임은 ASP.NET Core가 가진다.

```txt
Next.js
  - 버튼 표시 여부
  - 사용자별 UI 구성
  - 로그인 상태에 따른 화면 분기

ASP.NET Core
  - 실제 데이터 접근 권한 검사
  - 수정/삭제/댓글 작성 권한 검사
  - 관리자 정책 검사
```

프론트엔드의 권한 값은 UI 편의를 위한 값일 뿐 보안 경계가 아니다.

```ts
if (post.permissions.canEdit) {
  // 수정 버튼 표시
}
```

실제 수정 요청은 반드시 ASP.NET Core에서 다시 검사해야 한다.

```txt
PUT /api/posts/{id}
  -> 사용자 인증 확인
  -> 작성자 또는 관리자 여부 확인
  -> 포스트 수정
```

기본 권한 모델은 다음과 같이 시작한다.

```txt
visibility
  - public
  - members
  - roles
  - private

role
  - Admin
  - Editor
  - Member
  - Guest
```

복잡한 권한은 별도의 리소스 권한 테이블로 확장한다.

```txt
PostPermission
  postId
  roleId
  userId
  canRead
  canEdit
  canComment
```

# 7. 댓글과 게시판

댓글은 로그인 사용자와 외부인을 모두 고려한다.

```txt
Comment
  id
  postId
  authorId
  guestName
  body
  status
  createdAt
```

외부인 댓글은 스팸과 악성 입력을 고려해야 하므로 다음 정책이 필요하다.

- 게시판 또는 포스트 단위 외부 댓글 허용 여부
- CAPTCHA 또는 rate limit
- 관리자 승인 후 공개 옵션
- 신고 및 숨김 처리
- IP 또는 fingerprint 기반 제한

게시판은 포스트의 묶음이자 권한 정책의 기준이 된다.

```txt
Board
  id
  slug
  name
  allowGuestComment
  allowMemberPost
  requirePostApproval
  requireCommentApproval
```

# 8. MDX 보안

사용자가 MDX를 작성할 수 있게 되면 MDX는 단순 문서가 아니라 실행 가능한 표현 계층이 된다. 따라서 아무 JSX나 허용하면 위험하다.

기본 정책은 다음과 같다.

- 서버에는 MDX 원문을 저장한다.
- Next.js에서 허용된 컴포넌트만 등록해 렌더링한다.
- 일반 사용자 게시글은 Markdown subset으로 제한하는 것을 우선 고려한다.
- 관리자 또는 신뢰된 작성자에게만 확장 MDX 기능을 허용한다.
- 위험한 HTML, 임의 import, 임의 script 실행을 제한한다.
- 렌더링 전 sanitizing 정책을 둔다.

개인 블로그 글과 사용자 게시판 글은 같은 작성 권한을 부여하지 않는 것이 좋다.

```txt
관리자/작성자 개인 글
  -> 제한된 MDX 허용

일반 사용자 게시판 글
  -> Markdown 중심
```

# 9. API 공유 구조

C# DTO와 TypeScript 타입을 손으로 따로 관리하면 시간이 지날수록 불일치가 발생한다. 따라서 ASP.NET Core가 API 계약을 소유하고, Next.js는 생성된 타입과 클라이언트를 사용하는 구조가 좋다.

```txt
ASP.NET Core
  -> OpenAPI / Swagger 생성

Next.js
  -> OpenAPI 기반 TypeScript 타입 생성
  -> lib/api/client.ts에서 API 접근 중앙화
```

예상 구조는 다음과 같다.

```txt
backend/
  Controllers/
  DTOs/
  Program.cs

frontend/
  lib/
    api/
      client.ts
      generated/

contracts/
  openapi.json
```

프론트엔드는 직접 `fetch`를 흩뿌리지 않고 API client를 통해 접근한다.

# 10. 캐시 무효화

공개 포스트를 수정하면 ASP.NET Core가 저장 후 Next.js의 캐시 무효화 엔드포인트를 호출한다.

```txt
1. 작성자가 글 수정
2. ASP.NET Core가 DB 업데이트
3. ASP.NET Core가 Next.js revalidate endpoint 호출
4. Next.js가 /posts/{slug} 또는 post:{id} 캐시 무효화
5. 다음 요청에서 최신 HTML 생성
```

캐시 키는 경로와 태그를 함께 사용한다.

```txt
path
  /posts/{slug}
  /boards/{slug}

tag
  post:{id}
  board:{id}
  posts:list
```

# 11. 단계별 구현 계획

## 1단계: 백엔드 기반 마련

- ASP.NET Core Web API 프로젝트 생성
- DB 연결
- User, Role, Post, Board, Comment 기본 모델 정의
- OpenAPI 문서 생성
- Next.js에서 API client 생성

## 2단계: 포스트 조회 이전

- 기존 `posts` 파일 기반 데이터를 DB로 이관
- `getPostData` 계층을 API 기반으로 교체
- 공개 포스트 조회 API 구현
- Next.js에서 MDX 렌더링 유지

## 3단계: 인증과 권한

- 로그인/로그아웃 구현
- HttpOnly cookie 기반 세션 또는 토큰 정책 결정
- public, members, private 권한 구현
- SSR에서 권한 기반 페이지 처리

## 4단계: 웹 에디터

- 관리자/작성자용 에디터 페이지 구현
- MD/MDX 미리보기
- 저장, 발행, 비공개, 초안 상태 구현
- 수정 이력 저장

## 5단계: 댓글

- 로그인 사용자 댓글
- 외부인 댓글
- 승인/숨김/삭제
- rate limit 및 스팸 대응

## 6단계: 게시판

- 게시판 생성 및 관리
- 사용자 포스트 작성
- 게시판별 작성 권한
- 승인 후 공개 옵션

## 7단계: 운영 기능

- 검색
- 조회수
- 신고
- 알림
- 관리자 대시보드
- 백업 및 감사 로그

# 12. 최종 판단

이 프로젝트는 정적 블로그보다 콘텐츠 플랫폼에 가깝다. 따라서 GitHub Pages 중심 정적 배포보다는 Next.js 서버와 ASP.NET Core 서버를 분리하는 구조가 적합하다.

정적 배포는 공개 문서나 오래된 아카이브 글에는 유용하지만, 로그인, 권한, 댓글, 게시판, 웹 편집 기능을 중심으로 보면 서버 기반 구조가 더 자연스럽다.

최종 권장 구조는 다음과 같다.

```txt
Browser
  -> CDN / Reverse Proxy
      -> Next.js Server
          -> SSR / SSG / ISR
          -> MDX render
          -> UI
      -> ASP.NET Core API
          -> Auth
          -> Authorization
          -> Posts
          -> Boards
          -> Comments
          -> DB
```

Next.js는 사용자에게 보이는 웹 경험과 렌더링을 담당하고, ASP.NET Core는 데이터와 권한을 책임지는 도메인 서버로 둔다. 이 분리는 초기에는 약간 복잡하지만, 프로젝트가 블로그를 넘어 게시판과 CMS로 확장될수록 유지보수와 보안 측면에서 이점이 커진다.
